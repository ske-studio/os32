# VDM画面取得・GUI表示・遠隔操作の検討草案

状態: 計画（本線とは別の設計検討。実装・性能保証・着手時期は未決）
作成: 2026-09-28 JST
経緯: 2026-09-27〜28のユーザーとの議論
対象実機: PC-9821Ra266。ユーザー手元ではKAPI v65のOS32が起動済み。

## 1. 目的と位置付け

DOSソフトにOS32を意識させず、実機の余力で表示・入出力・ホストサービスを拡張する。
VDMの画面を高解像度OS32GUIのウィンドウへ表示し、ホストPCおよびホストを中継する他デバイスから操作できる構成を検討する。

ユーザーの実用目標は、対象DOSソフトにi386SX/16MHz程度の処理能力が残ること。
これはVDM内の対象ソフトに対する目標であり、OS32自体の最低CPU条件の変更ではない。
CPUのクロック比だけで割当率を決めず、対象ソフトの応答、音声、描画、割り込み遅延で評価する。

本書は独立草案であり、既存ロードマップ、凍結済みHAL、KAPI、GUI契約の変更を決定しない。
[アプリケーション優先設計](DESIGN_APP_FIRST.md)の「前景1アプリへ資源を集中する」思想を、DOS資産にも適用する検討である。
カーネルは権限・マッピング・割り込み・装置所有権を担当し、画像管理や変換の方針は共通エンジンへ置く。

## 3. 根拠と前提

### 3.1 従来GVRAM

ユーザー提供のPC9800Bible「2-7 グラフィック」§2-7-2には、VRAMは16bitバス接続で、32bitアクセスも16bitアクセス2回相当になる旨の記述がある。
Ra266でも従来の互換GVRAM経路について、この構造を前提に設計する。
待ち時間を含む実効読み出し速度は未測定である。PCIの公称帯域やCPUのメモリバス幅をそのまま当てはめない。

640×400・16色では以下を区別する。

| 対象 | 大きさ |
|---|---:|
| 1プレーンのメモリ窓 | 32,768 B |
| 4プレーンの1ページ | 131,072 B = 128 KiB |
| 表裏2ページの搭載量 | 262,144 B = 256 KiB |
| 通常の640×400の表示データ | 80 B/行 × 400行 × 4 = 128,000 B |

プレーンの先頭はA8000h、B0000h、B8000h、E0000h。
表示ページはA4h、CPUアクセス対象の描画ページはA6hで指定する。
描画ページをそのまま読むだけでは、表示中のページを取れるとは限らない。

スクロール、画面分割、表示開始位置によって、必要なVRAM範囲は変わる。
128,000 Bの線形コピーは通常表示の基準試験とし、実際のキャプチャは表示状態を反映するか、128 KiBのページ全体と表示状態を保持する。

提供された「4-4 ウェイト数」はI/O命令間の待ち時間であり、GVRAMのメモリ読み出しサイクル表ではない。
「3-1 H98・MATEの性能」も機能概要であり、Ra266の読み出し帯域の実測資料ではない。
「4-2 メモリマップ」の変換済み表には範囲・容量・プレーン表記の不整合があるため、実装時は§2-7-2および原資料と突き合わせる。

ハード資料の原文・添付ファイルはコミットしない。保管方針は[索引の外部リファレンス](INDEX.md)に従う。

### 3.2 現行実装との境界

- [v86_mem.c](../kernel/v86_mem.c): VDMのGVRAMは実物理へ直マップされる。
- [v86_io.c](../kernel/v86_io.c): グラフィックス関連I/Oには素通し経路がある。取得に必要な状態の全てを既に追跡できるとは限らない。
- [GUIからの全画面処理](tasks/gui/v13/TASK_T8_fullscreen_gfx.md): 現行はVDMの実VRAM書き込みとGUI表示の競合を理由に起動を制限する。
- [Host Services](tasks/network/HOST_SERVICES_PLAN.md): 画面更新・遠隔入力は本書の追加提案であり、既存サービスの実装済み機能と混同しない。
- [KAPI仕様](KAPI_SPEC.md): sys_time_nowはv59で追加。v65で利用できる。

これらは2026-09-28にfeat/guiのソース・仕様で確認した内容。
起動中のv65の正確なコードはverのCommitとImage CRCで特定してから測定プログラムをビルドする。

## 4. 共通化する境界

| 層 | 責務 |
|---|---|
| カーネル/HAL | 装置所有権、必要なメモリ窓、割り込み、状態変更の排他、計時 |
| PC-98画面取得器 | 4プレーンと表示状態の取得、必要に応じたTVRAM・文字情報の取得 |
| 共通画面エンジン | プレーン解釈、パレット適用、テキスト合成、変更領域管理、画像形式変換 |
| ローカル出力 | 共通サーフェスをOS32GUIへ渡す。クリッピングと拡大表示 |
| 遠隔出力 | 元プレーンまたは画像の差分、RLE、フレーム管理、ホストサービスへの送信 |
| カードドライバ | 通常の画像転送・表示。BitBLT、色変換、拡大、GPU合成などは任意の高速化 |

「共通化」は全出力を一律にRGBへ展開することを意味しない。
取得した元プレーンと状態を一度だけRAMに保持し、ローカル用変換と遠隔送信が共有する。
遠隔のみならホスト側でプレーン合成できる。PCIカードの表示色深度に通信形式を従属させない。

最小構成はCPUによる共通変換と通常の画像転送。
Cirrus/Matroxの2D機能、6200AのGPU処理へ置き換える場合も、PC-98の状態解釈を各ドライバへ重複実装しない。
具体的な関数名・構造体・能力ビットは未凍結。

## 5. 高解像度GUIと遠隔操作

### 5.1 ローカル

従来GVRAMをVDMの描画先として使い、追加PCIカードを高解像度GUIの表示先にする構成を第一候補とする。
640×400の内容をサーフェスとしてGUIに渡し、ウィンドウ移動・クリッピング・拡大に対応する。
PC-98の画素縦横比を保つ表示と整数倍表示の扱いは別途定義する。

PCIカード初期化、VGA資源との競合、表示切替、GUI側のサーフェス形式への対応が必要。
現行のGUI起動制限を外すだけでは実現しない。

### 5.2 ホストと中継

OS32からホストPCへ元プレーン＋状態または画像更新を送り、ホストが表示・動画エンコード・他デバイスへの配信を担当する。
入力は逆向きに正規化したキー/マウスイベントを送り、OS32のVDM入力経路へ注入する。
ローカル入力と遠隔入力の所有権、フォーカス、接続断時の押下解除を定義する。

画面更新にはサイズ、形式、パレット/モード世代、フレーム番号、差分の基準番号を持たせる案とする。
実際のワイヤ形式は[リンク計画](tasks/network/LINK_PLAN.md)との整合を確認して決める。
送信待ちをVDMの実行待ちへ直結させず、キューを有限にする。
差分の基準フレームを捨てた場合は、送達済み基準から差分を作り直すか、全画面で再同期する。

OS32GUI全体を高解像度のまま遠隔表示する場合は、VDMの640×400だけを送る場合と別の帯域評価が必要。

## 6. 帯域とRLE

下表は640×400、60回/秒、画像データのみ。MBは10^6 B。
音声、TVRAM、状態、通信ヘッダは別途加算する。

| 送信形式 | 1画面 | 60回/秒 |
|---|---:|---:|
| 4プレーン（表示データのみ） | 128,000 B | 7.68 MB/s = 61.44 Mbit/s |
| 4プレーン（ページ全体） | 131,072 B | 約7.86 MB/s = 約62.91 Mbit/s |
| インデックス8bit | 256,000 B | 15.36 MB/s = 122.88 Mbit/s |
| RGB565 | 512,000 B | 30.72 MB/s = 245.76 Mbit/s |
| XRGB8888 | 1,024,000 B | 61.44 MB/s = 491.52 Mbit/s |

Ra266のNEC仕様にはオンボードPCIの100BASE-TXが記載される。
100 Mbit/sの回線では元プレーンの無圧縮60回/秒が計算上収まる。
RFC 6349の通常MTUでのTCP理想上限は約94.9 Mbit/s。ただしOS32のNICドライバ、プロトコル、コピー回数、CPU負担を含む持続転送性能は未確認。
LGY-98等の10 Mbit/s経路とは区別する。

RLEは以下の選択を提案する。

1. 画像が不変なら状態変更のみを送る。
2. 変更ブロックまたは前回との差分（XOR等）をRLE化する。
3. 縮まらなければ無圧縮へ戻す。
4. パレット変更だけのときはプレーンを再送せず、受信側で再合成する。

一様な領域や疎な差分には有効。毎フレーム全体が変化する映像・細かな模様では圧縮率を保証しない。
圧縮がCPU時間を消費するので、無圧縮の方が有利な条件も測る。
全画面を読んで差分判定する方式では、RLEでGVRAM読み出し量自体は減らない。

## 7. 性能予測の扱い

議論中の予測は「30回/秒をまず狙い、60回/秒も検討可能」。
仮説として10〜20 MB/sを中心に置いたが、Ra266の測定値で裏付けられていない。
下表は読み出し＋RAM格納の実効速度を仮定した条件計算であり、ハードウェア仕様値ではない。

| 仮定した速度 | 128,000 Bのコピー | 30回/秒の取得時間比 | 60回/秒の取得時間比 |
|---|---:|---:|---:|
| 5 MB/s | 25.6 ms | 76.8% | 153.6%（成立しない） |
| 10 MB/s | 12.8 ms | 38.4% | 76.8% |
| 20 MB/s | 6.4 ms | 19.2% | 38.4% |

上記は取得処理だけ。変換・圧縮・通信・DOS自身の処理時間を含まない。
16bit幅だけから速度を断定しない。32bit命令へ変えても装置側の幅が倍になるとは考えない。
命令数削減の効果は16bit版と32bit版を実測して評価する。

ゲストの最低実用性とサービスに使う予算を先に定め、余力を画面取得・合成・通信へ配る。
無制限のゲスト優先でサービスが飢餓状態になる構成も避ける。
取得頻度、ゲストへ戻るまでの最大時間、音声/入力遅延を調整する。
20/30/60回/秒は評価条件であり、PC-98のネイティブVSYNCが常に60Hzという意味ではない。

## 8. KAPIv65での実測計画

### 8.1 時計

KAPIのsys_time_now(u32 *lo, u32 *hi)を使う。
成功時0、出力は同じスナップショットの64bit経過µsの下位/上位32bit。
tick_countとPIT ch0のラッチ値から補間する。仕様・エラー処理の正典は[KAPI_SPEC](KAPI_SPEC.md)の「µs 時計 (v59)」。

- get_tickは10ms刻みだが、sys_time_nowはµs単位の値を返す。
- 表現単位1µsと、呼出しオーバーヘッドを含む測定精度は区別する。
- 開始/終了の戻り値を確認し、失敗したサンプルは採用しない。
- IRQ0を長時間止めない。10ms周期を複数回またぐ割り込み禁止では時刻を取りこぼし得る。
- 空測定とRAM対照を行い、連続呼び出しコストとコピー時間を分ける。
- DOSゲストからこの32bit KAPIを直接呼べるとはしない。DOS＋RDTSC案は補助比較とする。

計時のためのKAPI追加は不要。起動中カーネルの更新が必要かどうかはアクセス経路で決まる。

### 8.2 実行権限と配備

通常のCPL3アプリからGVRAMの物理番地を直接参照しない。
[ビルド手順](08_build.md)と[実行モデル](09_exec.md)に従い、v65対応のCUI専用診断プログラムを検討する。
CPL0実行がその版で利用できるなら診断用途に限定して使う。利用できなければ限定したカーネル内診断が必要になる。
一般アプリへ任意物理メモリアクセスを追加する設計にはしない。

v65のABI・OS32Xヘッダ・CRT・データ欄配置に適合させ、min_api_verを対応範囲に設定する。
最新SDKでビルドしただけでv65へ配備できるとはみなさない。
verのCommit/Image CRC、実行した測定バイナリ、起動方法を記録する。

### 8.3 最初の測定

1. CUIで既知の従来16色モード、ページ、GRCG/EGC状態にそろえる。
2. GVRAM→RAMを16bit版と32bit版で測る。表示データ128,000 Bとページ全体131,072 Bを区別する。
3. 転送先は4プレーン分を保持できるRAMを確保する。比較対象も同じサイズ・配置条件にする。
4. 最適化で読み出しや書き込みが消えない実装にする。測定中はログを出さず、結果は終了後に表示する。
5. 単発を複数回測り、中央値・最大値・可能なら上位分位を記録。一定回数の合計測定も行う。
6. RAM→RAM対照、時計の空測定、16bit/32bit版のデータ一致を確認する。
7. 表示ON/OFF、ページ、取得頻度の条件を明記する。通常運用の採否は表示ONの結果で判断する。

GRCG/EGCの読出しモード、表示/描画ページ、書込み専用レジスタの状態復元を先に設計する。
書込み専用の値をINで保存できると仮定しない。
状態を変更したままVDMへ戻さない。初期測定はゲストと同時実行せず、次段で共存条件を測る。

測定値からの算出:

- 1画面平均µs = 合計経過µs / コピー回数
- MB/s = 1画面バイト数 × コピー回数 / 合計経過µs
- 取得時間比 = 1画面平均µs × 毎秒取得回数 / 1,000,000

### 8.4 続く測定

| 段階 | 確認すること |
|---|---|
| A: 取得のみ | GVRAM→RAMの帯域、16/32bit差、読み出し内容 |
| B: 共通変換 | プレーン→index8/RGB565/XRGB8888の時間、必要メモリ |
| C: 圧縮 | 静止画、部分更新、スクロール、全画面更新でRLE率と時間 |
| D: 通信 | 実NIC/ホストサービス経由の持続速度、キュー長、遅延 |
| E: VDM共存 | 対象DOSソフトの応答、音声、描画、最大停止時間 |
| F: 出力統合 | GUIウィンドウと遠隔表示、入力復帰、接続断、差分再同期 |

実機性能の採否をエミュレータの速度から決めない。
エミュレータは変換の正しさ、ページ/パレット/スクロール、復元、異常経路の検証に使う。

## 9. 未決事項と次の判断
