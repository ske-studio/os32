## 1. v1.x GUIシェル — 「デスクトップ革命」

**コンセプト**: Windows 3.1 / 早期 Windows 95 の**見た目**をモデルにしたグラフィカルデスクトップ環境。OS32のCLI・グラフィックス・ファイルシステム全技術の集大成。
API は Win16 の再現ではなく、その欠点を 386 で払える範囲の現代の様式で解消する
(2026-09-04 改訂。設計記録 [tasks/gui/DESIGN.md](tasks/gui/DESIGN.md)、凍結契約
[tasks/gui/API_CONTRACTS.md](tasks/gui/API_CONTRACTS.md))。

### 設計方針 (2026-09-04 改訂)

| 項目 | 決定 |
|------|------|
| デザインモデル | **Win3.1 / 早期Win95 の外観** — 協調型シングルタスクGUIデスクトップ (WM は gshell 常駐) |
| 描画方式 | **全面GFX描画**。9801 = 640×400×16色 (プレーン)、9821 = PEGC 640×480×256色 / ウィンドウアクセラレータ (Cirrus GD54xx) をバックエンド表で切替。テキストGDCは 9801 バックエンドの最適化にのみ使う |
| 再描画モデル | InvalidateRect 方式 (損傷 + commit)、ウィンドウ移動は XOR 枠のみ、全画面 1 枚のバックバッファ + クリップ |
| GUI起動方法 | CUIデフォルト + `os32gui` コマンド (コンフィグ書換え+リブート) |
| GUI API | **libos32gui** — Wayland 型協定 (非同期・ID 参照・型付き 16B イベント) + 保持型ウィジェット木 + ステートレス描画 + 箱レイアウト。Win32API 風の WndProc / SendMessage / DC は採らない |
| アプリ ⇄ WM の経路 | KAPI `gui_call(op, arg)` 1 本 + SHM ブロック 12〜15 (4 スロット)。ポインタは渡さない |
| GUI ライブラリの配置 | **共有ライブラリ帯域 0x400000〜0x4FFFFF** (固定アドレス・ジャンプ表)、アプリ本体は 0x500000 から (案 A) |
| メモリ配置 | シェル常駐帯域 1MB (0x300000-0x3FFFFF) — 完了 |
| 色 | 16 色を役割名で固定 (G6)。フォーカスのあるアプリに 14 色をリース (G8)、その間 WM は 2 色クロームで描く |
| GFXプログラム共存 | フルスクリーン占有 + 終了後GUI再描画 (WM がパレットを退避・復元) |
| CUI/GUI設定 | `/etc/system.cfg` (`GUI=0`/`GUI=1`) — FDDから復旧可能 |
| フォントキャッシュ | 既存KCGキャッシュ (295KB@0x100000) をそのまま使用 |
| GUI→CUI切替 | **明示的なGUIアクションが必須**。自動復帰なし |
| 性能上限 | Pentium 100MHz / 32MB で「超快適」。それ以上の機能は対象外 (DESIGN §0) |

### 技術基盤 (既存資産の活用)

| 既存資産 | GUIシェルでの活用 |
|---------|-----------------|
| libos32gfx | クライアントライブラリ G (描画) の下敷き。プレーン決め打ち部分は HAL バックエンド表の 9801 実装へ |
| libos32gui (Rust, 2026-09-03 版) | ウィンドウ管理部 → gshell の WM の核、ウィジェット部 → 共有ライブラリのウィジェット木 |
| KAPI v40 `gfx_screen_info` / `gfx_hw_*` | バックエンドの能力問い合わせと HW 塗り / BLT の枠 (CPU 実装は NOSYS) |
| lconsole (差分仮想VRAM) | ターミナルウィンドウの中核 (80×25セル→KCGでGVRAM描画) |
| ダーティ矩形転送 (`gfx_add_dirty_rect`) | 損傷統合の規則をそのまま WM の `invalidate` に使う |
| KCGフォントキャッシュ | ANK+漢字のグラフィカルテキスト描画 |
| スプライト機構 | マウスカーソル描画 |
| `ime_render` 関数表 | FEP の未確定文字列・候補窓を WM が GFX バックエンドで描く |
| `sys_halt` (v2 M0) | `OP_WAIT` のアイドル作法 |

### CUI → GUI 切替フロー

```
[CUI → GUI]
1. CUIシェルで `os32gui` 実行
2. /etc/system.cfg に GUI=1 書込み
3. sys_reboot() で再起動
4. カーネル: system.cfg 読取 → GUI=1
5. gshell.bin を Level 0 として起動

[GUI → CUI] ※明示的なGUIアクションが必須
1. ユーザが GUI上で明示的に「CUIに切替」アクションを実行
   (スタートメニュー → 「CUIモードで再起動」等)
2. gshell が /etc/system.cfg に GUI=0 書込み
3. sys_reboot() で再起動
4. カーネル: system.cfg 読取 → GUI=0
5. shell.bin を Level 0 として起動
※ 何もしなければ次回もGUIで起動する (永続設定)

[GUI終了プロセス]
1. ユーザが「シャットダウン」を選択
2. gshell: 全ウィンドウに Quit イベント
3. gshell: system.cfg は変更しない (次回もGUI起動)
4. gshell: gfx_shutdown() + exit
5. カーネル: テキストGDC START + system.cfg 再読取
6. カーネル: GUI=1 → gshell を再起動
   (GUI=0 に変更されていた場合のみ CUI shell を起動)

[ハング復旧]
1. FDDからブート → mount /hd0
2. edit /hd0/etc/system.cfg → GUI=0 に変更
3. リブート → CUIで起動
```

#### CUI/GUI抽象化レイヤーの設計

CUIプログラム (既存52本) をGUIターミナル上でも変更なしで動作させるための抽象化:

```
[CUI環境]                      [GUI環境]
  アプリ                         アプリ
    ↓                              ↓
  KernelAPI                      KernelAPI
  (shell_print等)                (同じAPI呼び出し)
    ↓                              ↓
  console.c (TVRAM直接)          console.c → gshellのターミナルウィンドウ
```

- 既存KAPIの `shell_print` / `console_write` をGUIモードで自動的にターミナルウィンドウにリダイレクト
- `kbd_getchar` / `kbd_getkey` をGUIイベントキューから取得するように切替
- GUI専用アプリは `libos32gui` APIを直接使用し、ウィンドウ・コントロールを操作

## 2. 長期ロードマップ (v2.0+)

### 協調型マルチタスク

v1.xはシングルタスクだが、v2.0ではタイマー割り込みベースの**協調型マルチタスク**を検討:
- ウィンドウごとに独立したプロセス
- メッセージパッシングによるIPC (v1.x の `gui_call` + SHM イベントリングを拡張。Win16 メッセージキューは採らない)
- 子プログラム実行中もデスクトップが応答可能

### 16bit DOSプログラム移植スキーム

```
[DOS 16bit .COM/.EXE]
        ↓
  逆アセンブル / 静的解析
        ↓
  INT 21h → KernelAPI マッピング
        ↓
  32bit OS32X として再コンパイル
```

- 半自動 + 手動修正が現実的
- 小さなツール (数KBの .COM) をケーススタディとして開始
- INT 21h → KernelAPI 互換レイヤーの設計が核心
