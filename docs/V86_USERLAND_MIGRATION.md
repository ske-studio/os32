# V86 ユーザー空間化 — 移行プランと切り分け思想

> 最終更新: 2026-05-15
> 位置付け: V86サブシステムの責務分離方針ドキュメント (Phase 0)
> 関連: [V86_STATUS.md](V86_STATUS.md), [KAPI_SPEC.md](KAPI_SPEC.md), [DEVELOPMENT.md](DEVELOPMENT.md)

---

## § 1. 背景と目的

### 1.1 現状

OS32 のv86サブシステムは、PC-9801上で MS-DOS / FreeDOS / DOSネイティブアプリ / ネイティブゲームをホストするために、リアルモード16ビット環境のエミュレーションをカーネル内で完結する設計で発展してきた。

しかし現時点で `kernel/` 配下に v86 関連ソースファイルが **37本 / 約11,325行** に達し、以下の問題が顕在化している。

- **カーネルメモリ破壊の頻発**: v86 セッションの起動・終了・BIOS HLE 経路で、カーネル側のスタック・ページテーブル・割り込みコンテキストの相互作用が複雑化し、ローカル変数すら信頼できない状況が発生 (代表例 §BUG-CTX, [V86_STATUS.md §12](V86_STATUS.md))。
- **改修ごとの影響範囲が読みにくい**: HLE ロジックの一行変更がカーネル全体のメモリレイアウト・ページング状態に波及するため、デバッグコストが上がっている。
- **ビルドの肥大化**: 11K 行超のv86コードがカーネルバイナリに含まれており、本来カーネルに不要な処理 (ジオメトリ計算、応答パケット生成、ログ整形等) が常駐している。

### 1.2 目的

本ドキュメントは、v86 サブシステムを以下の責務に再構成するための **思想と段階的な移行計画** を整理する。

- **カーネル**: 特権命令・ハードウェア例外・割り込み・ページング・I/Oトラップなど、Ring0 でしか実行できない処理のみを担当する。
- **外部プログラム**: BIOS High-Level Emulation (HLE)、セッション管理、Auto-Typer、ジオメトリ計算、ディスクイメージのマウント管理など、データ操作・状態管理が中心の処理を担当する。最終形は `programs/v86d/` (仮称) という常駐ユーザープログラムが DOS ブートシーケンスを駆動する。

### 1.3 ゴール

- DOS ブートシーケンスを外部プログラム側で記述できるよう、カーネルは「v86 ランタイム + イベントAPI」だけを提供する。
- 既存の `sys_v86_boot_image` / `sys_v86_boot_physical*` は段階的に置き換え、最終的には新APIのみで動作させる (旧APIは並存期間を設けてから削除)。
- メモリ破壊が起きた場合の影響範囲を、カーネルではなく外部プログラムのスタックに閉じ込める。

## § 2. カーネル / ユーザー切り分けの思想

### 2.1 「真にカーネル必須」の判定基準

以下のいずれかに該当する処理は **カーネルに残す**。

| 基準 | 例 |
|------|-----|
| 特権命令の発行 | CR0/CR3 書き込み、IDT/GDT 設定、IRETD、ring 切替 |
| ハードウェア例外の即時受理 | #GP (General Protection)、#PF (Page Fault) の一次受け |
| ハードウェア割り込みの即時応答 | IRQ0 (timer)、IRQ1 (KBD)、IRQ11 (FDC) の ISR 本体 |
| I/O ポート命令の #GP トラップ | V86 モードの IN/OUT は #GP で捕捉する必要があり、その一次デコードは Ring0 でしか行えない |
| ページテーブル直接書き込み | `paging_set_page*`、A20 切替時の PTE 改変 |
| DMA コントローラの設定 | µPD8237A の複数ポート同期、IRQ マスク変更を伴うため |
| V86 モード遷移 | `iretd` による VM ビット立て、レジスタ退避・復元 |

### 2.2 「ユーザー化が妥当」の判定基準

以下のいずれかに該当する処理は **外部プログラムへ移す候補**。

| 基準 | 例 |
|------|-----|
| データ変換のみ | CHS ↔ オフセット変換、ジオメトリ判定、セクタ長コード解釈 |
| HLE 応答内容の生成 | INT 1Bh / 18h / 29h / 1Ah / 11h / 12h / 1Ch の応答パケット生成 |
| BDA / IVT のデータ更新 | 0x055E (FDC 状態)、0x040 (タイマカウンタ) 等の書き換え内容生成 |
| セッションライフサイクル | ブート開始、Auto-Typer、終了処理、画面リストア |
| ディスクイメージ管理 | loop_dev のアタッチ・ジオメトリ取得 (KAPI で既に提供済み) |
| ログ・トレース・統計 | 計測・観測のためのデータ集約と整形 |

### 2.3 グレーゾーンの取り扱い基準

以下の判定軸で、その都度どちら側に置くか決定する。

- **リアルタイム要件があるか** → あればカーネル、なければユーザー
- **頻度が高くポーリング / IRQ 駆動か** → 高ければカーネル、まれならユーザー
- **状態がカーネル内オブジェクト (PT / IDT / TSS / IRQマスク) に依存するか** → 依存度が高ければカーネル
- **「いつでも安全に中断・再開できるか」** → できるならユーザー化候補

### 2.4 ユーザー化の副次的利点

- **障害の局所化**: ローカル変数 (スタック) 破壊問題が起きても、影響は外部プログラム自身のスタック内に閉じ込められる。§BUG-CTX のような事故がカーネル全体に波及しない。
- **カーネル変更の縮小**: BIOS HLE の仕様変更を KAPI_VERSION のインクリメントで管理でき、カーネルの再ビルドが減る。
- **不具合再現が容易**: 単体プログラムの実行で再現できるため、原因の絞り込みが速い。
- **コードレビューの対象縮小**: 「カーネルに入る変更」と「ユーザープログラムに入る変更」が分離されることでレビュー観点が明確になる。

## § 4. 現存 KernelAPI で既にユーザー化可能な部分

`exec/exec.h` の KernelAPI v38 で既に提供されている v86 関連 API。ユーザー化を進める際にはこれらを最大限再利用する。

| カテゴリ | API |
|---------|-----|
| ディスクイメージ管理 | `loop_attach`, `loop_detach`, `loop_status` |
| ブロック I/O (LBA) | `dev_blk_read`, `dev_blk_write` |
| 高レベル v86 ブート | `sys_v86_boot_image`, `sys_v86_boot_physical`, `sys_v86_boot_physical_ex` |
| ページング問い合わせ (R/O) | `paging_is_present` |

既存の `programs/cmds/v86.c` は `sys_v86_boot_image` 系を直接呼ぶ薄いラッパであり、Phase 5 まではこの API を維持する。

## § 5. 追加が必要な KernelAPI (新 API 群)

### 5.1 v86 イベント駆動 API (コア)

DOS ブートを完全に外部プログラム側で記述するために必要な、汎用 v86 ハンドル操作 API。

| API | 目的 |
|-----|------|
| `sys_v86_create(opts) -> handle` | v86 コンテキスト作成 (バッキングRAM確保、IVT/BDA初期化、画面退避を含む) |
| `sys_v86_run(handle, event_out) -> reason` | ブロッキング実行。#GP / INT / IO / HLT 発生でユーザーへ戻る |
| `sys_v86_get_regs(handle, regs_out)` | ゲストレジスタ取得 |
| `sys_v86_set_regs(handle, regs_in)` | ゲストレジスタ書き戻し |
| `sys_v86_read_mem(handle, gpa, buf, len)` | ゲスト物理アドレスからカーネル経由で読み出し |
| `sys_v86_write_mem(handle, gpa, buf, len)` | 同上、書き込み |
| `sys_v86_resume(handle)` | イベント処理後の再開 |
| `sys_v86_destroy(handle)` | リソース解放 |

**イベント種別 (案)**

```
V86_EV_INT        — INT n 命令発行 (n はイベント情報に含む)
V86_EV_IO_IN      — IN ポートアクセス
V86_EV_IO_OUT     — OUT ポートアクセス
V86_EV_HLT        — HLT 命令 (終了要求 or NOP は呼び出し側判断)
V86_EV_TIMEOUT    — 設定したタイムアウト経過
V86_EV_USER_EXIT  — Ctrl+Alt+Esc などホットキーによる脱出要求
```

これらの最小集合があれば、INT 1Bh の HLE は「`sys_v86_run` でブロック → `V86_EV_INT (n=0x1B)` で戻る → ユーザーがレジスタ参照しディスクイメージ操作 → `set_regs` で結果書き戻し → `sys_v86_resume`」のループで実装できる。

### 5.2 ディスク補助 API (任意)

| API | 目的 |
|-----|------|
| `dev_blk_read_chs(dev, c, h, s, count, buf)` | CHS 指定読み (既存 `dev_blk_read` は LBA のみ) |
| `dev_blk_write_chs(dev, c, h, s, count, buf)` | CHS 指定書き |

これらが必要かは Phase 3 着手時に再評価する。CHS→LBA 変換がユーザー側でジオメトリを保持すれば済むなら追加不要。

### 5.3 A20 制御

現状 `v86_mem.c` のポート 0xF2 フックがカーネル側で管理している。ユーザー側からは状態問い合わせのみ API 公開し、v86 ハンドルに紐づく状態として保持する程度で十分。

## § 6. 段階的移行ロードマップ

| Phase | 内容 | KAPI 変更 | 備考 |
|-------|------|-----------|------|
| **Phase 0** (本ドキュメント) | 思想・現状診断・ロードマップの確立 | なし | 本ドキュメントの作成と V86_STATUS.md への §BUG-CTX 追記 |
| **Phase 1** | §BUG-CTX の根本原因調査 (別タスク) | なし | スタック破壊原因の特定。ユーザー化前提を整える |
| **Phase 2** | v86 イベント駆動 API 追加 (§5.1) | KAPI 拡張 (旧 API 並存) | カーネル/ユーザー境界線の新設。`KAPI_VERSION` インクリメント |
| **Phase 3** | BIOS HLE の段階的ユーザー化 | KAPI 追加なし (イベント API 経由) | INT 1Bh → 18h → 1Ch → 29h → 11h → 12h の順を想定 |
| **Phase 4** | セッション管理のユーザー化 | KAPI 追加なし | v86_session.c の Auto-Typer・終了処理を `programs/v86d/` へ |
| **Phase 5** | 旧 `sys_v86_boot_image*` の deprecation 周知と削除 | 旧 API 削除 (`KAPI_VERSION` 大幅更新) | 全プログラムの新 API 移行完了後 |

**各 Phase の前提**: 「既存テスト (FreeDOS 起動・MS-DOS ブート確認) が通る」状態を維持する。失敗した場合は前 Phase に戻ってリグレッションを潰す。

- 旧 API (`sys_v86_boot_image` 等) は `KernelAPI` 構造体末尾にそのまま残し、バイナリ互換を維持

- Phase 5 の旧 API 削除時はメジャー更新扱いとし、リリースノートで明示する

## § 8. 既知のリスクと留意点

### 8.1 ユーザーへのイベント通知遅延

ユーザー化後もタイマ IRQ・キーボード IRQ はカーネル経由で配送される。`sys_v86_run` のブロッキング中に発生した割り込みは内部で処理されるが、ユーザーへのイベント通知は次回の `sys_v86_run` 復帰時まで保留される。シビアなタイミングを要求する DOS ゲームでは再検討が必要。

### 8.2 Auto-Typer のリアルタイム性

現状 v86_session.c の Auto-Typer は v86 内部から見たキーボードバッファに即座にスキャンコードを差し込む。ユーザー化後は KAPI 経由でメモリ書き込みするため、書き込みタイミングが 1 イベントぶん遅延する可能性がある。Phase 4 着手前に Phase 2 / 3 で計測しておく。

### 8.3 §BUG-CTX が解決されない場合のリスク

ユーザー化しても、KAPI ブリッジ自体のスタック領域 (Ring0 側) が壊れる症状が残れば、根本問題は解消しない。Phase 1 で原因を特定してから Phase 2 を着手することを推奨する。

### 8.4 既存テストカバレッジの限界

v86 のテストは現状「FreeDOS ブート可」「Ys I タイトル表示」程度の手動検証が主であり、自動化されていない。Phase 2 以降のリグレッションを検出するためには、シェル経由で起動できる V86 スモークテストを Phase 2 着手前に整備するのが望ましい。
