## 2. B8 — 読み取り失敗を「不存在」として扱う処理が**複数段**にある

> **2026-09-15 更新**: Codex の追調査 (`faa14df` 時点、ユーザー経由) で、当初の記述より
> **深く、かつ B8 より重い被害を伴う経路**があると分かった。**PM がコードで全件を確認済み。**
> 当初案の「`ext2_lookup` の畳み込みをやめる」だけでは**閉じない**。

### 2-1. 現象の連鎖 (B8 本体)

1. 親ディレクトリの読み取りが**一度**失敗する。
2. `ext2_find_entry()` は I/O エラーを返すが、**呼び手の `ext2_lookup()` が `NOTFOUND` に置き換える** (`fs/ext2_dir.c:553`)。
3. `ext2_vfs_stat()` でもパス解決の失敗を一律 `NOTFOUND` にする (`fs/ext2_vfs.c:261`)。
4. `vfs_open_internal()` は `NOTFOUND` なら続行する (H1/H3 の B7 修正で `O_CREAT` 経路のため意図的に残した)。
   次のサイズ取得が成功すると、**型の再確認なしで FD を返す** (`fs/vfs_fd.c:87`)。

結果: 実在する `/etc` に対し `cat /etc` がディレクトリの生データを読む。

### 2-2. 修正を閉じるために必要な追加の 3 箇所

| # | 箇所 | 問題 | 重さ |
|---|---|---|---|
| a | **`ext2_bmap()`** `fs/ext2_inode.c:232` | 間接ブロックの読み取り失敗を **`0` に変換**する (`if (ret != 0) return 0;`)。`0` は「ブロック未割当」と同じ値なので、`ext2_find_entry()` はそれを**検索終了**と読んで `NOTFOUND` にする。**`ext2_lookup` だけ直してもこの経路が残る。**ブロック未割当と I/O エラーの区別が要る | B8 と同じ |
| b | **open の `O_CREAT` 分岐** `fs/vfs_fd.c:109` | サイズ取得の**あらゆる失敗**で空ファイルの書き込みへ進む。「通常ファイルと確認済み → サイズ取得だけ一度 I/O 失敗 → 書き込み成功」で、**`O_TRUNC` が無くても既存ファイルを空にする**。作成へ進めるエラーを `NOTFOUND` に限定すべき | **最も重い。無言のデータ消失** |
| c | **`O_TRUNC` の戻り値** `fs/vfs_fd.c:121` | `write_file()` の失敗を**無視**し、サイズ 0 の FD を返す。ext2 の一括書き込みにはディレクトリ拒否 (`fs/ext2_file.c:175`) があるのに、**そのエラーもここで失われる** | 中 |

**b は B8 本体より重い。** `O_CREAT` を付けて `O_TRUNC` を付けない開き方 (「無ければ作る、あれば開く」)
は最も普通の書き込み用途であり、そこで**既存の中身が黙って消える**。

### 2-3. 修正順 (この順でやる)

1. **下位からエラーを保持する** — `ext2_bmap()` が I/O エラーを未割当と区別して返し、
   `ext2_find_entry()` / `ext2_lookup()` / `ext2_vfs_stat()` がそれを畳まず伝える。
2. **open が不存在以外で作成しない** — `O_CREAT` の分岐に進むのは `NOTFOUND` のときだけ。
   `O_TRUNC` は `write_file()` の戻り値を見て失敗を返す。
3. **サイズ取得がディレクトリを拒否する** — `ext2_get_size_ino()` (`fs/ext2_file.c:305`) と
   `hdrv_get_file_size()` (`fs/hostdrvfs.c:600`)。

### 2-4. 影響範囲の注意

- **`ext2_resolve_path()` の呼び出しは 14 か所** (すべて `fs/ext2_vfs.c`)。エラーの畳み方を変えると
  全部に波及する。`unlink` / `rename` / `mkdir` / `rmdir` / `stat` / `read` / `write` が含まれる。
- **H3 で足した mtime 更新も、一律 `NOTFOUND` の処理をそのまま引き継いでいる** (`ext2_vfs_set_mtime`)。
- これは **H1 以前からある欠陥**で、H1/H3 が持ち込んだものではない (PM 確認済み)。
  ただし開発ポリシー §1 (カーネル層の不具合は新機能より優先) の対象である。

### 2-5. 検証の要求

**実物の `vfs_open` / `vfs_open_sqlite` を通すこと。** `vfs_path_kind` の戻り値だけを見る試験では
往復 4 の B7 を取り逃した前例がある。

- **一度だけの I/O 失敗**を注入し、**FD が発行されない・`write_file` が呼ばれない・既存内容が残る**
  ところまで確認する。
- **間接ブロックを使う大きなディレクトリ**を対象に含める (2-2a の経路)。
- `O_CREAT` あり / なし、`O_TRUNC` あり / なし の 4 通り。
- 正常系の回帰: 本当に不存在なら `O_CREAT` で作れる、`O_TRUNC` は切り詰められる、
  通常ファイルは開ける、ディレクトリは `ISDIR`。

## 2-6. B8 往復 3 で判明した、範囲外の未解消 (2026-09-15)

- **`rename` の原子性** — `rename` 内の `add_entry` の書き込みが**部分的に**媒体へ届くと、
  リンク数 1 の inode を 2 つの名前が参照し得る。後で片方を `unlink` すると、残った名前が
  解放済み inode を指す (dangling)。これは解放処理ではなく**rename の原子性**の問題で、
  B8 (エラーの畳み込み) とは別系統。コーダーが失敗注入の網羅中に指摘した。**未確認・未着手。**
- **漏れ** — B8 往復 3 は解放の順序を「媒体上の参照を先に消し、解放は後」に変えたので、
  途中の I/O 失敗は交差リンクではなく**漏れ** (使用中だが未参照のブロック) になる。
  OS32 にはゲスト内の fsck が無いので、I/O 失敗が繰り返されると空き容量が減り得る。
  ホスト側の `e2fsck` で回収できる。**意図した交換であり、破壊ではない。**
- **二重故障** — 失敗注入の網羅は「N 番目の I/O を 1 回だけ」「N 番目以降を全部」の 2 形式。
  独立した 2 箇所の失敗の組み合わせは網羅しておらず、専用試験は 1 件だけ。

## 3. 併せて残っている小さいもの

- **`fs_is_dir` は「不明」を運べない**。stat と列挙の**両方**が失敗すると偽を返し、
  `cp -r` が誤った枝へ進む。H1 以前からの欠陥。解消には `cp`/`mv` が
  `fs_path_kind()` の負値を見て断る必要があり、呼び出し元の変更になる
  (`userland/shell/cmd_file.c` の 5 箇所)。
- **NP21/W の `hostdrvNT_getHostPath`** (`/home/hight/np21w-src/src/generic/hostdrvnt.c:368-390`) の
  ルート検査が区切り境界を見ない前方一致なので、`C:\os32` をルートにすると
  `C:\os32-other` 以下が通る。**別リポジトリ**なのでビルドと配備が要る。
  OS32 側は `\` を含む要素の拒否で緩和済み (H1 の B1) だが、これは修正ではない。

## 4. 受入の考え方
