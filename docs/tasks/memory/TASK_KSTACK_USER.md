# TASK_KSTACK_USER — カーネルスタックとその手前が CPL=3 から書ける

> 発行: PM (Claude Code `claude-opus-5`、2026-09-17) / 状態: **計画 (2026-09-17)**

基点: `feat/gui` = `6c9d049`。
発見: テストランナー段 3 の下調べ中 (`crash` が落ちないことから辿った)。
**カーネル層なので [`POLICY_DEV.md`](../../POLICY_DEV.md) §1 により最優先。**

## 0. 何が起きるか

**CPL=3 の普通のアプリが、カーネル帯域の `0x1F0000`〜`0x1FFFFF` を読み書きできる。**
ここには**カーネルスタック本体** (`0x1FC000`〜`0x1FFFFF`、16KB) が入っている。

`userland/tests/crash.c` は `0x1FB000` (カーネルスタックガード) へ書いて
**落ちるはず**の試験だが、2026-09-17 の実測で**落ちずに素通りした**。

    Crash test: writing to guard page (0x1FB000)...
    ERROR: should not reach here!          ← ここに来てはいけない

`fault_kill_count` は前後とも **0**。書いた値はそのまま残っている
(`/api/mem addr=0x1FB000` が `adde0000` = `0xDEAD`)。
`crash.bin` の OS32X ヘッダの flags は **0** なので `--cpl0` ではなく、
**CPL=3 で走っている**。

## 1. ページテーブルの実測 (2026-09-17、CR3=`0x14A000`)

PDE 0 = `0x00141027` (page table `0x141000`、P/RW/**US=1**)。
PDE 0 は master PD とアプリ PD で**共有**されている
(`kernel/paging.c:837` の `paging_pd_clone_selftest` の注記)。つまりアプリにも同じ表が見える。

| linear | PTE | P | RW | US | あるべき姿 (`include/memmap.h` の地図) |
|---|---|---|---|---|---|
| `0x100000` | `0x00100023` | 1 | 1 | **0** | カーネル .text — 正しい |
| `0x110000` | `0x00110023` | 1 | 1 | **0** | カーネル — 正しい |
| `0x13E000` | `0x0013E063` | 1 | 1 | **0** | カーネル .data — 正しい |
| `0x150000` | `0x00150063` | 1 | 1 | **0** | カーネルヒープ — 正しい |
| `0x1F0000` | `0x001F0007` | 1 | 1 | **1** | **空き/予約 (NP のはず)** |
| `0x1FB000` | `0x001FB067` | 1 | 1 | **1** | **スタックガード (NOT PRESENT のはず)** |
| `0x1FC000` | `0x001FC007` | 1 | 1 | **1** | **カーネルスタック (US=0 のはず)** |
| `0x200000` | `0x00200023` | 1 | 1 | **0** | SQLite — 正しい |

`0x1FB000` の PTE は Dirty (`0x40`) が立っている = **実際に書かれた証拠**。

## 2. 何が壊れているか (2 つ別々)

1. **`paging_set_not_present()` が効いていない。** `kernel/paging.c:197` が
   `MEM_STACK_GUARD`〜`MEM_STACK_GUARD_END` を、`:200` が
   `MEM_SHM_RESV_START`〜`MEM_SHM_RESV_END` を NP にするはずだが、
   どちらの範囲も **P=1 のまま**。
2. **カーネルスタックに US=1 が付いている。** `kernel/paging.c:191` の
   `paging_map_range(MEM_KSTACK_BASE, …, PAGE_RW)` は `PTE_USER` を渡していないのに
   US が立っている。**`paging_map_range` がフラグを「置き換え」ではなく
   「足し込み」しているのではないか** — SHM 用に US を立てた前の写像が残り、
   後から `PAGE_RW` だけで写し直しても US が落ちない、という筋 (**仮説**。要確認)。

この 2 つは独立に直せる。1 だけ直してもスタック本体の US=1 は残る。

## 3. なぜ重いか

- **アプリがカーネルスタックを壊せる。** 戻り番地を書き換えれば任意のカーネルコードへ
  飛ばせる。CPL=3 の分離が意味を持たなくなる。
- **カーネルスタックの溢れが検出されない。** ガードが NP でないので、溢れても
  フォルトせず**静かに手前の領域を潰す**。`0x1FAFFF` 以下は「空き/予約」なので
  症状が出るまで時間がかかり、原因追跡が極めて難しくなる。
- **`crash` はこの穴のせいで 2026-09-17 時点で試験として機能していない。**
  `void main` なので終了コードも出ず、誰も気づかなかった
  (票 [`../test/TASK_TEST_RESULT.md`](../test/TASK_TEST_RESULT.md) の第 2 陣で扱う予定だった)。

## 4. 調べること (実装の前に)

1. **いつから壊れているか。** `paging_set_not_present` と `paging_map_range` の
   実装と履歴を見る。メモリ改修 (2026-09-09 前後) が疑わしいが**未確認**。
2. **同じ理由で US=1 になっている範囲が他にもないか。** PDE 0 の 1024 本の PTE を
   全部読んで、`memmap.h` の地図と突き合わせる。**穴は 1 つとは限らない**。
   シェル帯 (`0x300000`〜) と PDE 1 以降も見る。
3. `paging_map_range` が「置き換え」か「足し込み」か。仮説の裏を取る。

## 5. 受入

| ID | 反例・操作 | 期待 |
|---|---|---|
| G1 | ゲストで `crash` | **落ちる**。`fault_kill_count` が +1、`$?` = 139。今は素通り |

| G5 | ホスト試験 | `paging_map_range` / `paging_set_not_present` の**フラグの置き換え規則**を固定する。足し込みに戻す変異で RED |

G2 と G3 が本体。**1 か所直して終わりにしない** — 地図と実物を機械で突き合わせ、
以後ずれたら起動時に分かるようにする。
