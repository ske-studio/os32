# OS32 v2 カーネルアーキテクチャ計画

> 策定: 2026-09-01 / 対象起点: v1.1.0 (`4740bea`)
> 位置づけ: v2 で扱う**カーネルの構造変更**の計画。GUI の設計は含まない
> (後述 §7 のとおり別トラック)。判断の根拠は
> [リング3か、Rustか](https://claude.ai/code/artifact/5b8de11b-83a8-4708-a466-541c633725e3)
> の分析と、本書 §3 の実測に基づく。

---

## 1. スコープ

このトラックが扱うのは OS32 の identity を保ったままの**保護機構の導入**である。

**扱う (in scope)**

- リング 3 導入 (CPL=3 のユーザプログラム + CPL=0 のカーネル)
- KAPI をゲート経由の呼び出しに変える (トランポリン方式)
- `get_tick` ビジーポーリングの根絶 (リング 3 の前提条件)
- 複数プログラムの同時ロード方式の決定 (未決 — §6)
- Rust の適用範囲の確定 (新規ユーザランド層のみ)

**扱わない (out of scope)**

- GUI シェル・`libos32gui`・ウィンドウマネージャの設計 → v1.x トラック (`docs/ROADMAP.md`)
- マルチタスク (スケジューラ・プリエンプション) → identity から外れる。§7 参照
- カーネル本体 23K 行の Rust 書き換え → 回収できない。§5 参照

## 2. 確定した決定 (2026-09-01)

| # | 決定 | 根拠 |
|---|------|------|
| D1 | **リング 3 を導入する** | [ABI4] (KAPI ポインタ非検証) を消せる唯一の道。土台 (TSS・CPL=3 遷移・PTE_USER) は V86 用に既にある |
| D2 | **identity は「DOS の 32bit ネイティブ版・シングルタスク」** | DOS エクステンダ (DOS/4GW 等) と同じ位置。`fork`/`pipe`/busybox は方向が逆 |
| D3 | **Rust は新規ユーザランド層に限定** | カーネルに来る新規コードが少なく、23K 行の書き換えは回収できない。GUI 層 (新規・大量・状態管理) が Rust の効く場所 |
| D4 | **apps / game はモノレポから分離済み** | `ske-studio/os32-apps` (20 commit) / `os32-game` (12 commit)。本体はカーネル + SDK に純化 (`4740bea`) |
| D5 | **V86 第1実装 (vdm-v1) は破棄** | vdm-v2 が MS-DOS 5.00A 起動を実機確認済み。第1実装は不要と判断し削除 |

## 3. 実測: KAPI 呼び出し頻度

リング 3 では KAPI 呼び出しが INT ゲート遷移 (386 で ~6μs) になる。実プログラムの
呼び出し頻度が成立条件になるため、計測カーネル (`-DKAPI_PROFILE`) で実測した。

| 状態 | KAPI 呼び出し | うち `get_tick` | `get_tick` 除く | 6μs 換算 CPU |
|------|--------------|----------------|----------------|-------------|
| アイドル (rshell 待ち) | 311,703 /s | 100 % | 100 /s | **187 %** |
| demo1 実行中 | 5,726 /s | 95.9 % | 233 /s | 3.4 % (全体) / **0.1 %** (除く) |

計測手法: `kapi/kapi_profile.h` の `KAPI_HIT(slot)` が計測ビルドでのみ slot 別
カウンタを増やす。`kapi_hits[]` を `/api/mem` で読み、`tick_count` の差分で
calls/sec を出す (`tools/` 相当のスクリプトはセッション外)。

### 3.1 結論

- **`get_tick` を除けば KAPI レートは無視できる** (0.1 % CPU)。v22 で描画
  プリミティブを KAPI から外し、フレームバッファ直接操作に移した効果。
  **ホットパスは既に KAPI 境界を越えていない。**
- **`get_tick` のビジーポーリングが唯一かつ致命的な障害。** 残したまま
  リング 3 に進むとアイドルだけで CPU が振り切れる (187 %)。
- したがって **M0 (get_tick 根絶) がリング 3 の絶対的な前提条件**になる。

## 4. マイルストーン

順序に依存関係がある。M0 を飛ばして M1 以降に進むと即破綻する。

### M0 — `get_tick` スピンの根絶 (最優先)

「時間待ちのスピン」を `sys_halt()` ベースに置き換える。PIT は 100Hz なので
`hlt` は最大 10ms で必ず起きる。時刻取得としての `get_tick` (ベンチの差分計測等)
はそのまま残す。

棚卸し (v1.1.0 時点):

| 箇所 | 内容 | 対応 |
|------|------|------|
| `userland/shell/rshell.c` (3 箇所) | `w=get_tick()+1; while(get_tick()<w);` — **アイドル 311k/s の主因** | `sys_halt()` に置換 |
| `userland/cmds/sleep.c` | sleep コマンドの待ち | 同上 |
| `userland/system/sndtest.c` | 音長の待ち | 同上 |
| `tests/blit_test2` `rotate_test` `gfx_demo200` | fps 計測の frame 待ち | デモ。優先度低 |
| `tests/bench*` `mgx_test` `blit_test` | 経過時間の**計測** (待ちではない) | 触らない |

検証: 計測カーネルで「アイドルが 311k/s → 数十/s」に落ちることを確認する。
M0 は v1 にも効く (今アイドルでホスト CPU を無駄に食っている)。

### M1 — リング 3 の土台

- GDT に DPL=3 の code/data を 2 本追加 (`0xFA` / `0xF2`)。`GDT_ENTRIES` 4 → 6
- `exec` がロードするプログラムページに `PTE_USER` を立てる
  (`paging_set_page` は対応済み)
- ユーザスタックを CPL=3 用に用意。カーネルスタックは TSS.ESP0 で復帰

### M2 — KAPI トランポリン

KAPI 表の形 (172 エントリの関数ポインタ) を保ったまま、各エントリを
**ユーザ空間のスタブ**に向ける。スタブが `int 0x80` でカーネルに入る。

- プログラム側のソースは無変更 (`api->kprintf(...)` のまま)
- 制約 [ABI2] 「末尾追加のみ」も維持
- 関数番号を EAX に載せる全面 syscall 化より ABI の断絶が小さい

### M3 — 検証

- 不正ポインタを KAPI に渡し、**カーネルが死なずページフォールトで止まる**
  ことを `kselftest` に追加 (現在この種のテストが無い)
- 6μs ゲートの実測 CPU が M0 後に無視できる水準であることを再計測

## 5. Rust の適用範囲

規模 (v1.1.0 実測): 自作カーネル C 23,131 行 / アセンブラ 3,308 行 /
vendored C (SQLite+FatFs+zlib) 278,281 行。**書き換え可能なのは 23K 行だけで、
リンクされる C は 278K 行残る。**

| 層 | 判断 | 理由 |
|----|------|------|
| `libos32gui` (新規 GUI 層) | **Rust で新規開発** | 量が多く状態管理のバグが出やすい。`no_std` + 固定配列でカーネル非依存。`os32_lz4` (text 541B) と同じ staticlib 形式 |
| V86/VDM のゲスト境界 | Rust 化を検討 | DOS プログラムを走らせるならゲスト値は全て信頼できない入力 |
| カーネル本体 | **C のまま** | 新規コードが少なく回収できない。リング 3 が入れば保護はハードウェアが担う |
| ドライバ・ISR 周辺 | **C のまま** | ポート I/O と `irq_save` が主。`unsafe` だらけになる |
| SQLite/FatFs/zlib | C のまま | 選択の余地なし |

**リング 3 と Rust は補完関係。** リング 3 が守るのは「プログラム→カーネル」、
Rust が守るのは「カーネル内部のバグ」。ただしカーネル新規コードが少ないため、
Rust の主戦場はカーネルではなく新規ユーザランド層になる。

## 6. 未決定事項

### 複数プログラムの同時ロード方式

現在 OS32X は `0x400000` 固定リンクの平坦バイナリで、`exec` はプロセスを置換する。
GUI で複数ウィンドウ (= 複数アプリ) を同時に持つには、この前提を変える必要がある。

| 方式 | 内容 | 帰結 |
|------|------|------|
| 再配置可能バイナリ | OS32X に再配置情報を持たせ別番地へロード | フォーマット変更、リンカスクリプト改修 |
| PD 切替 | 各アプリは `0x400000` に居ると思い込み、切替時に CR3 を差し替える | リング 3 と自然に組む。物理ページ管理が要る |

**この 1 点がリング 3 の設計・メモリマップ・ローダの全部に波及する。** M1 着手前に
仮決めが要る。協調型マルチタスクを `gshell` (ユーザランド) の責務にする場合でも、
複数アプリのメモリ配置はカーネルの問題として残る。

## 7. GUI トラックとの関係

**GUI の設計はこのトラックに含まれない。** Win3.1 風デスクトップ、`gshell`、
`libos32gui`、ウィジェットは `docs/ROADMAP.md` の v1.x トラックにあり、
その 9 割以上はユーザランドである。カーネル側の GUI 作業は
`/etc/system.cfg` 解析・テキスト GDC 制御・CUI 出力の GUI リダイレクトの 3 つだけ。

両トラックは独立だが、3 点で交差する。

1. **KAPI 呼び出し方式** — リング 3 化は GUI アプリの KAPI 呼び出しにも及ぶ。
   M2 のトランポリンが GUI アプリにもそのまま効く (ソース無変更)。
2. **複数アプリの同時ロード (§6)** — GUI マルチウィンドウの要求そのもの。
   GUI 側の要件がこの未決事項の決め手になる。
3. **`get_tick` 根絶 (M0)** — GUI のイベントループも同じスピンに陥りやすい。
   M0 で確立するアイドル作法 (`sys_halt` ベース) を GUI ループの基準にする。

GUI の識別: v1.x の GUI は「シングルタスク GUI デスクトップ」であり、
Windows 3.1 が「シングルタスクの DOS 上で GUI シェルが協調マルチタスクを
実装する」構造だったのと同じ。協調マルチタスクを入れる場合も `gshell` の責務とし、
カーネルは DOS のまま保つ (D2)。

## 8. リスクと後戻り

| リスク | 影響 | 緩和 |
|--------|------|------|
| `get_tick` を残したままリング 3 | アイドル 187 % で常時振り切れ | M0 を絶対的前提とする (§4) |
| KAPI 呼び出しに毎秒数万回のプログラム | トランポリンが成立しない | 実測で 233/s (get_tick 除く) と確認済み。新規プログラムも同水準に保つ |
| V86 とリング 3 の TSS.ESP0 競合 | DOS 起動経路が壊れる | M3 で共存を検証。vdm-v2 は動作実績あり |
| 複数アプリ方式の選択ミス | メモリマップ全体の作り直し | §6 を M1 前に仮決め、実装前に検証 |
