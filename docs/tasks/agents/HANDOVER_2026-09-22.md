## 決裁 (ユーザー、2026-09-22)

- LAN は v3 の順序 (動的読み込みが先) を待たず、PCI 列挙 → 82557 を静的で入れる (足りなければ SHM を 16KB 削る)。
- 実機のホストは **Ubuntu ノート** (スイッチ直結)。橋は AF_PACKET。この Windows/WSL 機は手で操作する場面だけ。
- シリアルの保険 (番犬) は往復を重ねて直す (Codex 4 往復で打ち止め、最後は設計変更で閉じた)。

## カーネル予算の切り直し (2026-09-23、ユーザー指示「順に実行」)

- **1. KHEAP 320KB → 192KB**: 実測は FD 起動 + kout_test 後で `kmalloc_peak_bytes` = 65,552 (64KB の一時確保が起動時に 1 回)。
  予算 468KB → **596KB (残り 134KB)**。写し: `build/os32.ld` の `MEM_KERNEL_IMAGE_MAX = 0x95000`、`tools/tests/test_memmap_{gen,boot}.py` の
  予算定数、起動行の HEAP 表示は定数から。`make check` 通過 (aa536e9 以降)。GUI/NHD 環境での peak は次に NHD で起動したときに読む (kernel.map の `kmalloc_peak_bytes`)。
- **2. 静的なページ表 (`paging.c` の pd_raw 8KB + pt_raw 36KB + page_tables 4KB = 48KB) を画像の外へ**: 置き場は SQLite 帯の予約域の残り
  (0x2DD000〜0x2E7FFF、44KB、うち 36KB が要る) しか無く、SQLite の伸び代が 8KB になるので**単独ではやらず 4 に含める**。
- 3 (動的読み込み) は v3 §3 のとおり。**4 (メモリマップの見直し)** は v3 の票として起こす: カーネル帯 2MB (SQLite を上へ)、ページ表と DMA プールの固定配置、
  KHEAP/SHM の再配分、PCM ステージングをプール外へ。
- Codex 往復 1 (TASK_MEMMAP_V3) で 9 件: 2-2 (カーネル帯 2MB) はシェルの PDE 1 写像・pgalloc の配布域・予算式・ビルド経路 5 つ・NHD 移行・アプリ帯の PDE・ローダ 508KiB を先に決める大きい票 → **保留** (134KB で PCM と 82557 は入る)。2-3 の小さい整理 (地図の文言、ページ表の整列 8KB、PCM ステージングを KHEAP へ) は着地。`fat12.o` は未リンクの残骸 (FAT は FatFs だけ)。

## 次の実機の回でやること (順に)

1. FD (最新ビルド) で起動、9600 で `ver` → `--fast 115200` (ack の往復と、失敗時の 9600 復帰)。

3. その値で L-B (82557 最小ドライバ) を書く。
