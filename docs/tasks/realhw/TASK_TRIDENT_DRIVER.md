## 1. 何を解決するのか — 今の症状と照らして

### 1-1. 今の実機の画面 (2026-09-25〜26 の記録)

| 経路 | 実機 Ra266 + 液晶での状態 | 出典 |
|---|---|---|
| `gfxmode pc98` (640x400x16、GDC 24kHz 系) | **正しく映る** | TASK_PEGC480 §0 |
| `gfxmode pegc` (640x480x256、GDC を 31kHz / 480 ラインへ切り替え) | **桁ずれ** (液晶が正しい位置で取り込めない) | TASK_PEGC480 §0 |
| CUI (起動時の PEGC 準備が同期を触っていた頃) | 桁ずれ → `pegc_prepare` で同期を触らないようにして消えた | TASK_FDC_REALHW §9-1、`include/gfx_hal.h` の `prepare` 注記 |

**PITCH=80・GDC クロック 5MHz** にするのに `pegc_init` はどちらも設定していない (H5 の裏付け、TASK_PEGC480 §3)。
**実機の ROM の値はまだ採っていない** (`v86 -g` は実装済み・実機未実施)。

### 1-2. Trident で解決するもの・しないもの

| 観点 | PEGC (今) | Trident で見込めること | 確度 / 根拠 |
|---|---|---|---|
| **桁ずれの回避** | uPD7220 の SYNC・PITCH・GDC クロックを OS32 が直に書く。値は NP21/W 由来で、実機の ROM と一致するか未確認 | 映像の同期は Trident の CRTC と画素クロック生成器が作る。**GDC を 480 ラインへ切り替えない** (98 側は 400 ラインの CUI のまま置いておける) | **中**。同期の値は結局 OS32 が書く (VGA 互換 CRTC + 拡張レジスタ + クロック生成器) ので「値が正しければ直る」のは PEGC と同じ。違いは、VGA 系の標準タイミングは液晶側が前提にしている形式だという点 (一般論、docs/hw に記述なし)。ただし**レジスタ資料が手元に無い** (§3) |
| **液晶の水平/垂直周波数** | 31kHz / 480 ライン。液晶の OSD で実値を見る段 0 (TASK_PEGC480) は未実施 | 640x480@60 なら VGA 標準の約 31.5kHz / 約 60Hz、800x600@60 なら約 37.9kHz / 60Hz、1024x768@60 なら約 48.4kHz / 60Hz (一般値、docs/hw に記述なし。VESA DMT は未入手) | 液晶の対応範囲はユーザーの機種次第 (**型番・対応周波数の記録なし**) |

| **色数** | 256 色 (PACKED8) | 8bpp のまま (推奨)。16bpp は可能性があるが GUI・libos32gfx 全体に波及 (§4-3) | チップの対応色深度は資料に記述なし |
| **描画速度** | CPU が主記憶の BB (300KB) → F00000h の窓へ転送 | (a) 表示面とクライアント面をカード VRAM に置き、**present をエンジン BLT** にする (Cirrus と同じ形)、(b) エンジンの塗り / 転送 (HW_FILL / HW_BLT)。**どちらも条件付き** — 用途・安全なアクセス範囲・容量が確認できるまで前提にしない (§4-2) | エンジンのレジスタは資料に記述なし。PEGC 窓と Trident の LFB のどちらが速いかは**実測していない** (Ra266 の PEGC も PCI の 1033:0009 の先にある — io_pci.md 表 2 の「98ｸﾞﾗﾌｨｯｸｽ」、実測 lspci) |
| **テキスト面の合成** | 合成あり (TEXT_OVERLAY) | **無くなる見込み** — 映像出力を 98 側から切り替えるので、テキスト VRAM は映らない (Cirrus と同じ、DESIGN §1 R4) | 切り替えの手段が資料に無い (§2-4)。**戻す経路が要る** (§3-5) |
| **PEGC の 15MB 穴 (F00000h〜)** | 043Bh bit2=1 (16MB 以上を RAM) の構成では PEGC 窓が使えない | Trident の BAR は 0x2000_0000 帯 (実測) で RAM の穴を要らない | 実測 (lspci) |

**要するに**: Trident は「GDC の 480 ライン切り替えを使わずに済む」ことで桁ずれを**回避しうる**経路であり、解像度と
描画の上積み (エンジン BLT) を伴いうる。ただし**レジスタ資料が無い**ので、確度は資料の入手 (§3) で決まる。
PEGC の直し (TASK_PEGC480 段 1〜2) の方がはるかに安く、両方を残す意味がある (§7 決裁 T1)。

## 2. Trident が Ra266 にどう見えるか

### 2-1. 実測 (2026-09-23 `lspci` TASK_LAN_82557 §6 → **2026-09-29 17:32 段 0 の採取**、PCI config の読み取りのみ)

段 0 の採取 (実機 Ra266、実機エージェント、カーネル Commit 135b6b5 / API v68。`lspci -v` は BAR の大きさ測定の書き込みをしない — `cmd_pci.c` で確認。
09-23 / 09-25 の `pcidump` と差なし。記録は §9-3):

```
0:8.0 1023:9660 Trident  revision d3  class 03.00.00 (VGA)  command 0002 (I/O- Mem+ BusMaster-)  status 0280
      subsystem 0000:0000  BAR0 0x20000000 / BAR1 0x20400000 / BAR2 0x20800000 (mem32, prefetch なし)
      Expansion ROM BAR (0x30) = 0x21000000 (bit0 = 0 で無効)  interrupt line 0xff  pin A  cache line 0  latency 0
      pcidump: 00: 23 10 60 96 02 00 80 02 d3 00 00 03 00 00 00 00 / 10: 00 00 00 20 00 00 40 20 00 00 80 20 00 00 00 00
               30: 00 00 00 21 00 00 00 00 00 00 00 00 ff 01 00 00 / 40-f0: all 00
0:7.0 1033:0009 NEC (98 グラフィックス)  revision 03  class 03.80.00  command 0003 (I/O+ Mem+)  status 0280
      subsystem 0000:0000  ROM BAR 0  BAR all 0  0x44 = 01 (意味は資料に記述なし)

    / 0:12.0 1103:0004 (io 0x6020.., irq 6) / 0:13.0 1131:7164 (bar0 mem64 0x20c00000, irq 10)
```

**事実** (config の値そのもの):

- **BAR は 3 本とも memory (32 ビット、prefetch なし)**。I/O BAR は無い。大きさは測っていない (`drivers/pci.c` は BAR に書かない方針)。
- **Command = 0002: I/O Space Enable = 0、Memory Space Enable = 1、Bus Master = 0** (起動時点、OS32 は Command に書いていない)。
  0:7.0 (98 グラフィックス) は 0003 で I/O も Mem も有効。
- Revision d3、class 03.00.00 (PCI class code の「VGA 互換コントローラ」— 一般、docs/hw に記述なし)、**subsystem 0000:0000 (9680 / 9682 の判別材料にならない)**。
  revision d3 がどちらのチップに当たるかは**資料に記述なし**。
- **Expansion ROM BAR = 0x21000000、enable bit = 0** (ROM の decode は無効。アドレスだけ割り当て)。ROM の有無・中身は読めていない (読むには enable への書き込みが要る = 段 1 の範囲外)。
- IRQ line 0xff (未割当)、pin A。割り込みを使わない作り (VSYNC はポーリング) なので**拒否の理由にはしない** (§4-1)。

**推定** (事実から導いた上限で、確認ではない):

- **隣の割り当てからの推定は「BAR の decode 幅の上限」でしかない**: bar1 は 82557 の bar0 (0x20410000) の手前なので **64KB 以下**、
  bar0 は 0x20400000 の手前なので **4MB 以下**、bar2 は 0:13.0 の bar0 (0x20C00000) の手前なので **4MB 以下** (v1 では推定不能としていた。段 0 で 0:13.0 が分かった)。
  **3 つを区別する**: (i) BAR aperture (decode 幅)、(ii) 実 VRAM 容量、(iii) 連続してアクセスできる範囲 (aperture の中で実際に VRAM が応える範囲)。
  (i) の上限は (ii)(iii) の下限を何も言わない。「表示面 + クライアント面の二面が入る」は (ii)(iii) が実機で確認できるまで**前提にしない**。
- Bus Master = 0 は 2D エンジンの可否を何も言わない (エンジンが VRAM 内で完結するか、バスマスタが要るかは**資料に記述なし**)。
- ROM の decode が無効なことは「起動時に VGA BIOS が走ったか」を**どちらにも決めない** (走ってから閉じたのか、初めから走っていないのかは分からない)。

**I/O デコード無効 (Command bit0 = 0) が §2-3・D1 に効くこと**:

- 事実: PCI の Command bit0 が 0 のあいだ、**この PCI ファンクションは I/O 空間のアクセスに応答しない** (PCI 規格の Command レジスタの意味 — 一般、docs/hw に記述なし)。
  I/O BAR も無いので、この関数の I/O 経路があるとすれば **VGA 互換の固定番地 (3Bxh/3Cxh/3Dxh) の legacy decode** だけで、それも今は閉じている。
- 推定: したがって**起動時点では経路 (A) (3C0h 系のまま) は PCI ファンクションを通しては届かない**。届かせるには **Command bit0 への書き込み**が要り、
  それは (1) 段 1 の許可リスト (読み取りだけ) の**範囲外**、(2) **装置の状態変更** (§3-5 R4 の「最初の装置変更」に当たる = 復帰フック有効化の後、段 2 以降)、
  (3) 有効にした瞬間に 3Cxh の legacy decode が **§2-3 の部分デコード (640KB FDD・GP-IB) と同居する**ことになり、その配送と衝突は**資料に記述なし**。
- 推定: 経路 (B) (NEC 流の写し替え) が「PCI ファンクションの I/O decode」で実現されているなら (A) と同じく閉じている。**ボード側の論理** (Cirrus 機の 0FAAh/0FABh のような
  PCI ファンクションの外の制御ポート) で実現されているなら Command に関係なく届きうるが、Trident 機にそのような論理があるかは**資料に記述なし** (§2-2)。
- 事実: **Memory Space Enable = 1** なので BAR の窓 (経路 (C) MMIO) は起動時点で decode されている。**段 1 で書かずに読める経路は (C) だけ** — ただし
  「Trident の VGA レジスタが MMIO に出ているか」「どのオフセットか」「読み取りの副作用」は**チップ資料が無いので分からず**、許可リストに入れられない (§3-4-1)。
  → **チップ資料が無い限り、段 1 の読み取りは 0 件**である (段 0 で得た事実で変わらない)。
- 0:7.0 が I/O+ なのは 98 グラフィックス側の話で、Trident の経路を何も言わない。0x44 = 01 の意味は資料に記述なし。

### 2-3. VGA 互換ポートの置き場所 — **資料に記述なし、しかも衝突の恐れがある**

Trident の VGA 互換レジスタ (3C0h〜3DFh) が PC-98 の I/O 空間のどこに出ているか、**資料に記述なし**。
PC/AT の番号 (3C0h 系) のまま出ているなら、Bible §4-3 の I/O マップの**部分デコード**に当たる:

| VGA のポート | 下位バイト | Bible 4-3 で同じ下位バイトを拾う装置 (上位バイトは X = 見ない) |
|---|---|---|
| 3C8h・3CAh・3CCh・3CEh (DAC 書き index・Feature 読み・Misc 読み・GC index) | C8h〜CEh の偶数 | **640KB FDD コントローラ 765 相当** (表の 26) |
| 3C1h〜3CFh の奇数 (Attr 読み・Seq data・DAC data・GC data ほか) | C1h〜CFh の奇数 | **GP-IB 7210 相当** (表の 27) |
| (Trident のクロック設定 43C8h/43C9h — PCem 由来のソースの番号) | C8h・C9h | 同上 |

- PCI ホストブリッヂがこれらを PCI 側で先に受けるのか、C バスへ流すのかは**資料に記述なし**。Bible の部分デコードは「衝突を警戒する根拠」であって、
  **Ra266 で実際にどこへ配送され何と衝突するかは資料に記述なし**。
- NP21/W の PCI 型 Cirrus は「PCI 版はポート番号そのまま」(3C0h 系、`cirrus_vga.c` の `vga_convert_ioport`) だが、
  これは**エミュレータの作りであって実機の仕様ではない**。→ **段 0〜1 では 3Cxh 帯に I/O を出さない** (FDC を叩く恐れ)。
- 候補は (A) 3C0h 系のまま、(B) NEC 流の写し替え (Cirrus の 0CA0h 系と同様)、(C) BAR の MMIO (bar1 の 64KB 以下の窓が候補)。
  **段 0 の事実 (§2-1): 起動時点で Command の I/O Space Enable = 0** → (A) と「PCI ファンクションの I/O decode による (B)」は今は閉じていて、
  開けるには Command への書き込み (= 装置変更、段 2 以降) が要る。Memory Space Enable = 1 なので (C) の窓だけが読める状態にある。
  これは (C) が「正しい経路」だという意味ではない — MMIO にレジスタが出ているかはチップ資料待ち。
  **(A)〜(C) は PCI Command の I/O Space Enable や BAR の有無では判別できない** (I/O Enable が立っていても写し替え先は分からず、
  MMIO BAR があってもレジスタがそこに出ているとは限らない)。(B) の写し替え先・(C) の MMIO の**レジスタ対応表と読み取りの安全性**が
  資料 (§3-2) で確認できた経路だけを段 1 の許可リストに入れる。**経路が未確定なら段 1 は停止する** (推測で読まない)。

### 2-4. 98 グラフィックとの共存 (映像の切り替え)

- Ra266 のモニタ端子は 1 つで、98 グラフィック (PEGC を含む) と Trident の出力をどう切り替えるかは**資料に記述なし**
  (Xa 系なら 0FACh bit1、§2-2)。
- 9821 の BIOS / GDC は 98 グラフィック側の話で、Trident には触らない (資料の範囲)。**PC-98 の起動時に Trident が初期化されるか**
  (VGA BIOS の実行、メモリクロック・画素クロックの設定) は**資料に記述なし** — 段 1 の許可リストの読み値で分かる範囲だけ判断する。
  段 0 の Expansion ROM BAR (0x21000000、decode 無効) はこの問いを**どちらにも決めない** (§2-1)。
- CUI (テキスト VRAM) は Trident の出力中は**映らない**見込み (§1-2)。**パニック・例外・CTRL+STOP・所有者の異常終了・初期化途中の失敗で
  98 側へ戻す**経路が要る — 要件と接続点は **§3-5**。戻せなかったときの復旧はシリアルの rshell とリセット (保証範囲の外は §3-5 R5)。

### 2-5. リニアフレームバッファ

- bar0 (0x20000000、decode 幅 4MB 以下の推定) が VRAM のリニア窓かどうかは**資料に記述なし**。**段 1 では書かない** — bar0 の用途が
  未確認のまま書けば VRAM 試験ではなく「未知の装置領域への書き込み」になる。用途は資料 (§3-2) で確定し、確かめる書き込みは
  段 2 (前提 §3-5・§4-2 が揃った後) の `trident -t` で初めて行う。
- NP21/W のソース (`src/wab/tgui9680.c`、PCem の `vid_tgui9440.c` 由来) は PCI の device ID を **9440h**・BAR を **1 本** (リニア窓) で返す作りで、
  **実機の 9660h・BAR 3 本と合わない**。参照実装としても Ra266 の構成の根拠にはならない。

#### 3-4-1. 段 1 の許可リストの作り方

段 1 の「読むだけ」は無条件には成り立たない: 索引方式のレジスタ (VGA の Seq / CRTC / GC、Trident の拡張レジスタ) は
**索引の書き込み**が要り、FIFO や状態レジスタは**読むだけで副作用**がありうる。だから段 1 は「全ダンプ」ではなく、
項目ごとに次を書いた許可リストの範囲に限る。リストに無いものは読まない。

| 欄 | 内容 |
|---|---|
| アドレス・幅 | I/O ポート番号 (経路 (A)/(B)) か MMIO オフセット (経路 (C)) と、8/16/32 ビット |
| 出典 | docs/hw の節、またはチップ資料のページ。**「資料に記述なし」の項目は入れない**。チップの対応表だけでは足りず、**Ra266 でその番地に届く根拠** (機種の資料か §3-2 [Ra266 結線] の確認) も要る (Codex D1) |
| 読み取り手順 | 直読みか、索引書き → データ読み か。索引書きが要るなら**索引レジスタの元の値を先に読んで、読み終えたら戻す** (復元) |
| 読み取りの副作用 | 「無し (資料に明記)」だけ採用。「資料に副作用の記述が無い」は「副作用なしの証明」ではないので**入れない**。状態クリア・FIFO 取り出し・ラッチ更新のあるものは入れない |
| 復元方法 | 索引の戻し、または「不要」 |

- **0FACh にも例外を作らない** (Codex 2 回目 P2-3): io_wab.md の記述は Xa 系が対象で、Ra266 で同じ番地に届く根拠も「副作用なし」の明記も**無い**。
  上の採用条件を満たす資料 (Ra266 の機種資料、または §3-2 [Ra266 結線]) が出るまで**リストに入れない**。
  読めたとしても読み値は「Ra266 でも同じ作り」の証明にはならない (§3-5 R1)。
- **リストが空なら段 1 は読み取り 0 件で停止する** (v2 の「0FACh だけで終わる」は撤回)。読み取り 0 件も §9-1 の表に「未実施 (理由: 許可リスト空)」で残す。
- 経路 (A) 3Cxh は §2-3 の衝突が資料で否定されるまでリストに入れない。(B)/(C) はレジスタ対応表 (§3-2) が要る。
  **どの経路も確定しなければ読まない**。
- 純粋部 (許可リストの表・読み手順の組み立て・復元の順序) はホスト試験で、偽 I/O に対して「リストに無いポートへ 1 回も触らない」
  「索引を必ず元に戻す」「リストが空なら 1 回も触らない」を検査する。
- 分担 (Codex D8): **実行・検証の機構** (表の形式、読み手順の組み立て、復元、ホスト試験) はカーネル共通、**アドレス・幅・手順の中身は機種別** (Ra266 の表)。
  共通化のために未確認機種への操作を増やさない。

### 3-5. 映像を 98 側へ戻す経路 — 段 2 の前提 (Codex P1-2)

現行のカーネルには「Trident の出力中に止まったら 98 側へ戻す」経路が**無い**:

- 致命的例外 (`kernel/isr_handlers.c` `exception_handler`) は `_disable()` → テキスト VRAM に表示 → `exec_nest_level > 0` なら
  `exec_fault_recover()`、それ以外は `hlt` で停止。**`gfx_shutdown()` には接続されていない**。映像が Trident 側なら表示は見えず、
  rshell (シリアル) もこの停止からの復旧は保証しない。
- 通常の戻しは KAPI `gfx_shutdown` → `backend->leave()` を**アプリ (gshell) が呼ぶ約束**。所有者の異常終了・CTRL+STOP で
  カーネルがするのは `appslot_gfx_owner_exit()` で所有者 ID を WM へ戻すことだけで、表示は戻さない。
- タイマ待ち (`trident -t` の N 秒) は割り込みが生きている前提。

だから**最初の映像切り替えより前に**、次の R1〜R5 を票と実装で満たす。

| # | 要件 | 中身 |
|---|---|---|
| **R1** | 復帰操作の根拠 | Ra266 で 98 側へ戻す操作 (ポート・ビット・値) が**確定している**こと。認めるのは 2 つだけ: **(a)** Ra266 固有の資料 (§3-2 [Ra266 結線]) に載っている、**(b')** 段 2-X の探索試験 (§5、ユーザー承認済み) で**実際に Trident 側へ切り替えて 98 側へ戻った往復の成功が §9-1 の形で記録されている**。0FACh は Xa 系の資料しか無く、Ra266 は「資料に記述なし」。読み値 (段 1) は根拠にならない。**「復帰値を先に書いて表示が変わらない」は根拠にしない** (v2 の (b) は撤回 — 書き込みが無視された場合と区別できず、ビットの意味が未確認なら「同じビットの逆向き」も根拠にならない、Codex 2 回目 P1-1)。(b') は通常の段 2 とは**別の「復帰未確認・リセット前提の探索試験」(段 2-X)** で、往復の成功を記録してから R1 を満たした扱いにする。リセットの案内だけでは代替にならない |
| **R2** | 復帰資源の準備と寿命 | 復帰処理が使う資源 (I/O ポート番号、必要なら MMIO の写像、機種別の操作表) は**復帰フックを有効化する前に準備を終え、有効化後は失敗・shutdown・CUI 復帰の後も保持する** (畳まない)。I/O ポートだけで戻せる経路を優先 (写像不要)。経路 (C) で復帰に MMIO が要るなら、その窓は master PD に supervisor+PCD で張り (動的 PT の追加は master CR3・live AS=0 の時点だけなので、張るのは T8 の境界 = §4-2)、**写像に失敗したらフックを有効化しない** (未写像領域へ復帰処理が触りに行く経路を作らない、Codex P2-4)。復帰処理が使う関数・データは**カーネル常駐** (段 2 の診断が CPL0 アプリでも、アプリ側には置かない) |
| **R3** | 冪等で依存の無い復帰処理 | `gfx_core` に `gfx_emergency_restore()` (仮名) を置く。**入口と寿命管理 (有効化・無効化しない・再入) はカーネル共通、操作の中身は backend 固有** (Codex D8)。backend には `panic_leave` (仮名) を**新しい契約**として足す — 既存の `leave` への単純な差し込みはしない (PEGC の `leave` は空で同期の復元は `shutdown` 側、Cirrus の `leave` は `cirrus_sync_io` を含む)。契約: 割り込み停止中 (IF=0) でも使える、**割り込み・`kmalloc`・tick 待ち・エンジンの完了待ちを使わない** (エンジンは待たずに表示だけ戻す。VRAM の内容は捨ててよい)、再入しても無害、失敗しても戻り値で報告するだけで止まらない。**「状態を見ずに必ず書く」(Cirrus `leave` と同じ、`s_relay_on` の食い違いで黒画面になった教訓) は R2 の準備完了 = フック有効化の条件の内側に限る** — 有効化前は何も書かない。共通化のために未確認機種 (PC98 / PEGC) への操作を増やさない: PC98 の `panic_leave` は空、PEGC は `shutdown` の同期復元のうち IF=0 で済む部分だけを別途切り出すかを実装時に決める (本票の範囲外) |
| **R4** | 有効化の時期と接続点 | **有効化 (arm)**: 対象識別 (probe で Ra266 の Trident と分かった) と R2 の準備が済んだ後、**最初の装置変更 (モード設定・切り替え) より前**に、フックの関数ポインタと操作表を static に差して有効化する。有効化した後は shutdown でも**外さない**。**接続点**: (1) `exception_handler` と `page_fault_handler` の**両方**で、**CPL=3 / syscall 由来の fault の分岐 (`ring3_fault_kill`) の後・致命的例外の TVRAM 出力の前** (v2 の「`_disable()` 直後」は撤回 — 分類の前だと子アプリの fault でも画面を戻し §9 P2-c と矛盾し、#PF は別ハンドラなので取りこぼす、Codex P1-2)。exec 復帰 (`exec_fault_recover`) と停止 (`hlt`) の両方がこの後に来る。(2) 画面所有者 (gshell / 単独 GFX アプリ) の終了 — **回収側 (exec の終了処理・`ring3_fault_kill` の回収) が「所有者が居なくなり CUI に戻る」と判断したときだけ**カーネル側が R3 を呼ぶ (今はアプリの `gfx_shutdown` 頼み)。子アプリの fault (所有者は WM のまま) では呼ばない。(3) CTRL+STOP で CUI に戻る経路 (= (2) と同じ回収の判断)。(4) **初期化途中の失敗**: 有効化**前** (BAR 検証・予約・写像) の失敗では**装置に触らない** (写像を戻すだけ)。有効化**後** (モード設定・切り替え) の失敗では、それまでに変えたものを逆順に戻し、**最後に状態を見ずに R3 を呼ぶ**。(5) `trident -t` の戻し (段 2 / 段 2-X) も R3 を呼ぶ。N 秒待ちは `tick_count` を `volatile` で読むポーリングだが、**tick が進まなくても上限回数で抜ける**ループにする |
| **R5** | 「必ず」の保証範囲 | 保証するのは **復帰処理へ到達できる場合** (上の (1)〜(5) に到達し、OS32 のコードが実行できる場合)。**保証しない**: CPU 停止 (三重フォルト、IF=0 での hlt 以外の停止)、PCI バスがアクセスに応答しない (バス停止)、無限ループ (ハング)。これらは**リセットだけ**が復旧で、票にそう別記する。ハングの検出はシリアル rshell の無応答。**段 2-X (探索試験) ではこれに加えて「復帰操作そのものが効かない」もリセットの対象**になる — それが「復帰未確認」の意味 |

**正常な遷移** (実装契約に含める、Codex D2): DETECTED → (T8 の境界で予約・写像) PREPARED → (arm) → (init: モード設定・切り替え) ACTIVE →
(`leave` / `shutdown`: 98 側へ) PREPARED (写像・予約・フックは保持) → (再入場: 再 init は写像を作り直さない) ACTIVE。
FAILED は有効化後の失敗で R3 を呼んだ後の状態 (再試行は PREPARED から)、ISOLATED は復元できない失敗 (再起動まで)。

**段 2 の開始条件** = R1 が (a) または (b') で満たされている + R2〜R4 が実装されてホスト試験 (偽バックエンドで
「有効化前は 1 回も書かない」「有効化後は状態を見ずに書く」「kmalloc / tick を呼ばない」「有効化後の init の各段の失敗で必ず呼ばれる」
「両ハンドラでアプリ fault の分岐の後にだけ呼ばれる」「shutdown 後もフックと写像が残る」を検査) を通る + R5 をユーザーに伝えた。
**段 2-X (探索試験) の開始条件** = R1 **以外**の全部 (R2〜R4 の実装とホスト試験、§4-2 の順序、モード手順が資料で確定) + 実施直前にユーザーへ
「復帰未確認・戻らなければリセット」を伝えた (承認そのものは §7 T9 で済んでいる)。
R3/R4 の入口と寿命管理は Trident 固有ではなく**カーネル共通**なので、カーネル予算 (§4-4) に先に数える。

## 4. 既存の構造にどう載せるか

### 4-1. 層 (DESIGN §6 の二層構造をそのまま使う)

```
gfx/backend_trident.c      GfxBackend (probe / prepare / init / query / present_rect / set_palette /
                           enter / leave / panic_leave / fill_rect / blit / shutdown)。Cirrus と同じ「アクセラレータ系」
  ├─ drivers/wab_tgui.c    チップドライバ: VGA の論理番号 (3C0h 系、wab_glue.h) と拡張レジスタだけを知る
  └─ drivers/wab_glue_ra266.c (仮)  ボードグルー: PCI の BAR から窓の番地、ポートの翻訳 (§2-3 の結論)、
                           映像の切り替えと復帰 (§2-4・§3-5 の結論)。struct pci_driver の probe から見つける
```

- **WabGlue の契約 (`drivers/wab_glue.h`) で足りる見込み**: `out/in` (翻訳)、`relay` (映像の切り替え)、`lin_base/lin_size`、
  `mmio` (エンジンのレジスタが MMIO なら)。違うのは**番地が定数ではなく BAR から実行時に決まる**ことだけ。
  `lin_base/lin_size = bar0` は**条件付き** — bar0 の用途・安全なアクセス範囲・容量 (§2-1 の (i)〜(iii)) が確認できてから (P2-6)。
  §2-3 で (C) MMIO 経路になった場合は `out/in` を MMIO で実装する (契約は変えない)。
- **pci_bind との結線 — 所有権と表示の稼働状態を分ける** (Codex P2-5):
  - pci_bind の probe は**装置に触らず** BDF・BAR・Command・Revision を控えて `PCI_PROBE_OK` を返す。この **BOUND = ドライバが所有
    (他の driver に渡さない)** であって**表示が稼働している**意味ではない。NIC 向けの手順 (STARTING → I/O Enable → reset → DMA →
    irq_register → Bus Master Enable → RUNNING) は**適用しない** (reset・DMA・Bus Master Enable は**今回の実装では使わない** — 表示装置に無いと言い切る根拠は資料に無い、Codex D5)。
  - **IRQ 未割当 (255) は拒否の理由にしない** (ポーリング方式)。`PCI_BIND_IRQ_UNSUPPORTED` 相当は出さない。
  - 表示の稼働状態は `backend_trident.c` の static に別に持つ: **DETECTED** (probe で控えた) → **PREPARED** (予約・写像が済んだ、§4-2) →
    **ACTIVE** (モード設定と切り替えが済み表示中) / **FAILED** (init のどこかで失敗、逆順に戻して 98 側 — 再試行可) /
    **ISOLATED** (復元できない失敗 — 再起動まで再試行しない)。失敗理由 (どの段で何が返ったか) を診断 (`gfxmode` の表示、`lspci` の
    備考) に出す。正常な遷移 (PREPARED ⇄ ACTIVE、再入場) は §3-5 の末尾を実装契約にする。
  - **復元できない失敗**では「98 側への復帰 (§3-5 R3、常に試みる)」と「Trident の再試行禁止 (ISOLATED)」を**別々に**扱う —
    前者は表示を守り、後者は未知の状態の装置に二度と触らないため。pci_bind の QUARANTINE (次の driver に渡さない) とは別の概念で、
    表示側の ISOLATED を pci_bind の記録に写す必要は無い (pci_bind は所有権の記録)。
- 選択: `GFX_PREF_TRIDENT` (= 4) を `include/gfx_hal.h` に足し、`gfxmode trident` / `system.cfg GFX=trident` で強制。
  強制指定の失敗は現行の規則どおり **PC98 (9801 標準) へ落ちる** (`gfx_select_backend`。PEGC には落ちない)。
  **auto の probe 順に入れるか**は決裁 T5。
- 能力ビット: `TEXT_OVERLAY` 無し、`HW_FILL` / `HW_BLT` は段 5 でエンジンが動いてから。

### 4-2. メモリ・窓 (v3 のメモリマップと DEVICE_RESERVATION)

**予約 (DEVICE_RESERVATION の拡張、Codex P2-4)**

- BAR は 0x2000_0000 帯 (実測)。RAM 64MB とも PEGC の 15MB 穴とも離れているが、それで済む話ではない —
  他装置との重複 (82557 の bar0 は 0x20410000 で Trident の bar1 の 64KB 上限のすぐ上)、所有権、decode 範囲、写像の寿命の検証は残る。
- DEVICE_RESERVATION の broker は**計画・未実装**で、対象は PEGC / Xe10、許可範囲は**既知候補の定数**に限る (§4 の 4)。
  実行時の BAR をそのまま受け付ける契約ではない。Trident 用に次を**同票へ追加する** (帯の担当と調停):
  1. **BAR 検証から要求範囲を確定する責任**は Trident のグルー (`wab_glue_ra266`) が持つ: 実測 BAR が 4KB 整列で、RAM・PEGC 窓・
     他装置の BAR・hotdeploy・exec arena・カーネル/shlib と重ならず、**decode 幅が資料か T4 の安全手順で確定している**こと。
     幅が確定しない BAR は要求範囲にできない (= 段 2 の前提)。broker には「検証済みの実測範囲」を渡す口 (定数ではない) を足す。
  2. **順序**: BAR 検証 → 予約 (broker commit) → **全写像成功** (帯) → **復帰フックの有効化 (§3-5 R4 arm)** → 装置操作 (モード設定・切り替え) → 面公開 (記述子 → exec の昇格)。
     有効化前の失敗は写像を戻すだけで装置に触らない。有効化後の失敗は逆順に戻して R3。予約と (有効化後の) 復帰用写像は保持 (broker の「永久保持」の規則)、未完成の面は公開しない。
  3. **段 2 の事前準備の置き場** (T8): broker は「master CR3・live AS=0・exec 不在」の境界でしか予約・写像できず、
     **CPL0 診断アプリ (`trident -t`) の中でもその条件は満たさない** (exec の中)。案 (i) 準備を GUI 境界 (`kernel/kernel.c` の
     `is_gui` 判定後・`exec_run` 前 = DEVICE_RESERVATION §5) に乗せ、`trident -t` は準備済みの窓を使うだけの CPL0 アプリにする
     (診断の起動は**独立した明示要求**として認識し、gshell との名前比較だけに依存しない入口にする)。案 (ii) 起動時の明示キーで一回だけ準備する
     (DEVICE_RESERVATION §1 の「設定の読み取りだけでは予約しない」の例外になる)。**ユーザー決裁 (2026-09-29): (i)** (§7 T8)。
- 16MB の仮想帯を**定義するだけではこの処理は実現しない** — 帯は写像先を与えるだけで、予約・順序・公開は上の 1〜3 が要る。

**写像 — 高位仮想窓は現行の面公開 API と接続できない (Codex P1-3)**

- **帯は実装済み** (feat/gui `44bd0fe1`、この worktree の基点 `590b399b` には**未取り込み**): `include/memmap.h` の `MEM_DEVICE_APERTURE_BASE/END`
  = [0xFE000000, 0xFF000000)、`MEM_DEVICE_APERTURE_PDE_SIZE` = 4MB (PT 1 枚)。`paging_init` が**先頭 4MB の PT だけ静的に**用意し (PDE 0x3F8)、
  Cirrus (Xe10) のリニア窓がそこに載る (`docs/02_memory.md` §2-1「デバイス窓」)。バックエンドは恒等写像を前提にしない (`bb_base` は仮想番地)。
- **この票の追加作業** (実装済みの帯と区別する):

  | 仮想範囲 | 配置 (Codex 2 回目の案) | 備考 |
  |---|---|---|
  | [0xFE000000, 0xFE400000) | **Cirrus 用として維持** (静的 PT) | 触らない |
  | [0xFE400000, 0xFE800000) | **Trident LFB の候補枠** (4MB) | 枠であって LFB 4MB の実在の認定ではない。**写すのは確認済みの必要範囲だけ** (bar0 の用途と decode 幅が §2-1 (i)〜(iii) で確定した範囲) |
  | 0xFE800000 以降 | 確認済み MMIO 等を**ページ単位**で配置 | bar1 (≤64KB 推定) が MMIO と確定したらここ。未確認の BAR は写さない |
  | その他 | 未使用・Not-Present | |

  - 物理 BAR (0x2000_0000 帯) はそのまま維持し、仮想枠からそこへ写像する。恒等写像 (master PDE 128 番) は使わない。
  - **静的 PT は先頭 4MB だけ**なので、Trident の枠 (PDE 0x3F9〜) の **PT は T8 の境界 (master CR3・live AS=0) で確保**する。追加 PT も予算に数える (§4-4)。
  - 分担: **帯側** = 仮想枠の割り当てと重複管理、**broker** = 物理範囲の所有 (上の予約)、**paging** = PT の確保と属性 (supervisor+PCD、USER 昇格の変種)、
    **Trident 側** = BAR 検証と面配置。
- **ここで現行の面公開 API が壊れる** (Codex 1 回目 P1-3):
  - `exec/exec.c` は `gfx_bb_phys_range()` の返値を**仮想範囲**として `paging_addrspace_map_user_keep()` に渡す。
  - `kernel/paging.c` `addrspace_map_user_range` は `phys_base == 0` のとき**物理ページ番号を仮想番地から作り直す** (`pfn << PAGE_SHIFT`)。
    PCD/PWT は保つが物理は保たない。
  - したがって**物理番地を返せば**高位の仮想面は USER にならず (0x200… の恒等 PTE が USER になるだけ)、**高位仮想番地を返せば**
    0xFE… → 0x200… の写像が 0xFE… → 0xFE… の恒等に**壊れる**。共有 PT (master と同じ) を書き換えるので、カーネル側の写像も壊れる。
  - 既存の `paging_addrspace_map_user_range_phys()` (K5b P1) は物理を明示できるが **PCD/PWT を保たない** (`keep_cache = 0`)。
- **要件**:
  1. **内部記述子** (仮名 `GfxClientSurface { u32 virt; u32 phys; u32 size; }`) を `gfx_core` の API にする (`gfx_bb_client_desc()` 仮名)。
     恒等写像のバックエンド (PC98 / PEGC / Cirrus) は `virt == phys` を返し、exec の現行の呼び方と同じ結果になる。
  2. **物理を明示しつつ既存 PTE の PCD/PWT を保つ USER 昇格** (`paging_addrspace_map_user_range_phys_keep()` 仮名 —
     `addrspace_map_user_range(…, keep_cache = 1, phys_base)`) を paging に足す。exec は記述子でこれを呼ぶ。
  3. 分担に **`gfx_core` (記述子 API)・`exec` (記述子で昇格)・`paging` (変種)・帯の担当 (仮想枠の割り当て)・`backend_trident`** を含める。
- CPL=3 へは**クライアント面だけ**を USER で見せる (契約 G4)。表示面と MMIO は supervisor。
- **試験** (ホスト試験 + `ring3_guard trident`): (a) 表示面・MMIO が非 USER (書くと kill)、(b) client の仮想→物理が BAR 内の client 面を指し、
  **帯の PTE が 0x200… を指したまま** (恒等に壊れていない)、(c) PCD/PWT が昇格後も残る、(d) 昇格が master 側の共有 PT の物理を変えない、
  (e) 恒等バックエンドで従来と同じ PTE になる (回帰)。
- バックバッファをカード VRAM の非表示領域に置く案 (Cirrus と同じ、主記憶の `sys_reserve_top` 不要) は**条件付き** —
  §2-1 の (ii)(iii) が確認できるまで。確認できなければ主記憶 BB (PEGC と同じ形) を退避案にする。

### 4-4. カーネルの大きさ

- 予算の制限対象は **`__bss_end`** (`docs/02_memory.md` §2-1: +21.0KB で `build/os32.ld` の ASSERT がリンクを止める)。
  バックエンドの `.text` だけでは判断できない — モード表 (.rodata)・状態領域 (.bss)・**共通の写像 / 復帰処理 (§3-5 R3/R4、§4-2 の記述子と paging の変種)**・
  **Trident の枠の追加 PT** (4KB × PDE 数。静的に持つなら `.bss`、T8 の境界で pgalloc から取るならカーネル像の外 — どちらかを見積もりに書く、Codex D7) も入る。
- 参考値: Cirrus 系の `.text` は `wab_glue_xe10.o` 0x19C + `wab_cirrus.o` 0xDAD + `backend_cirrus.o` 0xB4B ≈ **6.6KB** (手元の `build/out/kernel.map`)。
  Trident は同程度〜それ以上 (モード表・クロック計算・PCI 結線)。
- 「残り 21KB」は **2026-09-29 の文面**で、T7 の判断時点で**再計測**する数字。判断は**同じ構成の変更前後で `__bss_end` の全体増分**を測り、
  並行変更 (帯・broker・LAN) 込みの余裕とリンク ASSERT で見る。
- 順序: **段 2 の準備・復帰支援に要るカーネル増分 (R3/R4 の口、記述子、paging の変種、GUI 境界の準備) を先に見積もる** — 診断を CPL0 アプリにしても
  この支援はカーネルに残る。Trident 本体 (backend + chip + glue) を静的に積むかは統合後の全体予算で決める (T7)。

### 4-5. [HW1] との関係

[HW1] は 98 側 (EGC / GRCG / GDC) の描画命令の禁止。アクセラレータの 2D エンジンを使ってよいことは DESIGN §2 B3 にあり、
Cirrus は既に使っているが、**`docs/CONSTRAINTS.md` の [HW1] の本文には追記されていない**。Trident でエンジンを使うなら、
この追記を同時に済ませるのが筋 (本票では直さない — 規則の変更は PM・ユーザーの判断)。
