# OS32の根本方針 — 機器の延命と移植負担の最小化

> 作成・更新: 2026-09-19 / 状態: **ユーザー提示の根本方針、実現方法は設計案（第1版）**
> 対象: プロジェクトの目的とv3の設計判断。新しい移植先の実装・対応を宣言するものではない。

[全体計画](PLAN.md) / [デバッグ・モジュール方針](DEBUG_AND_MODULES.md) / [移行課題台帳](MIGRATION_AUDIT.md)。

## 1. 目的

OS32は、役割を失い捨てられていく機器に、その能力に見合った用途を与え、使い続けられる期間を延ばす。
旧世代の機器では、機能と負荷を絞ることで現在も役立つ道具を作れる、という考えを出発点にする。
搭載機器に必要な仕事を、持っているCPU・メモリ・表示・入出力の範囲で安定して行えることを重視する。

「その他のアーキテクチャに移植する要素を極力抑える」は、移植時に新しく実装・修正する箇所と、
その後の保守負担を最小化する意味で扱う。移植先を増やさない、あるいは移植性を後回しにする方針ではない。
共通の仕組みを保ち、機器の能力差は対象別の実装と提供機能の組合せで扱う。

MSX3のような別系統・将来の機器への搭載は、この方向を考える例としてユーザーが提示したもの。
本書はその製品の存在・発売状況・CPU・メモリ・MMU等を前提にせず、対応予定や性能を確約しない。
対象の実際の仕様と目的の用途が分かった時点で、必要な移植部分を評価する。

## 2. 「シームレスに搭載する」の到達目標

共通コア、アプリが使う操作の意味、設定・データ、試験の多くを再利用し、
機種を追加するときは主にCPU・起動・機器接続・ドライバの実装と構成定義を足す形を目指す。
起動できたことだけでなく、その機器の用途を完了でき、保守できることを移植の成果とする。

| 再利用するもの | 目標と限界 |
|---|---|
| アプリのソースと公開APIの意味 | CPU固有コードを持たない部分を再利用し、対象CPU向けに再ビルドする。任意の既存ソースが無修正で通る保証ではない |
| 設定・文書・データ | 外部形式の整数幅・バイト順・版を明示し、ネイティブ構造体の配置に依存させない |
| テスト | 同じ要求と期待結果を各対象で検査する。実機固有の受入は別に追加する |
| x86の旧バイナリ | PC-98/x86版v3での互換性契約として扱う。別ISAでそのまま実行できる保証は含めない |

別ISAのバイナリ互換には別の仕組みが必要であり、エミュレーションを全移植先の必須機能にしない。

## 3. 共通部分と移植部分

既存の [arch](../../../arch/README.md) と [platform](../../../platform/README.md) の2軸を土台とする。
以下はv3の責任分担案であり、現在のコードがすべて分離済みであることを意味しない。

| 層 | 置くもの | 新しい対象を足すときの方針 |
|---|---|---|
| 共通コア | 公開APIの意味、資源の所有・寿命、認可の判断規則、実行・I/Oの共通ロジック | 対象CPU名・物理番地・機種名による分岐を増やさない。差が必要なら契約の不足を見直す |
| CPU依存（arch） | 起動時のCPU状態、例外・割込み文脈、必要なコンテキスト保存、特権境界、アドレス変換、ABI橋渡し | CPUに依存する命令・呼出規約・整列条件を閉じ込める |
| 機種依存（platform） | 起動媒体とメモリ地図、時計・割込み配線、バスと機器接続、初期ログ | CPUが同じ別機種でも、この部分を選び直せるようにする |
| バス・デバイス | 機器の操作と能力の申告、転送・割込み処理、機器固有の制約 | 同じ制御器やプロトコルの実装を共用し、接続先の違いを構成で渡す |
| 構成定義 | 採用する機能、メモリ予算、対応ABI、認可対象と資源割当 | 機器ごとに定義し、不要な機能を組み込まずに済むようにする |

階層を増やすこと自体を成果にしない。低速CPUでの呼出しやコピー、常駐メモリの負担を測り、
ビルド時の選択や薄い橋渡しで済む箇所を、実行時の多段処理にしない。
描画加速など固有の能力は共通の操作の裏側で利用できるようにし、全機種で同じ実装方法を要求しない。

## 4. 能力に応じた提供機能

表示、入力、保存、通信、USB等は、提供する基本操作・任意機能・上限を照会できる契約を検討する。
アプリは必要な機能を宣言し、不足時は用途を損なわない縮小動作か、理由を伴う起動拒否を選ぶ。
未実装・未接続・未対応を成功として返すスタブで埋めない。

| 条件 | 構成の判断例（用途ごとに決定） |
|---|---|
| 小さいRAM・低速CPU | CUIを中心にし、アプリ数やキャッシュ量を制限。GUIや不要な常駐機能を含めない |
| 小さい画面・少ない色数 | 解像度・色数を照会し、表示内容を絞る。PC-98の画面形式を共通APIへ固定しない |
| USBやネットワークがない | 対象機能を除外。保存や入力など代わりに使える経路を用途に合わせて選ぶ |
| 特定の処理だけ加速できる | 同じAPIを保ち、利用可能な機器固有の実装を選ぶ |

縮小可能な機能と、維持しなければならない保証は区別する。
例えば認可が検証できない構成で未認可コードを正式ロードしたり、メモリ保護がないのに隔離済みと表示したりしない。
同じ保証を実現できなければ別構成として仕様を再検討し、黙って弱めない。
外部の高性能機器による補助は必要な用途の選択肢とし、基本構成の一律の前提にしない。

## 5. x86版の条件と対象別の契約

DX4・16MB、486カーネルISA、GUIの686以上の最適化は、現在計画しているPC-98/x86版v3の条件。
他のCPUへそのまま適用する共通下限ではない。現行継続系の最低条件も従来どおり維持する。

モジュールID・APIの意味・認可手順は共通にし、バイナリ、呼出規約、配置、必要CPU機能は対象別にする。
認可台帳は対象CPU・機種／構成・ABI・バイナリを識別し、別対象の承認を流用しない。
ロード位置は対象のアドレス地図と照合し、全機種共通の絶対番地を割り当てない。
固定仮想アドレス案はアドレス変換を備える対象で検討する案であり、全機器に同じMMUを要求する宣言ではない。
DMAの境界なども該当機器の制約として定義する。

一方、現行OS32はアドレス変換・特権分離を含む実行契約を持つ。
MMUのないCPU、異なるポインタ幅、極端に小さいRAM、8/16bit機等への移植を本書で保証しない。
各対象で共通コアの前提を満たせるかを確認し、満たせなければ機能縮小・別構成・対象外を根本設計の観点で判断する。

## 6. 移植負担の確認方法

既存のARMコンパイル計測は入口として使うが、起動やアプリの動作を証明するものではない。
次に実際の移植先を選ぶ際は、次の内容を記録する（Q15〜Q17、M23〜M25）。

1. 機器を使う具体的な用途と、入力から出力までの受入操作。
2. CPU、利用可能RAM、表示・入力・保存・通信、保護機構などの実際の能力。
3. 新規作成したCPU／機種／機器コードと、変更が必要になった共通コード・理由。
4. 採用した機能、除外した機能、ビルドサイズ、常駐RAM、ピークRAM、処理時間。
5. 共通試験と実機試験、旧構成への回帰結果、起動不能時の回復方法。

機種追加で共通コードの変更が繰り返される場合は、境界やAPIを見直す。
特定の削減率や「ディレクトリ追加だけで必ず移植できる」という達成を、測定前に主張しない。
初期v3からこの境界を保つ。新しい実機への移植着手時期は、対象仕様と受入用途が決まってから定める。
