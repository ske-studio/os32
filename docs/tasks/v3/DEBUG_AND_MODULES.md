# v3 デバッグ環境・認可モジュール設計方針

> 作成・更新: 2026-09-19 / 状態: **方向性を採用、詳細設計は追記中（第2版）**
> 根拠: ユーザーのデバッグ環境分離・認可データベース案と、その方向での文書化指示。
> 実装・実機受入は未実施。現行カーネルの規約や動作を変更する文書ではない。

[全体計画](PLAN.md) / [移行課題台帳](MIGRATION_AUDIT.md) / [文書分類](DOCUMENT_MAP.md)。
機器の延命と移植負担の最小化は [根本方針](PORTABILITY_PRINCIPLES.md) に従う。
方針の要約・未決事項の番号は PLAN、実現方法の記述は本書、課題の進捗は台帳で管理する。

## 1. 採用する方向性

| 全体計画ID | 採用する方向性 | 実装までに具体化すること |
|---|---|---|
| V3-09 | 通常アプリの開発はエミュレータを中心に完結させる。カーネル・機種依存部分には物理実機での環境構築・デバッグ・受入手順を用意する | 対象機、接続、配備・回復方法、結果形式（Q10） |
| V3-10 | 必要なドライバ・共通機能をカーネルへロードする。開発者が管理する認可台帳とロード契約に従う | モジュールABI、配置、認可形式、依存・資源管理（Q11〜Q13） |
| V3-11 | 初期v3ではロード済みコードを再起動まで保持し、稼働中のアンロード・差替えを行わない | 更新予約、失敗時の回復、常駐メモリ予算 |
| V3-12 | 拡張が領域・資源・依存方向などの原則を越える場合は、例外の追加で通さず根本設計を再考する | 機械検査できる不変条件、設計改訂と再受入 |
| V3-13 | USBの機器着脱はコードのアンロードと分ける | 切断・転送停止・参照回収、接続機器の許可範囲（Q14） |

固定仮想アドレス、署名付き承認レコード、起動用の小さな認可一覧は、この方向を実現する設計案。
具体的な番地・ファイル形式・署名方式・関数名を凍結したものではない。
全面的なマイクロカーネル化や、すべてのドライバの別プロセス化は必須要件に含めない。

## 2. デバッグ環境の分離

現在のPC-98版での「実機」は物理PC-98を指す。他機種へ移植する場合はその対象の実機を使う。NP21/W等のエミュレータ上のゲスト受入とは区別して記録する。
分類は配置先だけでなく、ハードウェアに依存する責任の有無で決める。

| 対象 | 日常開発 | 受入と責任 |
|---|---|---|
| 通常のCUI・GUIアプリ | SDKとエミュレータ。毎回の物理実機配備を要求しない | 公開API・入力・表示・終了・メモリ使用を検証。OS側が実機とのAPI契約を維持する |
| カーネル共通処理 | エミュレータによる反復、ホスト上の単体試験 | メモリ保護・例外・実行制御・互換性を物理実機でも受入 |
| ドライバ・機種依存処理 | エミュレータ／模擬機器でロジックを確認し、物理実機で検証 | IRQ・DMA・I/O待ち・機器固有挙動。ユーザーランドに置いたドライバもここに属する |

速度・音・描画タイミングを製品要件とするアプリには追加の実機確認を設ける。
GUI最適化の試験では、エミュレータが必要CPU機能を実装しているかを確認し、未対応なら実機などで補う。
エミュレータでの動作だけを、物理実機の性能や対応CPUでの実行の証明にしない。

### 2-1. アプリとハードウェアの境界

通常アプリは公開APIを使い、任意のポートI/Oやデバイスメモリを直接操作しないことを設計目標にする。
ただし現行の [実行仕様](../../09_exec.md) には、CPL=0の例外とアプリに見えるVRAM領域が記載されている。
ポートI/O、MMIO、共有バッファ、特権実行を別々に監査し、現行実装が完全に独立済みとは扱わない。
既存アプリの互換性を守る範囲（Q03）と、新規アプリの契約を分けて決める（M18）。

### 2-2. 実機ワークフローの構築案

1. 対象機・CPU・RAM・ボード・媒体と、復旧できる既知の正常版を記録する。
2. カーネル・モジュール・アプリをビルドし、版・ハッシュ・シンボルを保存する。
3. 対象を停止して配備し、起動した版を照合する。エミュレータ用成果物と実機用成果物を識別する。
4. 起動初期からログを回収し、共通の試験IDで試験を実行する。
5. 例外・停止時にレジスタ、障害アドレス、実行対象、ロード済みモジュールと範囲を記録する。
6. 失敗時は既知の正常版へ戻し、結果と配備状態を残す。

ログの伝送路はシリアルを第一候補とし、接続機材・設定・ホスト側収集手順をQ10で決める。
最小の障害出力は、動的ロード・通常FS・通常のヒープ確保や処理待ちに依存しない構成を検討する。
初期段階で完全なリモートデバッガを必須化せず、例外記録とオフラインのシンボル照合から始める。
実機・エミュレータの結果には実行ID、環境、ビルドID、試験対象、終了状態、完了印を含める。
ログ欠落やタイムアウトは成功にしない。既存の結果チャネル・ランナー課題M06と統合する。

## 3. BeOSから参考にする構造

BeOSの公式資料は、デバイスドライバ、共通APIを提供するカーネルモジュール、FSアドオンを区別する。
モジュールは版を含む名前で取得し、関数テーブルを使う。参照数による管理に加え、
`B_KEEP_LOADED` で未使用時のアンロードを抑止できる。
OS32ではこの契約の分離とコード保持を参考にし、BeOSのスケジューラやABIをそのまま採用しない。
カーネル内モジュールの動的ロードは、別アドレス空間への障害隔離を意味しない。
出典: [Be Book：ドライバとカーネル](https://github.com/haiku/website/blob/master/static/legacy-docs/bebook/DeviceDrivers_Introduction.html)、
[Be Book：モジュール](https://github.com/haiku/website/blob/master/static/legacy-docs/bebook/DeviceDrivers_WritingModules.html)。

## 4. 認可台帳と登録の契約案

アプリ／ドライバに付属するINF相当の情報は要求・申告、開発者が管理する台帳は正式な認可の根拠とする。
付属ファイルの申告だけで、アドレス・資源・ロード権限を取得できる構成にはしない。

### 4-1. 識別と記録

| 項目 | 記録する情報・区別 |
|---|---|
| ドライバ／モジュールID | 実装単位を識別する安定した一意のID。版は別に持つ |
| 対応デバイス | バス種別、機種ID、機能・インターフェース条件。USBではVID/PIDだけで個体識別できるとは扱わない |
| 機器インスタンスID | 接続された実体を識別。再接続時の世代を含め、古いハンドルと混同しない |
| 認可対象 | 対象CPU・機種／構成、バイナリのハッシュ、版、カーネルABI、契約の版、必要CPU機能 |
| メモリ契約 | ロード領域、コード・データ・BSS・作業領域の上限、整列、ページ属性 |
| 資源 | I/O・MMIO・IRQ・DMAの要求、所有・共有条件、割当方法 |
| 依存と公開API | 必要なモジュールと版、公開する機能と関数テーブルの版 |
| 認可記録 | 承認主体、対象契約、署名・失効情報の方式。詳細はQ12 |

対応機種とドライバの関係は一対一に限定しない。クラスドライバは複数機種を扱い、
複合デバイスは機能ごとに別のドライバへ結び付く場合がある。競合時の選択を暗黙に決めない。
同型機器が複数ある場合はコードを共有し、状態と資源を機器ごとに持つ。

### 4-2. 候補登録と正式ロード

候補登録、正式インストール、コードのロード、機器への接続は別の状態として記録する。
ユーザーが独自の候補を登録しても、開発者の認可を得るまで正式インストール・ロードを許可しない。
ローカルの「承認済み」フラグの編集だけで正式認可にはならない。
開発者の署名付き承認レコードと、標準カーネルに置く検証用公開鍵を使う案とする。
署名はデバイスIDだけでなく、対象CPU・機種／構成、実際にロードするバイナリと契約に結び付ける。別対象の承認を流用しない。
検証後に別のファイルへ差し替わらないよう、検証対象と実行する内容を一致させる。

管理DBの形式は未決。原本から起動用の小さな認可一覧を生成する案を優先して検討する。
起動用一覧はそれ自体を検証できるようにし、台帳を読むために未ロードのFS／デバイスが必要になる循環を避ける。
SQLiteやネットワークへの常時接続を、カーネル起動・認可確認の必須条件にしない。
旧台帳への巻戻し、失効、鍵更新、開発中コードの試験方法はQ12で設計する。
開発用の試験経路を設ける場合も、未認可のものを正式認可済みと表示しない。

認可はロードを許す判断であり、カーネル内の不正な書込みを実行時に隔離する機構ではない。
実装レビューと対象実機での受入を認可根拠に含める。

## 5. 配置・ロード・保持の契約案

固定配置で初期ローダを簡単にする案を、PC-98/x86版などアドレス変換を備える対象で検討する。固定する対象は原則カーネル仮想アドレスの範囲とし、
DMA等の物理配置条件とは分ける。実番地・割当単位・再配置方式は対象別にQ11で決め、全機種共通の絶対番地を要求しない。
予約した仮想領域全体を物理RAMとして確保せず、PC-98版の16MB構成でコード・機器別状態・作業領域の実消費を測る。他機種は対象別予算で確認する。
保護・アドレス変換のない対象はQ15で成立条件を再検討し、現在の隔離保証を維持できるとは断定しない。

ロード時の手順案:

1. 申告と認可を照合し、対象バイナリ・ABI・CPU・依存関係を検証する。
2. オーバーフローを含むサイズ計算、整列、コード・データ・BSSの全範囲を検査し、予約領域との重複を拒否する。
3. 必要な資源を取得できることを確認し、初期化する。依存循環や資源競合は初期化前に拒否する。
4. 初期化成功後にデバイス／APIを公開する。失敗時に未完成の登録を残さない。
5. ロード済みコードは再起動まで保持する。稼働中に上書きせず、更新は次回起動用として扱う。

初期化途中の失敗でも、開始したIRQ・DMA・コールバック等を停止する後始末は必要。
コードの保持によって資源の回収義務がなくなるとは扱わない。
メモリ上のコードを保持しても、登録数・ロード総量には上限を設け、枯渇時は追加ロードを拒否する。
別モジュールを固定番地で直接呼ばず、ID・版から取得した関数テーブルを介す。APIの意味とIDは共通化し、テーブルのバイナリ配置・呼出規約・実行形式は対象別ABIで定める。
旧アプリ向けKAPIとモジュール間ABIは別の契約にし、内部の変更を既存KAPIへそのまま漏らさない。

起動に必要なものは組込みまたは初期イメージに含める。最小の障害出力経路も確保する。
組込みとロード式で初期化・登録の契約を揃え、起動時の選択ロードから始めて実行中の追加ロードへ進む。
協調型のまま別プロセスのドライバを導入する場合は、I/O処理の実行機会を保証する契約が先に必要。
その保証がない段階では、時間制約の強い処理をカーネル側に残す案とする。

## 6. USBの着脱とコードの寿命

USBではドライバコードと接続された機器の寿命を分ける。
通常の接続は「検出 → 認可された対応付けの確認 → 機器別状態の初期化 → 公開」、
切断は「新規要求停止 → 転送停止・完了処理 → 切断通知 → 最後の参照解放後に状態回収」とする案。
突然抜かれる場合もあるため、安全な取外し操作の実行を前提にしない。
保存機器の未完了書込みを成功にせず、データ保存の保証とは別に切断を扱う。

ドライバコードは切断後も保持し、再接続では新しい世代の機器状態を作る。
古いハンドルや遅れて届いた完了通知が、新しい機器に作用しないようにする。
既存ハンドルを持つアプリには切断を返し、参照中の状態を先に解放しない。
ホストコントローラがIRQ・DMAを所有する部分と、機器・インターフェースごとの転送資源を分ける。

認可済みクラスドライバに合う機器を広く許可するか、個別機種まで認可するかはQ14で決める。
複合デバイスの機能別許可、複数同型機器、再接続時の識別も同時に設計する。
USBの着脱対応を理由に、初期v3の実行中コードアンロードを必須化しない。
参考: [Linux USBの接続・切断とドライバ登録](https://docs.kernel.org/driver-api/usb/writing_usb_driver.html)。
OS32がLinuxのAPIを採用するという意味ではない。

## 7. 原則と設計を再考する条件

ここでの「クロスオーバー」は、予約範囲の侵入、無許可の資源共有、依存方向の逆転、
非公開データへの依存、CPU下限や既存ABIの破壊など、拡張による契約境界の越境を指す。
台帳登録時と実行時の資源割当で検査できる条件を明文化する。
IRQ等を共有する設計は、共有の調停・所有権を明示して契約化する場合に限る。

必要な拡張が原則に収まらなければ、当該追加の認可を保留し、理由と衝突する契約を記録する。
共通API・配置・所有権・依存関係を再設計し、必要なら契約版を上げて既存モジュールも再受入する。
デバイス固有の特例で検査を飛ばすことを標準手段にしない。

## 8. 段階と受入案

| 段階 | 内容 | 主な受入条件 |
|---|---|---|
| A | 実機環境とエミュレータ環境の手順・結果形式を整備 | 起動版照合、例外記録、既知の正常版への復帰を両環境で記録できる |
| B | 組込みのままモジュールABI・資源・登録契約を整理 | 既存アプリの互換性を保ち、失敗した初期化を公開しない |
| C | 認可台帳・起動時の選択ロード | 未認可、バイナリ不一致、ABI不一致、範囲重複、依存循環を拒否。認可済み構成を実機受入 |
| D | 実行中の追加ロードと再起動時の更新 | 使用中コードを差し替えず、総量上限・失敗後始末・回復手順を満たす |
| E | USB機器の着脱 | 転送中切断、複数同型機器、複合機能、再接続、古い参照を試験。コードは保持 |

全体計画のP3にA、P5にB〜Dを対応させる。Eの着手は対象USBハードとQ14の決定後とする。
各段階でPC-98/x86版はDX4・16MBの予算とカーネル486 ISAを確認する。他機種は対象別の能力・予算・ISAを確認する。実機・USB対応の実装完了を現在の状態として表記しない。
