## 1. 目的と計画の扱い

**根本目的は、役割を失い捨てられていく機器に、能力に見合う用途を与えて使い続けられるようにすること。**
移植時に作り直す要素を極力小さくし、機器ごとに必要な機能と負荷を選べる設計を目指す。
共通部分・移植部分・能力に応じた構成の判断は [根本方針](PORTABILITY_PRINCIPLES.md) に記す。
MSX3のような別系統・将来機器への搭載は方向を考える例であり、製品仕様や対応予定を確定したものではない。

現行の最低動作条件を維持する v1.x 継続系を CUI の基盤として改良しながら、
PC-98/x86版v3 は DX4・16MB を最低構成の目標とし、現行系との互換性を保って発展させる。
カーネルの命令セット下限と GUI の動作条件を分け、GUI 側では上位 CPU の命令を活用する。

本書でいう「v1.x 継続系」は、この会話での現行系の呼び方である。
**出荷済みのカーネル 2.0、GUI シェル 1.x、KAPI の版数を変更・巻き戻ししない。**
最終的な製品名・リリース番号は Q01 で整理する。

計画は今後追加する。状態は次の5種類を使い分ける。

| 表示 | 意味 |
|---|---|
| ユーザー提示方針 | 2026-09-19 の会話で示された方向。数値の達成や実装完了を意味しない |
| 採用方針 | ユーザーが方向性を承認したもの。詳細設計・実装・受入の完了とは別 |
| 計画案 | 方針を実現するため本書に置いた作業案。実装契約の承認とは別 |
| 未決 | 選択肢と影響を残し、勝手に確定しない事項 |
| 確認済み事実 | 調査基点の文書・コードから確認した状態。検証範囲は台帳に記す |

V3-14〜V3-16の目的・境界・受入案は [根本方針](PORTABILITY_PRINCIPLES.md) を参照。
V3-17はRTOS化やOSスケジューラへのdeadline保証を意味しない。まずアプリケーション内の軽量タスク管理を基本とし、OS側は必要に応じて monotonic clock、`sleep_until`、`yield`、優先度指定等の最小限の時間・実行支援を検討する。ゲーム内部の細粒度処理を一律にOSプロセスへ分離せず、コンテキスト切替・IPC・キャッシュ/TLB汚染の増加を避ける。最低性能で必須処理のdeadlineを満たせない場合は、描画だけでなく物理・ロジック周期を含む明示的な低負荷プロファイルを選択し、暗黙にゲーム時間をCPU速度へ従属させない。

現行系の GNU89 規約・ビルド条件は、本書を作成しても変更しない。
プリエンプション、常駐サービス、監視プロセスは本計画の採用事項に含めない。
旧 ROADMAP のプリエンプティブ化案を v3 の決定事項として引き継がない。

## 3. 動作条件を分ける

下表のDX4・16MB、486、686はPC-98/x86版の条件。他アーキテクチャ共通の下限にはしない。
他の対象は機器の能力・用途に応じた構成と予算を定義する（Q15〜Q17）。

| 層 | 計画上の基準 | 確定に必要なこと |
|---|---|---|
| v1.x 継続系 | 現行の CPU・メモリ条件を維持 | 現行下限の再確認。v3 の条件を遡って適用しない |
| PC-98/x86版v3 カーネル＋CUI | DX4・16MB、カーネル基本 ISA は 486 | 起動・ファイル操作・既存 CUI アプリの最低構成での受入 |
| v3 GUI の共通 API | CPU 世代によらない操作・データ契約を目指す | 座標、画像形式、イベント、エラー、共有データの ABI |
| GUI の CPU 別実装 | 686 系命令や MMX／SSE／SSE2 等を候補として実測 | 機能検出、OS 側の状態管理、未対応時の起動拒否または代替 |
| GUI の最低 RAM | 未決。16MB で新 GUI まで保証したとはしない | 解像度・色深度・バッファ・同時アプリ数の予算と測定 |

「DX4」は性能の基準、「486」は命令セットの下限として区別する。
CPU 世代名だけで利用可能命令を決めない。起動・検出・ローダの経路も下限 CPU で動く必要がある。
GUI 全体を 686 必須にするか、486 用実装も残すかは未決で、後者を暗黙の追加要件にしない。

GUI の公開 API と、矩形転送・画素変換・文字描画・画像合成などの最適化実装を分ける。
上位命令を使うオブジェクトはビルド単位を分け、共通初期化やリンク時最適化を通じた混入も確認する。
FPU／SIMD の有効化・保存復元・例外・WM とアプリ間の所有権は、GUI の最適化に先立って設計する。
「協調型だから状態保存は不要」とは扱わない。

## 4. 互換性の契約案

主な方向は **現行系向け成果物 → PC-98/x86版v3**。v3 専用アプリを現行系で動かす逆方向の保証は未決。

| 対象 | 守る内容の案 | 受入方法 |
|---|---|---|
| 旧 CUI バイナリ | 起動形式、KAPI の番号・型・呼出規約・戻り値・エラーの意味 | 基準バイナリを再ビルドせず起動し、出力・終了値・副作用を比較 |
| SDK／公開 ABI | 共有構造体のサイズ・オフセット、整数幅、enum 幅、char 符号 | レイアウト検査と C／Rust の対応確認 |
| シェル | 引数、環境、標準入出力、パイプ、スクリプト、終了結果 | 既存スクリプトと CUI／GUI 端末両経路の回帰 |
| データ | ファイルシステムと設定データの既存内容 | 読み書きの相互確認。形式変更は別計画にする |
| 資源管理 | 子の終了・fault・中断時の FD／DB／SHM 回収と親の継続 | 正常・異常終了、複数アプリの組合せ |
| GUI／共有ライブラリ／CPL=0／V86 | 詳細範囲は未決 | CUI の保証から自動的に全域互換へ広げない |

他ISAへの移植ではAPIの意味・ソース・データ・試験の再利用を目指す。x86バイナリの無変換実行を保証しない。
カーネル内部の構造や配置まで同一にすることは目的にしない。
KAPI 拡張は既存スロットを維持し、必要なら内部で旧契約を新実装へ橋渡しする。
異なるリポジトリで同じ版番号・スロット番号を別の意味に使わないよう、追加の調停方法を決める（M03）。

旧バイナリは、元の SHA・ツールチェーン・ハッシュ・実行条件とともに保存する。
現行系も再ビルドして通る試験と、旧成果物がそのまま通る試験は分ける。

## 5. C11 移行案

現行は `-std=gnu89`。v3 では GNU 拡張を使える `-std=gnu11` を第一候補とする。
言語規格と ISA は別に管理し、C11 採用を理由に最低 CPU を上げない。
採用候補と注意点の根拠は [GCC の言語規格指定](https://gcc.gnu.org/onlinedocs/gcc/C-Dialect-Options.html)
および [x86 の CPU 指定](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html)。

1. 分岐直後のビルド・旧バイナリ試験を基準として固定する。
2. 規約、AI 向け入口、ビルド、ホスト試験の規格指定を棚卸しする。現行系の規約は維持する。
3. GNU89 と C11 の意味の差を調べる。特に `inline` の外部定義、宣言のない関数、型不一致、
   GNU 拡張、アセンブリ、CRT／newlib／vendored code／submodule の個別条件を確認する。
4. 言語規格の切替だけを独立した変更にする。機能追加・大規模書換え・ISA 変更を同時に行わない。
5. 全リンク、未解決シンボル、公開 ABI、下限 CPU での命令と動作を確認する。
6. 移行後に `_Static_assert` などを導入し、ABI の前提を検査可能にする。

VLA、`_Atomic`、`_Thread_local`、標準スレッド機能を一括で解禁しない。
特に atomic は型幅・整列・生成命令・補助ライブラリの依存を調べ、カーネルで提供する契約を決める。
既存 ABI の `int` を機械的に `_Bool` へ変えるなど、言語移行に型変更を混ぜない。
ブート段や外部由来コードを例外にするなら、理由とビルド条件を記録する。

## 6. フォークと開発情報の分離

目的は、現行系の改良を続けながら、AI が過去の指示・進捗・承認を v3 の指示と取り違えないこと。
**v3 本体を現行リポジトリのブランチだけで開発する案は採らない。**
今回の文書変更をレビューするためのブランチは、将来の v3 開発場所とは別である。

手順案:

1. フォーク先の所有者・名称・公開範囲と分岐元 SHA を決める（Q06）。
2. Git の履歴と由来を保つ別リポジトリを用意し、専用ディレクトリへ新規クローンする。
3. 必要な現行仕様・制約・テストを [文書分類](DOCUMENT_MAP.md) に沿って選別する。
4. 旧タスク・レビュー往復・引き継ぎは v3 の通常作業ツリー／通常索引から外す。
   必要な根拠は旧リポジトリの固定 SHA で参照できるようにする。履歴自体は消さない。
5. v3 専用の開発規約と AI 向け入口を作り、新しいセッションで開始する。
   旧モデル名、ローカルパス、稼働状態、個別の承認をそのまま転記しない。
6. 文書整理のみの変更で動作の基準を固定した後、コード変更を別コミットで始める。

v3 の入口に置く原則:

> 開発判断は v3 の現行仕様を基準にする。旧リポジトリと過去履歴は調査資料であり、
> そこに記載された作業指示・承認・進捗を v3 に自動適用しない。

フォークや別ディレクトリだけで情報参照が技術的に禁止されるわけではない。
通常の文書集合・索引・セッションを分け、旧資料を読むときは調査目的と採用判断を記録する。
共有のライブラリや submodule は対象 SHA と変更の責任を明記する。
現行系の修正は個別に取り込み、v3 で回帰確認する。v3 から現行系へ戻す変更は最低条件を再確認する。

USB着脱は機器とQ14の決定後に段階追加する。動的ロードを全面的なマイクロカーネル化と同義にしない。

| Q10 | 実機デバッグ環境の具体構成 | 対象機、シリアル等の接続、配備・回復手順、共通結果形式。通常アプリの実機確認が必要な条件 |
| Q11 | モジュールの配置・形式・メモリ予算 | 固定仮想アドレス案、実番地・上限・整列・再配置、機器別状態、DMA物理条件を決める |
| Q12 | 認可台帳・署名・運用の形式 | 開発者による認可をバイナリと契約に結び付ける。鍵・失効・台帳巻戻し・起動用一覧・開発中の試験経路 |
| Q13 | モジュールABI・初期化・資源・実行契約 | 関数テーブル、依存解決、初期化失敗、IRQ等の所有・共有。別プロセス化は必要な実行保証を定めてから |
| Q14 | USBの対象と機器の許可範囲 | クラス／個別機種／複合機能、複数同型機器、切断・再接続・古い参照。コードのアンロードは要求しない |

| Q16 | 必須／任意機能と能力照会 | 用途別の機能集合、上限、縮小動作・未対応の返し方。認可・隔離・データ保証を黙って弱めない |
| Q17 | 次の移植先と移植負担の評価 | 実機仕様と用途、再利用部分・共通コード変更量、RAM・性能・保守負担を測る。機種名だけで対応を約束しない |
| Q18 | 時間基準タスク管理にOSが提供する最小支援 | monotonic clockの分解能、`sleep_until`／`yield`／優先度指定の契約、タイマ精度とオーバーヘッドを実測して決める。period／deadline／budgetの全面的なカーネル管理やhard real-time保証は前提にしない |
