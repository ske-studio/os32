# v3 の計画 — カーネルの構造を組み直す

> 発行: PM (Claude Code `claude-opus-5`、2026-09-17) / 状態: **計画 (2026-09-17)**

**着手は v1.x が終わってから** ([`../../ROADMAP.md`](../../ROADMAP.md) §1 の残りは
8bpp バックエンド (R2) / About / テキストエディタ)。

呼び方: 出荷済みのカーネルが既に **2.0** を名乗っているので、次期カーネルは **v3**
(ユーザー決裁 2026-09-15、ROADMAP §0)。

## 0. なぜ「構造を組み直す」なのか

2026-09-17 に**カーネル帯域 1MB が 17KB 足りない**状態を踏んだ
([`../memory/TASK_KSTACK_USER.md`](../memory/TASK_KSTACK_USER.md))。共有メモリ帯が
カーネルスタックを飲み、**スタックが設計の 16KB ではなく 4KB しかなく**、
**余裕は 224 バイト**しか残っていなかった。誰も気づいていなかった。

応急処置で余裕は **34.4KB** に戻したが、**カーネル本体は 433.6KB あり育ち続けている**。
そしてこの先に積みたいものが、どれも小さくない (§3)。

**帯の中で削るのは延命でしかない。** v3 は「機能を足す」前に「入れ物を作り直す」。

## 1. 順序 (これは動かさない)

| 順 | やること | なぜその順か |
|---|---|---|
| 1 | **規約を C11 へ** (変数は**固定長を維持**) | `_Static_assert` は定数式でなければ**コンパイルエラー**。今の自作 `STATIC_ASSERT` は定数式でないと**黙って無効化される** (`kernel/shm.c` の 2 本が毎ビルド警告を出しながら何も検査していなかった)。**再配置を検査なしでやらないため** |
| 2 | **メモリマップの全体再配置** | §2。**ドライバの置き場とアプリへの払い出しを最初から勘定に入れる** |
| 3 | **ドライバの動的読み込み** | §3 |
| 4 | **PCI の列挙** | [`../realhw/PLAN.md`](../realhw/PLAN.md) §6 |
| 5 | **Intel 82557 のドライバ** | 同 §5 |

1 と 2 を**同時に動かさない**。どちらも全ファイルに触れるので、壊れたときに
**どちらが原因か切り分けられない**。この領域は静かに壊れる (§0 の 224 バイトがそれ)。

## 2. メモリマップの再配置 — 先に決めること

**先に数字を決めないと、削ってもまた同じ場所に戻る。**

| 決めること | 現状 | 論点 |
|---|---|---|
| **カーネル本体の上限** | 433.6KB / 予算 468KB (残り 34.4KB) | 育ち続ける。**どこまで許すのかを決める** |
| **ドライバの置き場** | 無い (全部カーネルに静的リンク) | §3。**再配置の時点で場所を取っておく** |
| **アプリへの払い出し** | §4 | 既存票あり |
| 浮動と固定の隣接 | `KHEAP_BASE` が `__bss_end` から浮き、固定番地のスタックと隣り合っていた | **同じ構図を作らない**。門はリンカの `ASSERT` で既に入れた |

**やってはいけないこと**: 再配置を先にやってから「ドライバの置き場が無い」と気づく。
**§3 と §4 を決めてから帯を切る。**

## 3. ドライバの動的読み込み (ユーザー指摘 2026-09-17)

### なぜ要るか — 数字

| | 大きさ |
|---|---|
| カーネル本体 | 433.6KB |
| 残り予算 | **34.4KB** |
| 現在のドライバ群 | 約 89KB (`drivers/` 70KB + `net/` 19KB) |
| これから足したいもの | PCI (数 KB) + 82557 (十数 KB) + …… USB は**単独で 100KB 超** |

**34KB では足りない。** 静的リンクのまま積めば、2026-09-17 と同じことが必ず起きる。

### 土台は半分ある

`kernel/shlib.c` (12.4KB) が共有ライブラリを `0x400000` の 1MB 帯へ起動時に読み込む。
**ヘッダの値だけで配置を決め、番地を直書きしていない。**
**再配置とジャンプ表という一番面倒な部分は既に動いている。**

### ただし 3 つ違う

| | 共有ライブラリ | ドライバ |
|---|---|---|
| 特権 | CPL=3 のアプリ向け。USER で載る | **カーネル権限**。ポート I/O と割り込み |
| 呼ぶ向き | アプリが呼ぶ | **カーネルが呼ぶ** |
| 置き場 | アプリ空間 (`0x400000`) | **カーネル帯。そこが今まさに満杯** |

必要なのは KernelAPI とは別の**内側向けの取り決め** (ドライバが実装すべき口と、
カーネルが提供する口)。

### 設定は手動でよい (ユーザー、2026-09-17)

自動検出も依存解決も要らない。**起動時に一覧を読んで順に載せるだけ**で足りる。
一覧はファイルに持たせる (試験ランナーの `guest_tests.txt` と同じ考え方)。
これで実装がかなり軽くなる。

### 決めること

- カーネル帯のどこに置くか (**§2 と同時に決める**)
- 内側向けの取り決めの形。**KernelAPI の [ABI2] 追記のみの規則をここにも効かせるか**
- 読み込みに失敗したドライバをどう扱うか (**起動を止めるのか、その機能だけ諦めるのか**)
- どのドライバを外に出すか。**全部は出さない** — ブートに要るもの (IDE / コンソール) は
  静的のままでよい

## 4. アプリへのメモリの払い出しを見直す (ユーザー指摘 2026-09-17)

**既存票がある**: [`../memory/APP_BAND_PDE.md`](../memory/APP_BAND_PDE.md)
(アプリ帯の可変 PDE 化)。実装は `b8dab24` で着地済みだが、
**§5 のゲスト受入が未記録のまま**。**まずここを閉じる。**
受入していない土台の上に見直しを積まない。

現状 (`CLAUDE.md` の帯の表): `0x500000` から
**コード+bss → sbrk → guard → exec_heap → スタック** の順に積む。

論点:

- 1 アプリに渡せる量の上限は何で決まっているか。**PDE の枚数か、物理メモリか、設計の都合か**
- 2 系統のヒープ (newlib の sbrk と KAPI の `exec_heap`) を持ち続けるか。
  シェルはこれで一度事故っている (2026-09-03 に `exec_heap` を分離した経緯が
  [`../../02_memory.md`](../../02_memory.md) にある)
- 協調型で最大 4 本動くとき、**帯をどう分けるか**
- **要求した量が取れなかったときの答え方**。今は何を返すか

## 5. 温めているアイデア (ユーザー、2026-09-17) — **計画ではない**

**まだ決まっていない。** 形になっていないものを計画表に混ぜると順序が狂うので、
ここに分けて置く。**どれも v3 の 1〜5 が済んでからの話。**

### 5-1. ネットワーク越しのホストを仮想メモリとして使う

386 はページングを持ち、ページフォルトを捕まえられるので、**原理的には成立する**。
Host Services のワイヤ (`net/link.c`) も既にある。

**ただし確かめるべきことが多い。**

- **待ち時間**。LAN の往復はミリ秒単位。**ディスクのスワップより速いとは限らない**
- **再入**。ページフォルトを処理する最中に NIC ドライバを呼ぶ。**その NIC ドライバが
  触るメモリがスワップアウトされていたら詰む**。ここの切り分けが設計の核心
- **どのページを対象にするか**。カーネル帯は当然除外。アプリ帯のどこまでか
- **落ちたときの答え方**。ネットワークが切れたらどうなるのか

**先に測るべき**: 実機の LAN でページ 1 枚 (4KB) を往復させたとき何ミリ秒かかるか。
**それがディスクより遅ければ、この案は成立しない。**

### 5-2. 外部プロセッサ / KVM のようなもの

**まだ定義が足りない。** 少なくとも 2 つの別の話が混ざっている。

- **計算の外出し** — 重い処理をネットワーク越しのホストにやらせる。
  Host Services の延長で、**現実的**。何を外に出すのかを決めるところから
- **仮想化** — 386 にはハードウェアの仮想化支援が無いので、KVM と同じものは作れない。
  OS32 は既に **V86 で DOS を動かしている**ので、その延長に何を足したいのかを
  はっきりさせる必要がある

**次にやること**: どちらの話なのかを決める。**それまで見積もれない。**
