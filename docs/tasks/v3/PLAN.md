## 1. 目的と計画の扱い

**根本目的は、役割を失い捨てられていく機器に、能力に見合う用途を与えて使い続けられるようにすること。**
移植時に作り直す要素を極力小さくし、機器ごとに必要な機能と負荷を選べる設計を目指す。
共通部分・移植部分・能力に応じた構成の判断は [根本方針](PORTABILITY_PRINCIPLES.md) に記す。
MSX3のような別系統・将来機器への搭載は方向を考える例であり、製品仕様や対応予定を確定したものではない。

現行の最低動作条件を維持する v1.x 継続系を CUI の基盤として改良しながら、
PC-98/x86版v3 は DX4・16MB を最低構成の目標とし、現行系との互換性を保って発展させる。
カーネルの命令セット下限と GUI の動作条件を分け、GUI 側では上位 CPU の命令を活用する。

本書でいう「v1.x 継続系」は、この会話での現行系の呼び方である。
**出荷済みのカーネル 2.0、GUI シェル 1.x、KAPI の版数を変更・巻き戻ししない。**
最終的な製品名・リリース番号は Q01 で整理する。

計画は今後追加する。状態は次の5種類を使い分ける。

| 表示 | 意味 |
|---|---|
| ユーザー提示方針 | 2026-09-19 の会話で示された方向。数値の達成や実装完了を意味しない |
| 採用方針 | ユーザーが方向性を承認したもの。詳細設計・実装・受入の完了とは別 |
| 計画案 | 方針を実現するため本書に置いた作業案。実装契約の承認とは別 |
| 未決 | 選択肢と影響を残し、勝手に確定しない事項 |
| 確認済み事実 | 調査基点の文書・コードから確認した状態。検証範囲は台帳に記す |

V3-17はRTOS化やOSスケジューラへのdeadline保証を意味しない。まずアプリケーション内の軽量タスク管理を基本とし、OS側は必要に応じて monotonic clock、`sleep_until`、`yield`、優先度指定等の最小限の時間・実行支援を検討する。ゲーム内部の細粒度処理を一律にOSプロセスへ分離せず、コンテキスト切替・IPC・キャッシュ/TLB汚染の増加を避ける。最低性能で必須処理のdeadlineを満たせない場合は、描画だけでなく物理・ロジック周期を含む明示的な低負荷プロファイルを選択し、暗黙にゲーム時間をCPU速度へ従属させない。

現行系の GNU89 規約・ビルド条件は、本書を作成しても変更しない。
プリエンプション、常駐サービス、監視プロセスは本計画の採用事項に含めない。
旧 ROADMAP のプリエンプティブ化案を v3 の決定事項として引き継がない。

## 3. 動作条件を分ける

下表のDX4・16MB、486、686はPC-98/x86版の条件。他アーキテクチャ共通の下限にはしない。
他の対象は機器の能力・用途に応じた構成と予算を定義する（Q15〜Q17）。

| 層 | 計画上の基準 | 確定に必要なこと |
|---|---|---|
| v1.x 継続系 | 現行の CPU・メモリ条件を維持 | 現行下限の再確認。v3 の条件を遡って適用しない |
| PC-98/x86版v3 カーネル＋CUI | DX4・16MB、カーネル基本 ISA は 486 | 起動・ファイル操作・既存 CUI アプリの最低構成での受入 |
| v3 GUI の共通 API | CPU 世代によらない操作・データ契約を目指す | 座標、画像形式、イベント、エラー、共有データの ABI |
| GUI の CPU 別実装 | 686 系命令や MMX／SSE／SSE2 等を候補として実測 | 機能検出、OS 側の状態管理、未対応時の起動拒否または代替 |
| GUI の最低 RAM | 未決。16MB で新 GUI まで保証したとはしない | 解像度・色深度・バッファ・同時アプリ数の予算と測定 |

「DX4」は性能の基準、「486」は命令セットの下限として区別する。
CPU 世代名だけで利用可能命令を決めない。起動・検出・ローダの経路も下限 CPU で動く必要がある。
GUI 全体を 686 必須にするか、486 用実装も残すかは未決で、後者を暗黙の追加要件にしない。

GUI の公開 API と、矩形転送・画素変換・文字描画・画像合成などの最適化実装を分ける。
上位命令を使うオブジェクトはビルド単位を分け、共通初期化やリンク時最適化を通じた混入も確認する。
FPU／SIMD の有効化・保存復元・例外・WM とアプリ間の所有権は、GUI の最適化に先立って設計する。
「協調型だから状態保存は不要」とは扱わない。

## 4. 互換性の契約案

主な方向は **現行系向け成果物 → PC-98/x86版v3**。v3 専用アプリを現行系で動かす逆方向の保証は未決。

| 対象 | 守る内容の案 | 受入方法 |
|---|---|---|
| 旧 CUI バイナリ | 起動形式、KAPI の番号・型・呼出規約・戻り値・エラーの意味 | 基準バイナリを再ビルドせず起動し、出力・終了値・副作用を比較 |
| SDK／公開 ABI | 共有構造体のサイズ・オフセット、整数幅、enum 幅、char 符号 | レイアウト検査と C／Rust の対応確認 |
| シェル | 引数、環境、標準入出力、パイプ、スクリプト、終了結果 | 既存スクリプトと CUI／GUI 端末両経路の回帰 |
| データ | ファイルシステムと設定データの既存内容 | 読み書きの相互確認。形式変更は別計画にする |
| 資源管理 | 子の終了・fault・中断時の FD／DB／SHM 回収と親の継続 | 正常・異常終了、複数アプリの組合せ |
| GUI／共有ライブラリ／CPL=0／V86 | 詳細範囲は未決 | CUI の保証から自動的に全域互換へ広げない |

他ISAへの移植ではAPIの意味・ソース・データ・試験の再利用を目指す。x86バイナリの無変換実行を保証しない。
カーネル内部の構造や配置まで同一にすることは目的にしない。
KAPI 拡張は既存スロットを維持し、必要なら内部で旧契約を新実装へ橋渡しする。
異なるリポジトリで同じ版番号・スロット番号を別の意味に使わないよう、追加の調停方法を決める（M03）。

旧バイナリは、元の SHA・ツールチェーン・ハッシュ・実行条件とともに保存する。
現行系も再ビルドして通る試験と、旧成果物がそのまま通る試験は分ける。

### 4.1 将来の Windows 98 互換レイヤーに備える API 設計

v3 の成果物に Win98 互換レイヤー、PE32 ローダ、Win32 DLL 群を含めることは要求しない。
ここで行うのは、後から互換レイヤーを追加するときにカーネルや主要 KAPI の大改造を要求しないよう、
**OS32 固有機能と互換ランタイムの責務境界を先に決めること**である。

想定する将来構成:

```text
PC-98 Windows 98 向け PE32 アプリ
        |
        v
Win98 compatibility layer        <- 将来開発。OS32 本体と分離
(kernel32/user32/gdi32/winmm 等)
        |
        v
Win32 -> OS32 wrapper
        |
        v
v3 KAPI / libos32gui / gfx / sound / VFS
```

v3 API は Win32 の型や HANDLE、NT Native API をそのままカーネル契約へ持ち込まず、
互換層が組み立てに使える低水準かつ用途非依存の原語を提供する。候補は以下。

| 領域 | v3で準備する境界 | v3で要求しないもの |
|---|---|---|
| 仮想メモリ | アプリ領域の確保／解放、必要なら固定位置・保護属性・照会を表現できる契約 | `VirtualAlloc` 等のWin32名、NT Memory Manager互換 |
| 実行形式／モジュール | 複数コード／データ領域、再配置や外部シンボル解決を将来ローダが実装できる配置契約 | PE32ローダそのもの、`LoadLibrary` 実装 |
| ファイル | VFSのopen/read/write/seek/stat等を安定した型・エラーで利用可能にする | Windows path/drive/共有モードのカーネル実装 |
| 時刻 | monotonic time、wall clock、sleep系の意味と分解能を明確化 | Win32 timer APIそのもの |
| GUI／入力 | window/event/drawingをWin32と独立したOS32契約として保持 | HWND/HDC等をKAPIへ導入 |
| 音声 | PCM/FM等の能力照会と再生境界をOS32ネイティブで定義 | WinMM/DirectSound APIそのもの |
| 互換用オブジェクト | Win32 HANDLE等は将来ラッパー内部で管理可能にする | NT Object ManagerをOS32カーネルへ導入 |
| 実行モデル | 現行の協調型・単一アプリ集中方針を維持できるAPIにする | Win32対応を理由としたプリエンプション、SMP、汎用thread scheduler |

Win98互換の対象はユーザーアプリであり、Windows 98用VxD、デバイスドライバ、ディスク管理や
OS保護機構に密結合したツールまで互換対象に含めない。将来、実アプリの要求から必要APIを
追加する方針とし、「Win98 API 100%実装」をv3の設計目標にはしない。

GPL主体のReactOS等から実装コードをOS32のMIT部分へ直接取り込む前提にはしない。
必要な互換層はOS32 KAPIを呼ぶ独立ラッパーとして設計し、仕様・観測挙動・公開資料を基に
独自実装できる境界を保つ。ライセンスの異なる外部コンポーネントを将来採用する場合は、
OS32本体との配布・リンク・派生物の扱いを個別に確認する。

また、Win98互換層が将来WinSock／WinINet等を必要としても、それを理由にOS32へTCP/IP・DNS・TLSを
導入する前提にはしない。既存の [Host Services計画](../network/HOST_SERVICES_PLAN.md) が定める
「ホスト = I/Oコプロセッサ、OS32は要求と結果だけを扱う」境界を継承し、対応可能な通信機能は
compat wrapper → Host Services → Host Agent の経路へ写像する。

v3での受入は「Win98アプリが動くこと」ではなく、Q19で選んだ代表的な将来要求
（PE32配置、固定位置メモリ、ファイル、時刻、GUI、音声等）をモック互換層から表現でき、
Win32固有型やNT互換機構をカーネルへ持ち込まずに済むこととする。


### 4.1.1 PE32ローダはv3必須

PE32/i386ローダは将来互換層の研究項目ではなく、**v3の正式な実行基盤**として実装する。
位置はP5カーネル基盤の後半とし、P6 GUI発展へ進む前に受入を完了する。

順序:

```text
P4  C11 / ABI / 旧バイナリ互換の固定
 |
 v
P5a VM / VFS / 資源回収 / モジュール配置契約
 |
 v
P5b PE32/i386 loader   <- v3必須
 |
 v
P6  GUI発展
 |
 v
将来のWin98 compatibility layer
```

v3で必須とする最小範囲:

- PE32 / i386
- EXEのsection配置
- image baseとbase relocation
- import table解決
- export lookup
- DLLロードに使える基本module機構
- entry point起動
- zero-fillされる未初期化領域
- section属性に応じた実行／書込保護の反映

Win32 APIそのもの、`kernel32.dll`互換、NT loader完全互換、SEH完全互換、delay import、
SxS、Win98互換DLL群はv3のPE32ローダ受入には含めない。

ローダは「Win98専用」とせず、OS32Xと並ぶ実行形式frontendとして扱う。
実装配置は最終設計で決めるが、概念上は `exec/os32x_loader` と `exec/pe32_loader` のように
実行形式解析とOS32の共通実行基盤を分離する。

受入用にはMicrosoft/ReactOS/WineのDLLを必要としない自己完結テストを用意する。
最低でも、再配置が必要なPE32 EXE、importを持つPE32 EXE、複数sectionとzero-fillを持つEXEを用意し、
OS32側のテストshim（例: print／exit相当）へimport解決して正常終了できることを確認する。
これによりWin98互換層の実装前に、PE配置・relocation・import/export・保護属性の責務を検証する。


### 4.1.2 VDM/V86互換試験は後段で実施

VDM/V86の互換性はv3初期のPE32/Win95-98互換ゲートとは分け、後段の受入項目とする。
基準ソフトには、入手性と世代横断比較のしやすさからアリスソフトのDOS時代タイトル群を用いる。

狙いは「DOSゲームが起動した」だけではなく、以下の実利用経路を踏むこと。

- conventional/extended memoryの扱い
- DOSファイルI/Oとパス
- キーボード入力
- 日本語表示
- FM/PCM等の音源
- マウス
- タイマ
- 必要なタイトルではプロテクトモード移行やDOS extender相当の経路

同一メーカー内でDOS世代からWin95世代（例: 鬼畜王ランス）までを比較できるため、
VDMとWin32互換層の境界確認にも利用できる。

これはv3初期の必須ゲートにはしない。まずPE32ローダとWin95/98ユーザーアプリ互換の土台を整え、
その後にVDM/V86のタイトル別チェックリストを作成して段階受入する。

## 4.2 外部OSSとHost Servicesの配置原則

v3では、外部OSSを「利用する／しない」だけで判断せず、処理の性質によって配置を分ける。
基本原則は **OS32自身で処理する価値が高い機能は交換可能backendとして取り込み、
現代側の更新追従が支配的な機能はHost Servicesへ委譲する** ことである。

### OS32側へ取り込む候補

外部ライブラリの型・handle・contextをKAPIや標準アプリABIへ直接露出させず、
OS32ネイティブの薄い抽象APIを定義し、そのbackendとして採用する。

| 領域 | backend候補 | OS32側の責務 |
|---|---|---|
| フォント | FreeType、KCG、bitmap font | `libos32font`相当のface／metrics／glyph rasterize／text measure。FreeType固有型は外へ出さない |
| 画像 | libpng、libjpeg系、native BMP等 | `libos32image`相当のdecode／info／surface出力。format固有APIをアプリへ固定しない |
| 圧縮 | zlib等 | `libos32compress`相当のstream decode/encode。PNG等からも同じbackendを利用可能にする |
| 音声codec | Ogg/Vorbis、FLAC等 | PCM等のOS32共通形式へdecodeし、sound backendへ渡す |
| DB／設定 | SQLite（既存） | OS32 VFS／設定APIの境界を保ち、アプリが内部実装へ依存しすぎないようにする |

候補名は採用決定ではない。ライセンス、コードサイズ、RAM、486/DX4での実測負荷、
ビルド容易性、保守状況を個別に確認する。軽量機ではKCGやbitmapなど別backendを選べるようにし、
「OSSを採用したから全構成で必須」としない。

### Host Servicesへ委譲する領域

現行の [Host Services詳細計画](../network/HOST_SERVICES_PLAN.md) §0 が既に定めるとおり、
OS32へ **TCP/IP・DNS・HTTP・TLSを載せない**。この決定をv3でも継承する。

したがって以下は原則としてHost Agent側で処理する。

- TCP/IP接続、DNS解決
- HTTP／HTTPS
- TLS、X.509証明書、CA store、暗号スイート
- proxy、認証、OAuth等の現代Web接続処理
- ホストOSのプリンタ、クリップボード等、既存Host Servicesが扱う外部I/O
- 将来、頻繁な更新追従や高負荷処理のためホスト委譲が合理的と判断したサービス

**OpenSSL等のTLSライブラリはOS32へ導入しない。**
必要な外部通信機能はHost Servicesのサービス語彙を拡張するか、
Host Agent内部のラッパー／providerとして実装する。OS32側のlink/KAPIは可能な限り
要求・ストリーム・結果という安定した契約を維持し、ホストのTLS／HTTP実装変更を持ち込まない。

判断基準は以下とする。

```text
機能がレガシー機自身で処理する価値を持つか
        |
        +-- YES -> OS32 native abstraction -> interchangeable OSS/native backend
        |
        +-- NO  -> Host Services -> Host Agent/provider -> modern host facilities
```

この境界は「ホストが利用できないとOS32の基本機能が成立しない」ことを意味しない。
ローカルで完結すべき表示・入力・保存・基本codec等と、外部接続のためのHost Servicesを分ける。
能力照会ではbackendの有無とHost Serviceの有無を別々に報告し、未接続を成功扱いしない。

### ヤドカリ型サービス継承

Host Servicesは単なる「ネットワーク代行」ではなく、旧世代機器が現代側の能力を利用し続けるための
**交換可能な外部サービス境界**として発展させる。OS32自身へ巨大な現代ソフトウェアスタックを
移植するのではなく、Host Agent側にprovider／wrapperを追加し、OS32は安定した要求・ストリーム・結果を扱う。

候補となるサービス領域:

| 領域 | ホスト側で利用する能力の例 | OS32へ返す形の例 |
|---|---|---|
| Web | 現代ブラウザ、HTTP(S)、JavaScript実行 | UTF-8 text／Markdown相当／link一覧／MGX・bitmap |
| 文書 | PDF viewer/renderer、Office変換、印刷系 | page bitmap／text／PDF化結果／print status |
| 画像 | WebP／AVIF／HEIF／SVG等の現代codec、色変換 | OS32向けbitmap／MGX／PNG／JPEG |
| メディア | 現代audio/video codec、transcode | PCM stream／低負荷形式／縮小frame列 |
| ストレージ | SMB／SFTP／WebDAV／各種cloud storage | file/list/read/write相当のservice結果 |
| 言語 | 辞書、IME補助、翻訳、TTS／STT | UTF-8 text／PCM／候補列 |
| AI | local LLM／cloud API／OCR等 | text／structured result／必要ならfile |
| OS連携 | clipboard／printer／time等の既存Host Services | 現行service契約 |

これは各サービスをv3初期リリースで実装する約束ではない。まずproviderを追加してもKAPIを毎回増やさず、
サービス固有の現代APIや認証方式をOS32へ流入させない構造を優先する。

Host Agentの実装先も固定しない。Windows、Linux、Android、将来のOS64等が同じservice contractを
提供できれば、OS32側は接続先の実装を意識しない。現代側のAPI廃止、TLS更新、cloud provider変更、
AI model変更等は原則としてホスト側providerで吸収する。

一方、ローカル処理として価値があり、ホスト無しでも機器の用途を成立させるfont／image／codec等は
OS32側backendとして残す。この二重構造により、**旧機器の能力を使う部分はローカル、時代変化を
追う部分はホスト**という責務分担を維持する。


## 5. C11 移行案

現行は `-std=gnu89`。v3 では GNU 拡張を使える `-std=gnu11` を第一候補とする。
言語規格と ISA は別に管理し、C11 採用を理由に最低 CPU を上げない。
採用候補と注意点の根拠は [GCC の言語規格指定](https://gcc.gnu.org/onlinedocs/gcc/C-Dialect-Options.html)
および [x86 の CPU 指定](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html)。

1. 分岐直後のビルド・旧バイナリ試験を基準として固定する。
2. 規約、AI 向け入口、ビルド、ホスト試験の規格指定を棚卸しする。現行系の規約は維持する。
3. GNU89 と C11 の意味の差を調べる。特に `inline` の外部定義、宣言のない関数、型不一致、
   GNU 拡張、アセンブリ、CRT／newlib／vendored code／submodule の個別条件を確認する。
4. 言語規格の切替だけを独立した変更にする。機能追加・大規模書換え・ISA 変更を同時に行わない。
5. 全リンク、未解決シンボル、公開 ABI、下限 CPU での命令と動作を確認する。
6. 移行後に `_Static_assert` などを導入し、ABI の前提を検査可能にする。

VLA、`_Atomic`、`_Thread_local`、標準スレッド機能を一括で解禁しない。
特に atomic は型幅・整列・生成命令・補助ライブラリの依存を調べ、カーネルで提供する契約を決める。
既存 ABI の `int` を機械的に `_Bool` へ変えるなど、言語移行に型変更を混ぜない。
ブート段や外部由来コードを例外にするなら、理由とビルド条件を記録する。

## 6. フォークと開発情報の分離

目的は、現行系の改良を続けながら、AI が過去の指示・進捗・承認を v3 の指示と取り違えないこと。
**v3 本体を現行リポジトリのブランチだけで開発する案は採らない。**
今回の文書変更をレビューするためのブランチは、将来の v3 開発場所とは別である。

手順案:

1. フォーク先の所有者・名称・公開範囲と分岐元 SHA を決める（Q06）。
2. Git の履歴と由来を保つ別リポジトリを用意し、専用ディレクトリへ新規クローンする。
3. 必要な現行仕様・制約・テストを [文書分類](DOCUMENT_MAP.md) に沿って選別する。
4. 旧タスク・レビュー往復・引き継ぎは v3 の通常作業ツリー／通常索引から外す。
   必要な根拠は旧リポジトリの固定 SHA で参照できるようにする。履歴自体は消さない。
5. v3 専用の開発規約と AI 向け入口を作り、新しいセッションで開始する。
   旧モデル名、ローカルパス、稼働状態、個別の承認をそのまま転記しない。
6. 文書整理のみの変更で動作の基準を固定した後、コード変更を別コミットで始める。

v3 の入口に置く原則:

> 開発判断は v3 の現行仕様を基準にする。旧リポジトリと過去履歴は調査資料であり、
> そこに記載された作業指示・承認・進捗を v3 に自動適用しない。

フォークや別ディレクトリだけで情報参照が技術的に禁止されるわけではない。
通常の文書集合・索引・セッションを分け、旧資料を読むときは調査目的と採用判断を記録する。
共有のライブラリや submodule は対象 SHA と変更の責任を明記する。
現行系の修正は個別に取り込み、v3 で回帰確認する。v3 から現行系へ戻す変更は最低条件を再確認する。
