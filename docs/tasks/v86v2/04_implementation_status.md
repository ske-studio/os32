## 1. 現在地

**実ディスクイメージの IPL を V86 で起動し、ゲストが `INT 1Bh` で本体を
最後まで読み込むところまで、実機で動作している。**
Ys I は IPL 実行 → 15 回の BIOS コール (失敗 0) → 本体ロード完了まで到達し、
**スレーブ PIC のポーリングで止まっている** (§7-1)。

| 機構 | 状態 | 検証 |
|---|---|---|
| TSS + I/O 許可ビットマップ | ✅ | `ltr` 成功を BUSY ビットで確認 |
| GDT 4 エントリ化 | ✅ | `gdtr_limit=31` |
| V86 モード遷移 (`iretd`) | ✅ | ゲストが 16bit コードを実行 |
| `#GP` の V86 分岐と復帰 | ✅ | ゲストが継続できる |
| バッキング RAM + VRAM 直マップ | ✅ | teardown 後も OS32 正常 |
| I/O 選択的パススルー | ✅ | 許可 4 回 / 拒否 2 回 → トラップ 2 回のみ |
| IN/OUT デコーダ | ✅ | IP が正しく進みゲストが継続 |
| **割り込み反射 (IRQ→ゲスト ISR)** | ✅ | 反射数とゲスト側カウンタが完全一致 |
| IRQ12 (サウンドボード) 経路 | ✅ | IDT[0x2C] = `irq_stub_12` |
| セッションタイムアウト | ✅ | 30 秒 (タイマ反射経路で計測) |
| **#GP 回数ウォッチドッグ** | ✅ | ゲストが `CLI` したまま暴走しても必ず戻る (§4-10) |
| **シェルからの起動 (`v86 -t`)** | ✅ | KAPI v36。4 回連続実行で安定 |
| **BIOS コールの HLE (`INT n`)** | ✅ | ゲストが `AH`/`CF` の書き換えを受け取れる |
| 実機 IVT / BDA の引き継ぎ | ✅ | HLE しないコールは実 BIOS ROM が処理する |
| **INT 1Bh SENSE (AH&0x0F=04h)** | ✅ | ゲストが装置ありと判定する |
| **INT 1Bh READ DATA (06h)** | ✅ | `v86 -d <image>` で直接読みとバイト一致 (KAPI v37) |
| 混在セクタ長への追従 | ✅ | `Ys.D88` の track0=256B×16 / 以降 1024B×5 を両方読める (§4-12) |
| **IPL ブート (`v86 -b`)** | ✅ | KAPI v38。IPL が動き `CS=0x0060` へ遷移した |
| **物理位置と論理 ID の分離** | ✅ | SEEK の CL+DH を記憶して ID 照合と分ける (§4-13) |
| **INT 1Bh 呼び出しログ** | ✅ | `v86_disklog` 32 エントリ。呼び出し列をホストから復元できる |
| **`#GP` 以外の V86 例外の捕捉** | ✅ | #DE/#DB/#UD/#PF に V86 分岐 (§4-14) |

未着手: **PIC/PIT の実仮想化 (次のブロッカー)**、WRITE/VERIFY、
キーボード入力経路 (§7)。

## 2. ファイル構成

```
kernel/
  tss.c/h          TSS (104B) + I/O 許可ビットマップ (8KB)
  gdt.c            GDT 4 エントリ化と TSS ディスクリプタ
  v86.c/h          #GP 一次ハンドラ、IN/OUT デコーダ、割り込み反射、
                   セッション管理 (setjmp/longjmp)、スモークテスト
  v86_entry.asm    iretd による V86 遷移、脱出口
  v86_mem.c/h      バッキング RAM 確保とアドレス空間の張り替え
  v86_io.c/h       I/O ポリシー (許可リスト) とポートディスパッチ
  v86_bios.c/h     BIOS コールの HLE、実機 IVT/BDA の退避と引き継ぎ、
                   INT 1Bh (SENSE / SEEK / READ DATA) と loop_dev への橋渡し、
                   呼び出しログ (v86_disklog)
  v86_test16.asm      ゲスト側スモークテストの正本 (NASM)
  v86_test16_disk.asm ゲスト側ディスクテストの正本 (NASM)
  isr_stub.asm     #GP/#DE/#DB/#UD/#PF の V86 分岐、RESTORE_KSEG、
                   V86_REFLECT、irq_stub_12
  idt.c            #DB (vec 1) と IRQ12 (vec 0x2C) の登録
  paging.c/h       PTE_USER の PDE 伝播、paging_pde_clear_user()
```

**カーネルに置いたのは特権命令の発行・例外の一次受け・I/O の一次デコード・
ページテーブル操作・モード遷移だけ**。BIOS HLE やセッション管理の高位ロジックは
ユーザ空間に寄せる方針を維持している（前回は 12,300 行がカーネルに積み上がった）。

## 3. 動作の流れ

```
v86_run(ctx)
  ├ exec_setjmp        脱出地点を記録
  ├ irq_enable(12)     サウンドボード IRQ を開ける
  └ v86_enter(ctx)     ← v86_entry.asm
       ├ TSS.ESP0 = 現在の ESP
       └ iretd (EFLAGS.VM=1, IOPL=3)  → ゲスト実行開始

  ゲスト実行中:
    許可ポートの IN/OUT ......... トラップしない (IOPM で素通し)
    VRAM 書き込み ............... トラップしない (直マップ)
    拒否ポートの IN/OUT ......... #GP → isr_stub_13 → v86_gp_handler
                                   → デコード → v86_io_in/out → IP を進めて復帰
    INT n ....................... #GP (IDT ゲートの DPL チェック)
                                   → HLE 対象なら v86_bios_dispatch で
                                     レジスタと CF を書いて IP を進める
                                   → 対象外なら v86_inject_int でゲストの
                                     IVT (多くは BIOS ROM) へ流す
    HLT ......................... #GP → セッション終了
    実 IRQ ...................... irq_stub_N → OS32 の処理 → V86_REFLECT
                                   → v86_reflect_irq → ゲスト ISR へ

  セッション終了:
    v86_exit_to_kernel → v86_longjmp_out → exec_longjmp
      → v86_run の setjmp 地点へ復帰 → irq_disable(12) → ESP0 復元
```

### 3-1. ディスクイメージからのブート (`v86 -b <image>`)

```
v86_boot(path)
  ├ loop_dev_attach(path, slot 0)     D88/FDI/HDI/RAW は loop_dev が判別する
  ├ v86_mem_setup()                   バッキング RAM を張る
  ├ IPL を C=0 H=0 R=1 から読む
  │    → 0x1FC00 (V86_IPL_SEG:0000) へ配置           ← PC-98 の IPL 規約
  ├ CS:IP = 1FC0:0000 / SS:SP = 0000:0290
  └ セッション開始 (以降は §3 と同じ)

  ゲストは INT 1Bh で次段を読み、そこへ far jump する。
  Ys I では実測で CS=0x0060 へ遷移することを確認した。
```

失敗時の戻り値は `-1` 画像なし/attach 失敗、`-2` メモリ不足、
`-3` IPL (C0/H0/S1) が読めない。

## 4. 【重要】守るべき不変条件

実装中に実際に踏んで、原因特定に時間がかかったものを残す。
**どれも破ると「原因不明のトリプルフォルト」になる。**

### 4-1. カーネルスタックは絶対にリマップしない

`0x90000-0x9FFFF` は V86 から `#GP` が入ったときに CPU がフレームを積む先。
実行中に張り替えたらその瞬間に全てが壊れる。
バッキング RAM のリマップ範囲を `0x00000-0x8EFFF` に切っているのはこのため
（ゲストから見える連続 RAM は 572KB になる）。

### 4-2. カーネル帯に `PTE_USER` を付けない

前回プロジェクトはトリプルフォルトの回避策としてカーネル帯に `PTE_USER` を
付け、その結果 V86 がカーネルメモリを実行できるようになり、それを
「エミュレータが U/S を無視している」と誤診した。
そこから 0x110000 スライドと A20 のリバート 4 連発に繋がっている。
→ [02_np21w_paging_analysis.md](02_np21w_paging_analysis.md)

### 4-3. USER は PDE と PTE の両方に要る

i386 の実効権限は **PDE と PTE の論理積**。PTE だけ USER にしてもユーザ
アクセスは拒否される。`paging_set_page()` が `PTE_USER` を PDE に伝播させる
ようにしてある。戻すときは `paging_pde_clear_user()`。

### 4-4. 全ての例外・IRQ スタブでセグメントを復元する

V86 → Ring0 の遷移で CPU は DS/ES/FS/GS を null セレクタにクリアする。
C ハンドラは DS を前提に動くので、復元前に呼ぶと即 `#GP`。しかもその `#GP`
ハンドラも DS=0 のまま C を呼ぶため**例外が無限再帰**し、カーネルスタック
64KB を食い潰してガードページに当たり `#DF` → トリプルフォルトになる。

**一次原因が完全に隠れる**のが最悪で、実際 Phase 1 の初回検証で
「#PF が起きていた」という事実がトリプルフォルトの裏に埋もれた。
`isr_stub.asm` の `RESTORE_KSEG` マクロを必ず通すこと。

### 4-5. IRQ フレームは `#GP` フレームと 1 ワードずれる

ハードウェア割り込みはエラーコードを積まない。取り違えると EFLAGS の
つもりで CS を読むことになり、**症状が出るのは注入した後**なので追いにくい。
`V86F_*`（#GP 用）と `V86I_*`（IRQ 用）を別定義にしてある。

### 4-6. PC-98 の PIT と CRTC は奇数/偶数で交互

PIT が `0x71/0x73/0x75/0x77`（奇数）、CRTC が `0x70-0x7A`（偶数）。
I/O 許可ビットマップを範囲でまとめて開けると、OS32 の 100Hz タイマを
ゲストに壊される。許可リストは `step=2` で偶数だけ開けている。

### 4-7. `INT n` は IOPL に関係なく IDT を引く

**IOPL=3 にしても `INT n` は素通しにならない。**
V86 の `INT n` はプロテクトモードの IDT を引く仕様で、OS32 のゲートは
DPL=0 / ゲストは CPL=3 のため「softint かつ `gate.DPL < CPL`」の規則で
必ず `#GP` になる。

設計当初これを「IOPL=3 なら素通し」と誤解し、IVT を自前スタブに向けて
スタブ内のトラップ命令で `#GP` を誘発する方式を実装してしまった。
実機で動かして初めて誤りに気づき、トランポリンを全廃して
`#GP` ハンドラで `CD ib` を直接デコードする形に作り直している。

**結果的にはこちらの方が簡単**なので実害は無かったが、
「IOPL=3 が消してくれるのは `CLI`/`STI`/`PUSHF`/`POPF`/`IRET` であって
`INT n` ではない」は憶えておくこと。

> `INT` は配送前に落ちているので**ゲストスタックには何も積まれていない**。
> BIOS の戻り値 (CF) はスタックではなくフレームの EFLAGS に書く。

### 4-8. セッション終了時に EFLAGS を復元する

セッションから抜けるのは `#GP` ハンドラからの `longjmp` なので、戻ってきた
時点の EFLAGS は「例外に入った直後の状態」になっている。

- **IF は割り込みゲートが自動でクリアしている**
- **IOPL は V86 ゲストの値 (3) がそのまま残る**

`longjmp` は EFLAGS を復元しない。直さずに返すとカーネルが**割り込み禁止の
まま動き続ける**。実際にこれを踏み、`v86 -t` の出力は正常に出たのに
シェルがタイマ待ちループから二度と抜けなくなった。
`v86_run()` が前後で `pushfl`/`popfl` して戻している。

> 症状が「コマンドは成功したのにその後シェルが固まる」なので、V86 自体は
> 正しく動いているように見えてしまう。`emu_regs` の `eflags` で IF を見るのが早い。

### 4-9. セッションは `pgalloc_init()` より後

バッキング RAM を `pgalloc_alloc_n()` から取るため。
初回はこれを踏んで `v86_mem_setup()` が `-2` を返していた。

### 4-10. ウォッチドッグは時間ではなく `#GP` 回数で持つ

タイマ由来のタイムアウト (§1 の 30 秒) は**ゲストが `STI` していることが前提**。
IOPL=3 ではゲストの `CLI` が実 IF を落とすので、`CLI` したまま回り続ける
ゲストには一切効かない。実際、最初のブート試行でセッションが止まらなくなり
**エミュレータのリセットが必要になった**。

`V86_GP_LIMIT` (現在 **50,000**) で `#GP` の総数に上限を置いてある。
値の決め方に注意が要る — 1 回の `#GP` が拒否ポートの読みだけなら数マイクロ秒
だが、`INT 1Bh` のように実ディスク I/O を伴うと数ミリ秒かかる。
最初 1,000,000 にしたところ**何分経っても帰ってこなかった**。
「必ず数十秒で戻る」値にしておくこと。

### 4-11. 診断用の変数を `static` にしない

`#GP` 発生地点などの診断値はカーネル内グローバル (`v86_gp_cs` / `gp_ip` /
`gp_fl` / `gp_n` など) にして `kernel.map` に載せること。
`static` にすると `emu_read_mem addr=<symbol>` で引けず、
**セッションが走っている最中に外から覗く**ことができなくなる。
ブート中の停止位置を突き止められたのはこれがあったから。

### 4-12. セクタ長はゲストの `CH` に従う (イメージの既定値ではない)

D88 は**トラックごとにセクタ長が違ってよい**。`Ys.D88` は
track0 が 256B×16、以降が 1024B×5 という構成になっている。

当初「ゲストの `CH` が `loop_dev` の bps と一致しなければ拒否」という
実装にしていたため、IPL は読めるのにその先で全滅した。
**`CH` (=N コード) をそのまま信じ、カーネル側の固定バウンスバッファ
(`static u8 secbuf[1024]`) 経由で転送する**のが正しい。

ただし**セクタ側の実長との一致は必ず見ること** (§4-13 の 2)。

### 4-13. 物理トラック位置と論理セクタ ID は別物

µPD765A は「いまどの物理トラックに居るか」をドライブ側で持ち、
READ DATA の C/H/R/N は**そのトラック上で照合する ID**でしかない。
両者が一致している必要はどこにもない。

`Ys.D88` は 155 トラック全部でずれている (特定セクタだけのコピープロテクト
ではない)。詳細は [05 §3.5](05_disk_bios_plan.md)。守るべき点は 3 つ:

1. **物理位置は SEEK の `CL` と `DH` の両方で決まる。**
   READ の `DH` を物理ヘッドに使うと、Ys の 3 番目のロードが物理トラック 0 を
   見に行って空振りする
2. **`N` も照合する。** ID だけ見て 256B セクタを N=3 の読みに返すと、
   ロード先の 3/4 が未初期化のまま「成功」が返り、ゲストがそこへ飛んで `#UD`。
   **見つからないなら失敗を返すほうがゲストは正しく振る舞える**
3. **`DH` を 1 ビットにマスクしない。** 同じ ID の物理トラックが 2 本あるので、
   マスクすると別トラックが「それらしく」読めて中身だけ違う結果になる。
   マスクしなければ読みが失敗し、ゲストが自分で `DH=0` に直して読み直す

`loop_dev_read_chs()` は D88 では使えない (物理=論理を仮定し、かつ読み出し長を
イメージ全体の `bps` — トラック 0 の値 — で頭打ちにする)。
`loop_dev_seek_d88()` を直接使うこと。

### 4-14. `#GP` 以外の V86 例外も分岐させる

`#GP` にだけ V86 分岐を持たせていた頃、ゲストが不正命令を実行すると
OS32 の汎用例外ハンドラが **「カーネルが EIP=0x120 で落ちた」** と表示して
シェルへ戻していた。`[OUT OF CODE!]` と出るのでカーネルのバグにしか見えない。

見分けるのは `EFLAGS.VM` ひとつ。例外ダンプのスタックに
`EFLAGS=0x00023202` が積まれているのに気づいて初めて V86 由来と分かった。

`#DE(0)` / `#DB(1)` / `#UD(6)` / `#PF(14)` に V86 分岐を入れ、
`v86_fault_handler()` でベクタ・CS:IP・そこのバイト列を残してから
セッションを畳むようにしてある。

## 5. 検証方法

### 5-1. スモークテスト

シェルから `v86 -t` で実行する (KAPI v36 `v86_selftest`)。
結果はカーネル側のグローバルにも残るので、`kernel.map` 経由で
ホストから直接読める。

```bash
# ゲスト側から
v86 -t

# ホスト側から (MCP)
emu_read_mem addr=v86_smoke_result len=4
```

| 変数 | 期待値 | 意味 |
|---|---|---|
| `v86_smoke_result` | `0` | 総合判定 |
| `v86_smoke_magic` | `0x1234` | ゲストがメモリに書けた |
| `v86_smoke_magic2` | `0x5678` | `#GP` 後もゲストが継続できた |
| `v86_smoke_reason` | `1` (HLT) | 想定どおりの終了 |
| `v86_smoke_gp` | `4` | I/O 2 回 + `INT` 1 回 + HLT 1 回 |
| `v86_smoke_iotrap` | `2` | **拒否ポートだけがトラップ = パススルーが効いている** |
| `v86_smoke_irq` | `3` | カーネルが反射した IRQ 数 |
| `v86_smoke_gcnt` | `3` | **ゲスト自身の ISR が数えた回数** |
| `v86_smoke_bcnt` | `1` | カーネルが処理した BIOS コール数 |
| `v86_smoke_bios` | `0xB105` | **ゲストが `AH=0` かつ `CF=0` を確認した印** |

`iotrap == 2` / `irq == gcnt` / `bios == 0xB105` の 3 つが機構の健全性を端的に示す。

失敗したときのために、最後に `#GP` した地点も残してある。
これが無いと「どの命令で落ちたか」が分からず手が止まる
(実際 §4-7 の `INT n` の件はこれで特定した)。

| 変数 | 意味 |
|---|---|
| `v86_smoke_gpcs` / `gpip` | 最後に `#GP` したゲストの CS:IP |
| `v86_smoke_gpop` | 同 先頭 4 バイト (オペコード) |
| `v86_smoke_gpfl` | 同 ゲスト EFLAGS (IOPL / VM / IF の確認用) |

ゲスト側コードの正本は `kernel/v86_test16.asm`。変更したら
`nasm -f bin kernel/v86_test16.asm -o /tmp/t.bin` で再生成して
`kernel/v86.c` の配列に反映する。

### 5-1b. ディスクテスト (`v86 -d <image>`)

ゲストが `INT 1Bh` READ DATA で C0/H0/S1 を読み、その中身を
カーネルが `loop_dev` で直読みした結果と突き合わせる (KAPI v37)。
**BIOS HLE とディスク経路だけを切り出して検証する**ためのもので、
ブートが失敗したときに「読めていないのか、読めた上で止まっているのか」を
一発で分けられる。

| 変数 | 意味 |
|---|---|
| `v86_disk_marker` | ゲストが READ を成功と判定した印 |
| `v86_disk_cmp` | 直読みと一致したバイト数 |
| `v86_disk_reason` | セッション終了理由 |

ゲスト側コードの正本は `kernel/v86_test16_disk.asm`。

### 5-1c. ブート (`v86 -b <image>`)

セッション中の様子はカーネルグローバルに残るので、
**走らせたまま**ホストから読める (§4-11)。

| 変数 | 意味 |
|---|---|
| `v86_boot_gp` | `#GP` 総数 (ウォッチドッグの分母) |
| `v86_boot_bios` | BIOS コール数 |
| `v86_boot_iotrap` / `v86_boot_ioport` | I/O トラップ数 / 最後に触ったポート |
| `v86_boot_gpcs` / `gpip` / `gpop` | 最後の `#GP` の CS:IP とそこのバイト列 |

`gpcs`/`gpip`/`gpop` の 3 つで「いまゲストがどの命令で足踏みしているか」が
そのまま出る。PIC ポーリングは `CS=0160 IP=0DF7` の
`e608 e408` (= `OUT 08,AL` / `IN AL,08`) で特定した。

`#GP` 以外の例外は別枠 (§4-14):

| 変数 | 意味 |
|---|---|
| `v86_flt_vec` | 例外ベクタ (6 = `#UD` など) |
| `v86_flt_cs` / `ip` | ゲストの CS:IP |
| `v86_flt_op` | そこの先頭 4 バイト |
| `v86_flt_fl` | ゲスト EFLAGS |
| `v86_flt_n` | 発生回数 |

### 5-1d. INT 1Bh 呼び出しログ

```bash
emu_read_mem addr=v86_disklog len=1024
```

32 エントリ × 8 ワードのリング。1 コールぶんが
`AX / CX / DX / BX / ES:BP / 呼び出し時の物理シリンダ / 転送バイト数 / 結果`。

**カウンタだけでは足りなかった。** 「何回失敗したか」は分かっても
「どういう順で何を要求されたか」が分からず推測が始まる。§4-13 の物理位置
モデルは、このログを並べた瞬間に確定した。デコードは
[05 §4-2](05_disk_bios_plan.md) に置いてある。

### 5-2. 失敗したときの追い方

Phase 0-0 で入れたフォルト捕捉が効く。トリプルフォルトでも
**モーダルは出ず、フォルト地点で凍結**したままレジスタとメモリを読める。

```bash
emu_status        # fault_generation が 0 以外なら発生している
emu_fault         # 理由 + 全レジスタダンプ + CS:EIP (シンボル注釈付き)
emu_regs          # eip_sym / prev_eip_sym でどのスタブか分かる
emu_read_mem      # ESP からスタックを遡って再帰の有無を見る
emu_resume        # 再開 (= リセットして再起動)
```

Phase 1 の初回トリプルフォルトは、この 4 コールだけで
「`isr_stub_13+0x39` から `#DF` へ、`cr2` はスタックガード、
スタックに vector 13 のフレームが反復」まで見えて原因が確定した。

## 6. I/O ポリシー (実測ベース)

分類の根拠は [03_ys_profile.md](03_ys_profile.md)。**推測ではなく実測**。

| 分類 | ポート |
|---|---|
| **パススルー** | FM音源 `0x188-0x18F` / I/Oウェイト `0x5F` / テキストGDC・VSYNC `0x60-0x6E` / CRTC `0x70-0x7A`(偶数) / GRCG `0x7C,0x7E` / グラフィックGDC `0xA0-0xAE` / EGC `0x4A0-0x4AF` / ビープ `0x37` / カレンダ `0x20` |
| **仮想化** | マスタPIC `0x00,0x02` / スレーブPIC `0x08,0x0A` / PIT `0x71,0x77` / KBD `0x41,0x43` / FDC `0x90-0x94,0xBE` / リセット `0xF0` / A20 `0xF2` |
| **保護** | RS-232C `0x30-0x35` / HostDrv `0x7EC,0x7EE` |

VRAM (`0xA0000-0xBFFFF`, `0xE0000-0xE7FFF`) は実物理を直マップ。
描画は I/O ではなくメモリアクセスなので**トラップコストがゼロ**になる。
これが 386DX20 で成立する最大の理由。

ROM 帯 (`0xC0000-0xFFFFF`) は R/O + USER で**ゲストから実行可能**にしてある。
前回は ROM 実行を排除する「方法C」を実装した翌日に全撤回しているので、
同じ回り道はしない。

## 7. 残作業

### 7-1. いま止まっている場所 — スレーブ PIC のポーリング

ディスク経路が片付いた結果、ゲストは本体を最後まで読み込んで先へ進んだ。
次に当たったのはここ。

```
BIOS コール : 15 回 (すべて成功、失敗 0)
#GP         : 50,001 → V86_GP_LIMIT に到達して打ち切り
最後の #GP  : CS=0160 IP=0DF7   E6 08 E4 08  = OUT 08,AL / IN AL,08
I/O トラップ: 49,981 回 (ほぼ全部これ)
```

`0x08` は PC-98 のスレーブ PIC。現在の実装は「読み `0xFF` / 書き破棄」の
スタブなので、ゲストが待っている状態が永遠に来ない。→ §7-2 の 3。

### 7-3. OS32 側の別バグ (V86 とは独立)

**外部プログラムを 1 つでも実行すると PTE[0] が `0x001` → `0x000` になる**
(`cal` だけで再現する)。`paging.c` は NULL ガードを意図的に R/O
(Not-Present ではない) で維持しているはずで、`paging_set_not_present(0,...)`
の呼び出し元も見つかっていない。
V86 側は `v86_bios_save_real()` で自衛しているため当面ブロッカーではないが、
**別途調査が必要**。

## 8. 前回プロジェクトとの差分

| | 前回 (`archive/feat-vdm`) | 今回 (`feat/vdm-v2`) |
|---|---|---|
| 方式の根拠 | 設計判断 | **386DX20 実測** |
| IOPL | 0 (全命令トラップ) | **3** (#GP レート 5〜6 倍減) |
