## 1. 現在地

**16bit ゲストを V86 モードで実行し、I/O を選択的にパススルーし、実 IRQ を
ゲストの ISR に届けるところまでが実機で動作している。**

| 機構 | 状態 | 検証 |
|---|---|---|
| TSS + I/O 許可ビットマップ | ✅ | `ltr` 成功を BUSY ビットで確認 |
| GDT 4 エントリ化 | ✅ | `gdtr_limit=31` |
| V86 モード遷移 (`iretd`) | ✅ | ゲストが 16bit コードを実行 |
| `#GP` の V86 分岐と復帰 | ✅ | ゲストが継続できる |
| バッキング RAM + VRAM 直マップ | ✅ | teardown 後も OS32 正常 |
| I/O 選択的パススルー | ✅ | 許可 4 回 / 拒否 2 回 → トラップ 2 回のみ |
| IN/OUT デコーダ | ✅ | IP が正しく進みゲストが継続 |
| **割り込み反射 (IRQ→ゲスト ISR)** | ✅ | 反射数とゲスト側カウンタが完全一致 |
| IRQ12 (サウンドボード) 経路 | ✅ | IDT[0x2C] = `irq_stub_12` |
| セッションタイムアウト | ✅ | 30 秒 (タイマ反射経路で計測) |
| **シェルからの起動 (`v86 -t`)** | ✅ | KAPI v36。4 回連続実行で安定 |

未着手: ディスク BIOS (INT 1Bh)、PIC/PIT の実仮想化、
キーボード入力経路、暴走時の脱出手段 (§7)。

## 2. ファイル構成

```
kernel/
  tss.c/h          TSS (104B) + I/O 許可ビットマップ (8KB)
  gdt.c            GDT 4 エントリ化と TSS ディスクリプタ
  v86.c/h          #GP 一次ハンドラ、IN/OUT デコーダ、割り込み反射、
                   セッション管理 (setjmp/longjmp)、スモークテスト
  v86_entry.asm    iretd による V86 遷移、脱出口
  v86_mem.c/h      バッキング RAM 確保とアドレス空間の張り替え
  v86_io.c/h       I/O ポリシー (許可リスト) とポートディスパッチ
  v86_test16.asm   ゲスト側スモークテストの正本 (NASM)
  isr_stub.asm     #GP の V86 分岐、RESTORE_KSEG、V86_REFLECT、irq_stub_12
  idt.c            #DB (vec 1) と IRQ12 (vec 0x2C) の登録
  paging.c/h       PTE_USER の PDE 伝播、paging_pde_clear_user()
```

**カーネルに置いたのは特権命令の発行・例外の一次受け・I/O の一次デコード・
ページテーブル操作・モード遷移だけ**。BIOS HLE やセッション管理の高位ロジックは
ユーザ空間に寄せる方針を維持している（前回は 12,300 行がカーネルに積み上がった）。

## 3. 動作の流れ

```
v86_run(ctx)
  ├ exec_setjmp        脱出地点を記録
  ├ irq_enable(12)     サウンドボード IRQ を開ける
  └ v86_enter(ctx)     ← v86_entry.asm
       ├ TSS.ESP0 = 現在の ESP
       └ iretd (EFLAGS.VM=1, IOPL=3)  → ゲスト実行開始

  ゲスト実行中:
    許可ポートの IN/OUT ......... トラップしない (IOPM で素通し)
    VRAM 書き込み ............... トラップしない (直マップ)
    拒否ポートの IN/OUT ......... #GP → isr_stub_13 → v86_gp_handler
                                   → デコード → v86_io_in/out → IP を進めて復帰
    HLT ......................... #GP → セッション終了
    実 IRQ ...................... irq_stub_N → OS32 の処理 → V86_REFLECT
                                   → v86_reflect_irq → ゲスト ISR へ

  セッション終了:
    v86_exit_to_kernel → v86_longjmp_out → exec_longjmp
      → v86_run の setjmp 地点へ復帰 → irq_disable(12) → ESP0 復元
```

## 4. 【重要】守るべき不変条件

実装中に実際に踏んで、原因特定に時間がかかったものを残す。
**どれも破ると「原因不明のトリプルフォルト」になる。**

### 4-1. カーネルスタックは絶対にリマップしない

`0x90000-0x9FFFF` は V86 から `#GP` が入ったときに CPU がフレームを積む先。
実行中に張り替えたらその瞬間に全てが壊れる。
バッキング RAM のリマップ範囲を `0x00000-0x8EFFF` に切っているのはこのため
（ゲストから見える連続 RAM は 572KB になる）。

### 4-2. カーネル帯に `PTE_USER` を付けない

前回プロジェクトはトリプルフォルトの回避策としてカーネル帯に `PTE_USER` を
付け、その結果 V86 がカーネルメモリを実行できるようになり、それを
「エミュレータが U/S を無視している」と誤診した。
そこから 0x110000 スライドと A20 のリバート 4 連発に繋がっている。
→ [02_np21w_paging_analysis.md](02_np21w_paging_analysis.md)

### 4-3. USER は PDE と PTE の両方に要る

i386 の実効権限は **PDE と PTE の論理積**。PTE だけ USER にしてもユーザ
アクセスは拒否される。`paging_set_page()` が `PTE_USER` を PDE に伝播させる
ようにしてある。戻すときは `paging_pde_clear_user()`。

### 4-4. 全ての例外・IRQ スタブでセグメントを復元する

V86 → Ring0 の遷移で CPU は DS/ES/FS/GS を null セレクタにクリアする。
C ハンドラは DS を前提に動くので、復元前に呼ぶと即 `#GP`。しかもその `#GP`
ハンドラも DS=0 のまま C を呼ぶため**例外が無限再帰**し、カーネルスタック
64KB を食い潰してガードページに当たり `#DF` → トリプルフォルトになる。

**一次原因が完全に隠れる**のが最悪で、実際 Phase 1 の初回検証で
「#PF が起きていた」という事実がトリプルフォルトの裏に埋もれた。
`isr_stub.asm` の `RESTORE_KSEG` マクロを必ず通すこと。

### 4-5. IRQ フレームは `#GP` フレームと 1 ワードずれる

ハードウェア割り込みはエラーコードを積まない。取り違えると EFLAGS の
つもりで CS を読むことになり、**症状が出るのは注入した後**なので追いにくい。
`V86F_*`（#GP 用）と `V86I_*`（IRQ 用）を別定義にしてある。

### 4-6. PC-98 の PIT と CRTC は奇数/偶数で交互

PIT が `0x71/0x73/0x75/0x77`（奇数）、CRTC が `0x70-0x7A`（偶数）。
I/O 許可ビットマップを範囲でまとめて開けると、OS32 の 100Hz タイマを
ゲストに壊される。許可リストは `step=2` で偶数だけ開けている。

### 4-7. セッション終了時に EFLAGS を復元する

セッションから抜けるのは `#GP` ハンドラからの `longjmp` なので、戻ってきた
時点の EFLAGS は「例外に入った直後の状態」になっている。

- **IF は割り込みゲートが自動でクリアしている**
- **IOPL は V86 ゲストの値 (3) がそのまま残る**

`longjmp` は EFLAGS を復元しない。直さずに返すとカーネルが**割り込み禁止の
まま動き続ける**。実際にこれを踏み、`v86 -t` の出力は正常に出たのに
シェルがタイマ待ちループから二度と抜けなくなった。
`v86_run()` が前後で `pushfl`/`popfl` して戻している。

> 症状が「コマンドは成功したのにその後シェルが固まる」なので、V86 自体は
> 正しく動いているように見えてしまう。`emu_regs` の `eflags` で IF を見るのが早い。

### 4-8. セッションは `pgalloc_init()` より後

バッキング RAM を `pgalloc_alloc_n()` から取るため。
初回はこれを踏んで `v86_mem_setup()` が `-2` を返していた。

## 5. 検証方法

### 5-1. スモークテスト

シェルから `v86 -t` で実行する (KAPI v36 `v86_selftest`)。
結果はカーネル側のグローバルにも残るので、`kernel.map` 経由で
ホストから直接読める。

```bash
# ゲスト側から
v86 -t

# ホスト側から (MCP)
emu_read_mem addr=v86_smoke_result len=4
```

| 変数 | 期待値 | 意味 |
|---|---|---|
| `v86_smoke_result` | `0` | 総合判定 |
| `v86_smoke_magic` | `0x1234` | ゲストがメモリに書けた |
| `v86_smoke_magic2` | `0x5678` | `#GP` 後もゲストが継続できた |
| `v86_smoke_reason` | `1` (HLT) | 想定どおりの終了 |
| `v86_smoke_gp` | `3` | I/O 2 回 + HLT 1 回 |
| `v86_smoke_iotrap` | `2` | **拒否ポートだけがトラップ = パススルーが効いている** |
| `v86_smoke_irq` | `3` | カーネルが反射した IRQ 数 |
| `v86_smoke_gcnt` | `3` | **ゲスト自身の ISR が数えた回数** |

`iotrap == 2` と `irq == gcnt` の 2 つが機構の健全性を端的に示す。

ゲスト側コードの正本は `kernel/v86_test16.asm`。変更したら
`nasm -f bin kernel/v86_test16.asm -o /tmp/t.bin` で再生成して
`kernel/v86.c` の配列に反映する。

### 5-2. 失敗したときの追い方

Phase 0-0 で入れたフォルト捕捉が効く。トリプルフォルトでも
**モーダルは出ず、フォルト地点で凍結**したままレジスタとメモリを読める。

```bash
emu_status        # fault_generation が 0 以外なら発生している
emu_fault         # 理由 + 全レジスタダンプ + CS:EIP (シンボル注釈付き)
emu_regs          # eip_sym / prev_eip_sym でどのスタブか分かる
emu_read_mem      # ESP からスタックを遡って再帰の有無を見る
emu_resume        # 再開 (= リセットして再起動)
```

Phase 1 の初回トリプルフォルトは、この 4 コールだけで
「`isr_stub_13+0x39` から `#DF` へ、`cr2` はスタックガード、
スタックに vector 13 のフレームが反復」まで見えて原因が確定した。

## 6. I/O ポリシー (実測ベース)

分類の根拠は [03_ys_profile.md](03_ys_profile.md)。**推測ではなく実測**。

| 分類 | ポート |
|---|---|
| **パススルー** | FM音源 `0x188-0x18F` / I/Oウェイト `0x5F` / テキストGDC・VSYNC `0x60-0x6E` / CRTC `0x70-0x7A`(偶数) / GRCG `0x7C,0x7E` / グラフィックGDC `0xA0-0xAE` / EGC `0x4A0-0x4AF` / ビープ `0x37` / カレンダ `0x20` |
| **仮想化** | マスタPIC `0x00,0x02` / スレーブPIC `0x08,0x0A` / PIT `0x71,0x77` / KBD `0x41,0x43` / FDC `0x90-0x94,0xBE` / リセット `0xF0` / A20 `0xF2` |
| **保護** | RS-232C `0x30-0x35` / HostDrv `0x7EC,0x7EE` |

VRAM (`0xA0000-0xBFFFF`, `0xE0000-0xE7FFF`) は実物理を直マップ。
描画は I/O ではなくメモリアクセスなので**トラップコストがゼロ**になる。
これが 386DX20 で成立する最大の理由。

ROM 帯 (`0xC0000-0xFFFFF`) は R/O + USER で**ゲストから実行可能**にしてある。
前回は ROM 実行を排除する「方法C」を実装した翌日に全撤回しているので、
同じ回り道はしない。

## 8. 前回プロジェクトとの差分

| | 前回 (`archive/feat-vdm`) | 今回 (`feat/vdm-v2`) |
|---|---|---|
| 方式の根拠 | 設計判断 | **386DX20 実測** |
| IOPL | 0 (全命令トラップ) | **3** (#GP レート 5〜6 倍減) |
| カーネル配置 | `0x110000` へスライド | **`0x100000` のまま** (スライドの根拠が消えた) |
| カーネル帯の `PTE_USER` | 付与 (回避策) | **付けない** |
| IRQ 注入 | IRQ0/1/2 のみ | **IRQ12 を含む** (FM の要) |
| 例外スタブのセグメント復元 | #GP の V86 経路のみ | **全スタブ** |
| フォルト時の観測 | モーダル + 再起動で証拠消失 | **フォルト地点で凍結して調査** |
| カーネル内の行数 | 12,300 行 | 約 800 行 (現時点) |
