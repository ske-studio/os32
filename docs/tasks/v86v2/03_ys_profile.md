## 1. 計測環境

OS32 は一切関与しない。**既存の `np21x64w.ini` は変更していない** — NP21/W は
コマンドライン引数で設定ファイルとディスクを差し替えられる (`np2arg.cpp:Parse()`)。

```bash
# HDD/SCSI/FDD を空にしたプロファイル専用 INI を用意 (aidebug=true は維持)
#   C:\Users\hight\Documents\np21w\ysprof.ini
np21x64w.exe C:\Users\hight\Documents\np21w\ysprof.ini C:\os32\Ys_FM.D88
```

- 拡張子 `.ini` の引数は設定ファイルとして解釈される (`-i<path>` も可)
- 拡張子がディスク系の引数は FDD 0-3 に順に挿入される (`diskdrv_readyfdd`)
- 設定の読み書き先も指定した INI に切り替わる (`ini.cpp:initgetfile()`) ので、
  終了時の書き戻しも本番の INI を汚さない

**起動確認**: タイトル画面 "Ancient Ys Vanished Omen" を表示。
`/api/status` は `protected_mode=0`（リアルモード）、`CS=0x0160`、
**`grph_disp=1`**（OS32 では 0）。

> 補足: 当初 `np21x64w.ini` の `FDD1FILE` に Ys を設定して再起動したが、
> HDD (`os32.nhd`) が先に起動してしまい Ys は立ち上がらなかった。
> Ys の D88 側は正常 — IPL は PC-98 標準の `MOV AX,0060` → `INT 1Bh`、
> media byte 0x20 = 2HD で IPL の DA/UA=0x90 (1MB FDD) と整合する。
> トラック 0/0 は 256B×16 セクタ、以降は **1024B×5 セクタ**という非標準
> フォーマットで、資料にある Ys のコピープロテクトと符合する。

## 3. 読み取れること

### 3.1 `INT n` がゼロ — ソフトウェア割り込みを一切使っていない

タイトル画面の間、Ys は BIOS を **INT 経由で一度も呼んでいない**。
ハードウェアを直接叩いている。DOS を通らない独自 IPL ブートゲームなので当然ではあるが、
**INT 命令のトラップコストはゼロ**ということ。

### 3.2 支配項は FM 音源 — しかもその 2/3 がステータスポーリング

0x0188 + 0x018A で **4,145 アクセス/s**、全 I/O の **74%**。
0x0188 の読みが 20,920 に対し書きが 10,460 で、ちょうど **書き 1 回あたり読み 2 回**。
OPN のレジスタ書き込み前に BUSY フラグが下りるのを待つ、定番のポーリングパターン。

**ここを #GP でトラップしたら 386DX20 では成立しない。**
逆に I/O permission bitmap で素通しにすればコストはゼロになる。

### 3.3 音楽はスレーブ PIC 側の IRQ で駆動されている

- `IRET` 319/s ≒ スレーブ PIC 読み 3,219 (=319/s)
- スレーブ PIC への書き 6,438 = 割り込み 1 回あたり 2 回 (EOI 等)
- マスタ PIC への書き 3,540 のうち約 3,219 はカスケード EOI、残り ~321 が別系統

つまり **約 320Hz の割り込みが スレーブ PIC (IRQ8-15) から入り続けている**。
PC-98 のサウンドボード (PC-9801-26K/86) の割り込みは既定で **IRQ12 = スレーブ側**。
FM ドライバがこの割り込みで演奏を進めていると考えるのが自然。

`CLI` 287/s ≒ `STI` 287/s ≒ 割り込み頻度と同じオーダーで、
割り込みハンドラ内のクリティカルセクションと整合する。

## 4. 【重要】Phase 3-1「Ys で FM が鳴らない」問題への示唆

前回、Ys は **FM 音源の「検出」には成功したが音が出なかった**。一方で単体の
FM テストプログラムでは鳴っていた。

本計測は、その差を説明する仮説を1つに絞り込む。

> **FM ドライバは スレーブ PIC 側の IRQ (約 320Hz) で演奏を駆動している。
> 前回の V86 実装が注入していたのは IRQ0 (タイマ) / IRQ1 (KBD) / IRQ2 (VSYNC) の
> 3 本だけで、サウンドボードの IRQ は注入対象に入っていなかった。**

これなら「OPN への書き込み自体は届く（＝音源は検出できる、単発の音は鳴る）が、
時間軸に沿って音符を進める割り込みが来ないので曲にならない」という観測と完全に一致する。

**検証方法**: V86 セッション中にスレーブ PIC の IMR とゲストの ISR 登録を観察し、
サウンドボード IRQ がゲストに配送されているかを直接確認する。
単体 FM テストが鳴ったのは、割り込み駆動ではなくポーリングやウェイトループで
書き込んでいたためと予想される（要確認）。

> ⚠️ これは**強い仮説であって確定ではない**。IRQ 番号の特定は
> ポート 0x0008 へのアクセスという状況証拠に基づく。次段で OCW2 の値または
> IMR の変化を直接観測して確定させる。

## 5. V86 コスト見積もり (386DX 20MHz)

`INT n` = 0 なので、IOPL の選択がそのまま効く。

| 構成 | トラップ源 | #GP レート |
|---|---|---:|
| **(a) IOPL=0・I/O 全仮想化**（前回の実装） | 命令 904 + I/O 5,579 | **6,483/s** |
| **(b) IOPL=0・FM と 0x5F をパススルー** | 命令 904 + I/O 1,340 | **2,244/s** |
| **(c) IOPL=3・FM と 0x5F をパススルー** | I/O 1,340 のみ | **1,340/s** |

(a) → (c) で **約 4.8 倍の削減**。

386DX 20MHz での #GP 1 回あたりのコストを、前回のような
1,000 行級の C ハンドラで 2,000 サイクル (=100µs) と見積もると:

| 構成 | オーバーヘッド |
|---|---:|
| (a) | 約 65% |
| (b) | 約 22% |
| (c) | **約 13%** |

ハンドラを軽量化して 600 サイクル (=30µs) まで詰められれば (c) は **約 4%**。

**結論の方向**: 「386DX20 で 286 相当」という要件に対し、
**(c) IOPL=3 + FM/GDC/GVRAM パススルー**なら十分に射程内。
逆に (a) は要件を満たせない。前回の実装が重かった理由がここにある。

### 残る最大のコスト源は PIC

(c) の 1,340/s はすべて PIC (0x0000 / 0x0008) である。OS32 が PIC を共有している以上
完全仮想化は外せないが、ここが唯一の最適化余地になる。

### IOPL=3 の代償

ゲストの `CLI` が実 IF を落とし、ホストの割り込みまで止まる。
Ys は `CLI` を 287/s 発行しており、対の `STI` も同数なので通常は即座に復帰するが、
**ゲストが `CLI` したまま暴走した場合の脱出手段**（NMI かウォッチドッグ）が必須。
Phase 1 で遷移機構と一緒に設計する。
