# 02: PC-9801 VRAMプレーン方式とパックトピクセル変換の設計

## 1. PC-9801 グラフィックVRAMの構造

PC-9801の16色グラフィックモードでは、1ピクセルの色(0-15)を **4枚のビットプレーン**
に分散して格納する。これはいわゆる **プレーナー方式** である。

### 1-1. プレーンアドレスとレイアウト

```text
プレーン0 (B/青):  0xA8000 - 0xAFFFF  (32,000 bytes)
プレーン1 (R/赤):  0xB0000 - 0xB7FFF  (32,000 bytes)
プレーン2 (G/緑):  0xB8000 - 0xBFFFF  (32,000 bytes)
プレーン3 (I/輝度): 0xE0000 - 0xE7FFF  (32,000 bytes)
```

各プレーンのサイズ: `640 / 8 × 400 = 80 × 400 = 32,000 bytes`

### 1-2. ピクセルとビットの対応

座標 (x, y) のピクセルに色 `c` (0-15) を設定する場合:

```text
バイトオフセット = y * 80 + (x / 8)
ビット位置       = 0x80 >> (x % 8)      /* MSBファースト */

for plane in [B, R, G, I]:
    if (c & (1 << plane)):
        plane[offset] |= bit             /* ビットセット */
    else:
        plane[offset] &= ~bit            /* ビットクリア */
```

**1ピクセル設定に4プレーン×2操作 (read-modify-write) = 最低8回のメモリアクセス。**

### 1-3. OS32のバックバッファ構造 (既存実装)

OS32 GFXサブシステムは拡張メモリ上にVRAMと同構造のバックバッファを持つ:

```c
/* gfx_core.c */
u8 *bb_b = (u8 *)MEM_GFX_BB_BASE;                   /* プレーン0 */
u8 *bb_r = (u8 *)(MEM_GFX_BB_BASE + GFX_PLANE_SZ);  /* プレーン1 */
u8 *bb_g = (u8 *)(MEM_GFX_BB_BASE + GFX_PLANE_SZ*2); /* プレーン2 */
u8 *bb_i = (u8 *)(MEM_GFX_BB_BASE + GFX_PLANE_SZ*3); /* プレーン3 */
```

描画 → バックバッファ(プレーナー) → `gfx_present()` で VRAM へ `rep movsw` 転送。

## 2. Pyxelとの根本的な違い

Pyxelは **パックトピクセル方式** を採用:

```text
Pyxel:   1バイト = 1ピクセル (値: 0-15)
         メモリ上: [px0][px1][px2][px3] ... (リニア配置)

PC-9801: 1バイト = 8ピクセル分の1ビット (× 4プレーン)
         メモリ上: Plane_B[byte0] Plane_R[byte0] Plane_G[byte0] Plane_I[byte0]
                   (4回のメモリアクセスで8ピクセルの1色分)
```

> **注意**: Pyxelのカラーインデックスは `u8` (0–255) だが、OS32 libpyxel では
> **16色固定** (0–15) として扱う。拡張パレットはサポートしない。

## 3. 変換方式の選択肢と評価

### 方式A: パックトピクセル中間バッファ方式

```text
[ゲームロジック] → [パックトバッファ 256×192] → [変換+スケーリング] → [プレーナーBB] → [VRAM]
```

- **利点**: Pyxel APIの移植が容易。`buffer[y * 256 + x] = color;` で直感的。
- **欠点**: 毎フレーム 256×192 = 49,152 ピクセルの変換処理が必要。

### 方式B: プレーナー直接描画方式

```text
[ゲームロジック] → [プレーナーBBの一部領域に直接描画] → [VRAM転送]
```

- **利点**: 変換オーバーヘッドなし。既存の `gfx_pixel()` / `gfx_fill_rect()` をそのまま利用。
- **欠点**: Pyxelの `blt` (スプライト転送) の実装が複雑。パックトデータからの変換は何処かで必要。

### 方式C: ハイブリッド方式 (推奨)

```text
[リソース変換ツール] → [プレーナー形式のバイナリ .os32res に事前変換]
[ゲームロジック] → [プレーナーBBに直接描画] → [VRAM転送]
                    └─ blt/bltm はプレーナーデータから直接転送
```

- イメージバンク・タイルマップは **ホスト側でプレーナー形式に事前変換**。
- ランタイムではプレーナー→プレーナーの `rep movsw` コピーのみ。変換コストゼロ。
- `pyxel_pset()` 等のプリミティブは既存の `gfx_pixel()` をラップ。
- `pyxel_blt()` はプレーナーデータ同士のマスク付きコピーで高速。

## 4. リソースのプレーナー事前変換 (方式C詳細)

### 4-1. イメージバンクのプレーナー化

変換ツール (`pyxres2os32.py`) で以下の変換を行う:

```text
入力: パックトピクセル配列 [256 × 256] (各要素 0-15)

出力: 4プレーン × (256/8) × 256 = 4 × 32 × 256 = 32,768 bytes/bank

Plane B[y][x_byte] = ビット列 (各ビット = 対応ピクセルの色bit0)
Plane R[y][x_byte] = ビット列 (各ビット = 対応ピクセルの色bit1)
Plane G[y][x_byte] = ビット列 (各ビット = 対応ピクセルの色bit2)
Plane I[y][x_byte] = ビット列 (各ビット = 対応ピクセルの色bit3)
```

**Pythonでの変換イメージ:**

```python
def pack_to_planar(pixels_256x256):
    """256x256パックトピクセル → 4プレーン × 32×256 バイト"""
    planes = [bytearray(32 * 256) for _ in range(4)]
    for y in range(256):
        for x_byte in range(32):
            for bit in range(8):
                x = x_byte * 8 + bit
                color = pixels_256x256[y][x]
                mask = 0x80 >> bit
                for p in range(4):
                    if color & (1 << p):
                        planes[p][y * 32 + x_byte] |= mask
    return planes
```

### 4-2. タイルマップのプレーナー化

タイルマップはタイル参照テーブル (タイルX, タイルY の配列) のままバイナリ化し、
描画時にイメージバンクのプレーナーデータから8×8タイルを切り出してコピーする。

> **注意**: 公式仕様ではタイル座標は `u16` 型。ただし実際の有効範囲は
> イメージバンク(256×256)を8で割った 0–31 であるため、
> `.os32res` では `u8` に縮小して保存してもよい。

### 4-3. スプライト (blt) のマスクデータ

透過色 (colkey) を使うスプライト描画では、マスクバイトが必要:

```text
mask[y][x_byte] = 透過でないピクセルのビットが1のバイト列

描画:
  dst_plane[p][offset] = (dst_plane[p][offset] & ~mask) | (src_plane[p][offset] & mask)
```

マスクデータもホスト側で事前生成し、`.os32res` に含める。

## 5. `.os32res` バイナリフォーマット (プレーナー対応版)

```text
オフセット  サイズ  内容
0x0000      4       マジック "PX32"
0x0004      4       バージョン (1)
0x0008      2       イメージバンク数 (0-3)
0x000A      2       タイルマップ数 (0-8)
0x000C      2       サウンド数 (0-64)
0x000E      2       ミュージック数 (0-8)
0x0010      4       イメージセクションオフセット
0x0014      4       タイルマップセクションオフセット
0x0018      4       サウンドセクションオフセット
0x001C      4       ミュージックセクションオフセット

[イメージセクション]
  各バンク:
    プレーンB: 32 × 256 = 8192 bytes   (BPL=32, 256行)
    プレーンR: 8192 bytes
    プレーンG: 8192 bytes
    プレーンI: 8192 bytes
    合計: 32,768 bytes/bank

[タイルマップセクション]
  各マップ:
    imgsrc: 1 byte (参照バンク番号)
    padding: 1 byte
    width: 2 bytes (タイル幅、通常256)
    height: 2 bytes (タイル高、通常256)
    data: width × height bytes (タイルインデックス)

[サウンドセクション]
  各サウンド: 可変長データ
    speed: 2 bytes (u16)
    note_count: 2 bytes (u16)
    notes[note_count]: note_count bytes (i8, -1=休符)
    tones[note_count]: note_count bytes (u8)
    volumes[note_count]: note_count bytes (u8)
    effects[note_count]: note_count bytes (u8)

[ミュージックセクション]
  各ミュージック:
    channel_count: 2 bytes
    各チャンネル:
      seq_count: 2 bytes
      seq[]: seq_count × 2 bytes (サウンド番号、u16)
```

> **注意 (サウンド構造について)**: Pyxel公式ではサウンドのノート配列に
> 明示的な上限はなく可変長である。`.os32res` では `note_count` フィールドで
> 実際のノート数を指定し、各配列はその長さ分だけ格納する。
> OS32のメモリ制約上、変換時に極端に長いサウンドは切り詰めが必要になる
> 可能性がある (実用上 128 ノート程度が上限目安)。

## 6. メモリ消費見積もり

| 項目 | サイズ | 備考 |
|------|--------|------|
| イメージバンク×3 | 96 KB | 32KB/bank × 3 |
| タイルマップ×8 | 最大512 KB | 256×256 bytes/map (実際は使用分のみ) |
| サウンド×64 | 〜8 KB | 可変長 (ノート数次第) |
| ミュージック×8 | 〜1 KB | 可変長 |
| **合計 (典型)** | **〜110 KB** | バンク2つ + マップ2つ程度 |

OS32のユーザーランドメモリ (ext2上の.binがロードされる領域) は数百KB確保可能
であるため、十分に収まる。
