# 03: スケーリング性能検証と設計

## 1. 画面レイアウト

```text
 画面全体: 640 × 400 ピクセル
 ┌────────────────────────────────────┬────────┐
 │                                    │        │
 │       ゲーム領域                    │  UI    │
 │       512 × 384                    │ 128×384│
 │       (256×192 を 2倍拡大)         │        │
 │                                    │        │
 │                                    │        │
 ├────────────────────────────────────┴────────┤
 │              ステータスバー 640 × 16         │
 └─────────────────────────────────────────────┘

 ゲーム領域: X=0, Y=0, W=512, H=384
 UI領域:     X=512, Y=0, W=128, H=384
 ステータス: X=0, Y=384, W=640, H=16
```

**基本構成**: 256 × 192 (Pyxel標準解像度に近い)
**表示倍率**: 2倍 (各ピクセルが 2×2 ドットで表示)
**表示解像度**: 512 × 384

### 解像度候補一覧

ベンチマークで性能を比較し、最適な構成を選択する。

| 候補 | 内部解像度 | 倍率 | 表示解像度 | ゲーム領域 | 転送量(4プレーン) | 特徴 |
|------|-----------|------|-----------|------------|----------------|------|
| **A** | 256×192 | ×2 | 512×384 | 512×384 | 96 KB | Pyxel標準。UI領域128px確保 |
| **B** | 240×160 | ×2 | 480×320 | 480×320 | 75 KB | GBA互換。転送量22%削減 |
| **C** | 480×320 | ×1 | 480×320 | 480×320 | 75 KB | スケーリング不要。高解像度 |

### 解像度選択ガイド (パフォーマンス順)

ゲーム開発者が `pyxel_init()` で指定する解像度の選択指針。
最終的な推奨値は Phase 0 ベンチマーク結果により確定する。

```text
★★★ 性能順ランキング (推定) ★★★

1位: 候補C  480×320×1 (スケーリングなし)
   │  スケーリング工程が完全に不要。描画座標がそのままVRAM座標。
   │  転送量 75KB。実装難度が最も低い。
   │  △ 1ドット = 1ピクセルなのでレトロ感が薄い
   │
2位: 候補B  240×160×2
   │  転送量 75KB (候補Cと同じがスケーリングコストが加算)
   │  GBA互換の解像度。ドットが太くレトロ感強い。
   │  △ スケーリング処理のオーバーヘッドあり
   │
3位: 候補A  256×192×2 (Pyxel標準)
      転送量 96KB (最大) + スケーリングコスト
      Pyxel標準解像度で互換性最高。右側128pxのUI領域も確保。
      △ 最も遅いが、ダーティレクタングルで補優可能
```

**全候補共通**: ダーティレクタングル方式を併用することで、
実際の転送量を大幅に削減できる（変更領域のみ転送）。

## 2. データ転送量の計算

### 2-1. プレーナー方式でのデータ量

```text
ゲーム領域 (512 × 384):
  bytes_per_line = 512 / 8 = 64 bytes
  lines = 384
  1プレーン = 64 × 384 = 24,576 bytes
  4プレーン = 24,576 × 4 = 98,304 bytes ≈ 96 KB

全画面 (640 × 400):
  1プレーン = 80 × 400 = 32,000 bytes
  4プレーン = 128,000 bytes ≈ 125 KB
```

### 2-2. 既存のgfx_present_rect のベンチマーク参考値

既存の GFX デモ (`tests/gfx_demo.c`) では 320×200 ビューポートで:
- 8スプライト + 16パーティクル描画
- `gfx_present_rect(VP_X, VP_Y, 320, 200)` で部分転送
- **目標は30fps以上を達成**

320×200 の転送量:
```text
  1プレーン = 40 × 200 = 8,000 bytes
  4プレーン = 32,000 bytes = 32 KB
```

512×384 の転送量は 96KB であり、320×200 の **約3倍**。

## 3. 転送性能の理論値

### 3-1. `rep movsw` のスループット

i386 (8MHz) での `rep movsw` は約2サイクル/ワードと仮定:

```text
転送速度 ≈ 8MHz / 2 = 4MW/s = 8MB/s (メインメモリ間)
```

ただし、VRAMアクセスはI/Oウェイトステートが入るため遅くなる:

```text
VRAM転送速度 ≈ 2〜3 MB/s (推定、ウェイト込み)
```

### 3-2. フレーム時間の計算

```text
60fps: フレーム時間 = 16.7 ms
30fps: フレーム時間 = 33.3 ms
20fps: フレーム時間 = 50.0 ms
```

96KB のVRAM転送にかかる時間:
```text
最良ケース (3 MB/s): 96KB / 3MB = 32.0 ms  → 30fps ギリギリ
最悪ケース (2 MB/s): 96KB / 2MB = 48.0 ms  → 20fps
```

> **【要検証】**: 上記は理論値。実機/NP21Wでのベンチマークが必須。
> スケーリング転送のオーバーヘッドも加算される。

## 4. スケーリング転送方式の設計

### 4-1. 方式: プレーナーバックバッファ直描画 + スケーリング転送

**ゲーム描画はバックバッファの 256×192 相当領域にプレーナーで直接行い、
VRAM転送時に2倍拡大する。** バックバッファ自体は640×400のフル解像度。

```text
描画: BB[y][x_byte] に通常通り描画 (256×192 領域)
転送: BB → VRAM に1行ずつ2倍拡大転送
```

**スケーリング転送の擬似コード (1プレーン分):**

```c
/*
 * 256ピクセル/行 = 32バイト/行 (ソース)
 * 512ピクセル/行 = 64バイト/行 (デスティネーション)
 *
 * 各バイトの8ビットを16ビット (各ビットを2回繰り返し) に拡大
 */

/* 事前計算LUT: 1バイト → 2バイト (各ビットを2倍に展開) */
static u16 scale2x_lut[256];

void init_scale2x_lut(void)
{
    int i, bit;
    for (i = 0; i < 256; i++) {
        u16 val = 0;
        for (bit = 0; bit < 8; bit++) {
            if (i & (0x80 >> bit)) {
                val |= (0xC000 >> (bit * 2)); /* 2ビット分セット */
            }
        }
        scale2x_lut[i] = val;
    }
}

void scale2x_present(void)
{
    int plane, src_y;
    for (plane = 0; plane < 4; plane++) {
        u8 *src_plane = bb[plane];
        u8 *dst_plane = (u8 *)vram_base[plane];

        for (src_y = 0; src_y < 192; src_y++) {
            int dst_y = src_y * 2;
            u8 *src_row = src_plane + src_y * 80;  /* BBピッチ=80 */
            u8 *dst_row0 = dst_plane + dst_y * 80;
            u8 *dst_row1 = dst_row0 + 80;           /* 次の行 */
            int x_byte;

            for (x_byte = 0; x_byte < 32; x_byte++) {
                u16 expanded = scale2x_lut[src_row[x_byte]];
                /* 拡大した2バイトを書き込み */
                dst_row0[x_byte * 2]     = (u8)(expanded >> 8);
                dst_row0[x_byte * 2 + 1] = (u8)(expanded & 0xFF);
                /* 同じデータをY方向にも複製 */
                dst_row1[x_byte * 2]     = (u8)(expanded >> 8);
                dst_row1[x_byte * 2 + 1] = (u8)(expanded & 0xFF);
            }
        }
    }
}
```

### 4-2. LUT方式の演算量

```text
1行の処理:
  - 32回のLUT参照 (テーブル引き)
  - 32×4 = 128回のバイト書き込み (dst_row0, dst_row1 各2バイト)

1プレーン:
  - 192行 × (32 LUT参照 + 128 書き込み) = 192 × 160 = 30,720 操作

4プレーン:
  - 30,720 × 4 = 122,880 操作
```

### 4-3. アセンブラ最適化の可能性

内側ループはアセンブラ化で大幅に高速化できる:

```nasm
; esi = src_row, edi = dst_row0, ebx = scale2x_lut base
; ecx = 32 (バイト数)
.loop:
    movzx eax, byte [esi]       ; ソース1バイト読み出し
    mov   ax, [ebx + eax*2]     ; LUT引き (16bit値取得)
    mov   [edi], ax             ; dst_row0 に書き込み
    mov   [edi + 80], ax        ; dst_row1 に書き込み (次行)
    inc   esi
    add   edi, 2
    dec   ecx
    jnz   .loop
```

このループは反復あたり約10サイクル。
4プレーン × 192行 × 32反復 = 24,576 反復 × 10 = 245,760サイクル。
8MHzで 約30ms。
— これにVRAMウェイトが乗るため、**直接VRAM書き込みすると50-60ms** になる恐れ。

### 4-4. 代替案: バックバッファにスケーリング展開してから転送

```text
[256×192 描画領域 (BB内)] → [BB内の512×384領域にスケーリング展開] → [gfx_present_rect]
```

バックバッファ (メインメモリ) 上でスケーリング展開すれば、メモリ→メモリの転送は
VRAMアクセスよりはるかに高速。展開後、`gfx_present_rect(0, 0, 512, 384)` で
通常の `rep movsw` VRAM転送を行う。

**この方式の場合:**
1. BBメモリ間スケーリング: メモリ速度で 96KB ≈ 12ms
2. VRAM転送: 96KB ≈ 32ms
3. **合計: ~44ms → 約22fps**

## 5. 性能改善策

### 5-1. ダーティ領域ベースのスケーリング

毎フレームで全画面をスケーリングするのではなく、変更のあったタイル領域のみを
スケーリング + VRAM転送する:

```text
ダーティ領域 = 変更のあった8×8タイル群のバウンディングボックス
              → その領域のみ2倍展開 + present_rect
```

スプライト8個 + 背景スクロールなしの場合、ダーティ面積は画面の10-20%程度。
転送量が 1/5 〜 1/10 になれば **60fps近くも視野に入る**。

### 5-2. 描画を直接2倍座標で行う

プリミティブ描画関数を2倍座標系にして、バックバッファの512×384領域に
直接2倍サイズで描画することで、スケーリング工程を省略:

```c
void pyxel_pset(int x, int y, u8 color)
{
    int rx = x * 2;
    int ry = y * 2;
    /* 2×2 ブロックとして描画 */
    gfx_fill_rect(rx, ry, 2, 2, color);
}
```

**利点**: スケーリング転送工程が不要。
**欠点**: `blt` / `bltm` は1ピクセルずつ展開が必要で重い。

### 5-3. 方式選択のまとめ

| 方式 | 推定FPS | 実装難度 | 備考 |
|------|---------|---------|------|
| 全画面スケーリング毎フレーム | 15-22 | 低 | 最もシンプルだが遅い |
| ダーティ領域スケーリング | 30-60 | 中 | 推奨。タイル単位で管理 |
| 2倍座標直接描画 | 30-45 | 中 | blt/bltm の実装が課題 |
| LUT+ASMスケーリング | 20-30 | 高 | VRAMウェイトが支配的 |
| **480×320 スケーリングなし** | **30-60** | **低** | **スケーリング工程不要。要測定** |

**推奨**: ダーティ領域方式を基本とし、まずは全画面スケーリングで動作検証を行い、
実測FPSに基づいて最適化戦略を選択する。

## 6. ベンチマーク計画

実装前に、以下のマイクロベンチマークを `tests/` 以下に作成して実測する:

1. **memcpy ベンチマーク**: メモリ→メモリ、メモリ→VRAM それぞれの `rep movsw` 速度
2. **LUT展開ベンチマーク**: 256→512 の LUT 展開速度 (メモリ→メモリ)
3. **全画面転送ベンチマーク**: 以下の3解像度で `present_rect` 所要時間を比較:
   - 512×384 (候補A: 256×192×2)
   - 480×320 (候補B: 240×160×2 / 候補C: 480×320×1)
4. **ダーティレクタングルベンチマーク**: 各解像度で以下のケースを計測:
   - 小ダーティ: 32×32 矩形 ×1個 (スプライト1枚相当)
   - 中ダーティ: 64×64 矩形 ×4個 (複数スプライト)
   - 大ダーティ: 160×128 矩形 ×1個 (画面の約1/3)
   - 全画面ダーティ: 全領域 (全画面転送との差を確認)
5. **§4-3 ASMスケーリング検証** (§4-3 の理論値を実測で確認):
   - C実装 (`scale2x_present`) の1フレームあたり所要時間
   - ASM実装 (LUT+`mov`ループ) の1フレームあたり所要時間
   - メモリ→メモリ展開のみ / メモリ→VRAM直接展開 のそれぞれを計測
   - 候補A (256→512) と候補B (240→480) の両方で実測
6. **gfx_fill_rect ベンチマーク**: 2×2 ブロックの連続描画速度
7. **スケーリング有無比較**: 同一描画内容で ×2スケーリング転送 vs ×1直接転送 のFPS差
8. **総合ベンチマーク**: 実際のゲームループを模擬した測定:
   - 背景クリア + スプライト8枚描画 + dirty rect転送
   - 3候補それぞれでFPSを計測

各ベンチマークを `tick_count` (100Hz) で計測し、ミリ秒単位でレポートする。

**ベンチマーク結果の判断基準:**

| 条件 | 判断 |
|------|------|
| 全候補で 30fps 以上 | 候補A (最高互換性) を採用 |
| 候補Aのみ 30fps 未満 | 候補B または C を採用 |
| 全候補で 30fps 未満 | ダーティレクタングル必須、候補C 優先 |

> **注意**: 480×320×1 (候補C) が十分な性能を示した場合、スケーリング工程を
> 完全に省略できるため、実装難度が大幅に下がる。ただしドットが細かくなるため、
> レトロゲーム感とのトレードオフを考慮する必要がある。
