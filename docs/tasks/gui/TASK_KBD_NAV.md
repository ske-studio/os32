# TASK_KBD_NAV — マウスなしで GUI を操作する (WM のショートカット + マウスキー)

> 発行: PM (Claude Code `claude-opus-5-5`、2026-09-25) / 状態: **方針案 (Codex の設計レビュー待ち)**
> 背景: 実機 PC-9821Ra266 にはバスマウスが無い。GUI (gshell) は窓の中のウィジェット・開いた後のメニュー・WM のダイアログはキーで操作できるが、**WM の操作 (スタートメニューを開く、窓の切り替え・移動・閉じる、右クリックメニュー) とポインタの移動はマウスが前提**。ユーザー依頼 (2026-09-25): 「キーボードだけで GUI を操作するためのショートカット群」。マウスモードの切り替えは「ラッチの効く、あまり使わないキー」 → **カナ** (ユーザー提案)。

## 0. 事実 (2026-09-25 の調査、ファイル:行)

- キーは IRQ1 → raw リング → gshell `capture_keyboard` (`userland/gshell/src/input.rs:270-452`)。1 件 = `scan | down<<8 | mods<<9`。mods の並びは `drivers/kbd.h:131-135` (SHIFT 01 / CAPS 02 / **KANA 04** / GRPH 08 / CTRL 10)。修飾キー自身 (0x70-0x74) は Key として配らない (input.rs:349)。
- 振り分けの順: 修飾 → CTRL+STOP (強制終了) → SHIFT+SPACE (FEP) → modal → startmenu → (窓なし) standalone → FEP → 最前面の窓 (input.rs:357-447)。
- **カナ**: `drivers/kbd.c:299` は **make でだけ状態を反転**し break を無視する (CAPS も同じ)。OS32 のどこもカナの状態を使っていない (FEP はローマ字入力、`ime` のカタカナは `ime_set_mode` で別)。キーボードが「ロックで make、解除で break」を送る方式 (機械式ロック) だと反転のしかたが合わない可能性 → **実機で確かめる (§3)**。
- ポインタを動かす KAPI は無い (`sdk/kapi.json` の mouse_* は poll / available / bounds / cursor mode のみ)。gshell は毎周期 `mouse_poll` の値で `st.mouse_x/y` を上書きする (input.rs:454-)。
- X4 (ポンプ中は状態機械を進めない) の制約 (input.rs:23-42)。

## 1. 方針

### 1-1. WM のショートカット (GRPH を Alt の代わり、PC-98 に Alt / Win は無い)

| 操作 | キー | 備考 |
|---|---|---|
| スタートメニューを開く / 閉じる | CTRL+ESC | 開いた後は既存の ↑↓ / RETURN / ESC |
| 窓を順に切り替える (逆順は SHIFT も) | GRPH+TAB | 最小化した窓も対象。切り替えは押すたびに確定 (Alt+Tab の一覧は出さない、v1 は最小) |
| 最前面の窓を閉じる | GRPH+f･4 | アプリへ閉じる要求 (閉じるボタンと同じ経路) |
| 窓メニュー | GRPH+SPACE | 移動 / サイズ / 最小化 / 最大化 / 閉じる (既存の右クリックメニューの部品で出す) |
| 移動・サイズ変更の実行中 | ↑↓←→ で 8 ドット、SHIFT+矢印で 1 ドット、RETURN で決定、ESC で元に戻す | XOR 枠 (既存の方式) で表示 |
| 右クリックメニュー | SHIFT+f･10 | ポインタの位置ではなく最前面の窓 / デスクトップに対して出す |
| タスクバーにフォーカス | GRPH+ESC (案) | ←→ でボタン、RETURN で窓を前へ。v1 で要るかはレビューで判断 |

- 取る場所: `capture_keyboard` の **modal / startmenu より前、FEP より前**。ただし CTRL+STOP と SHIFT+SPACE は今の順のまま先に処理する。modal が開いているときは GRPH+TAB と窓メニューを出さない (モーダルの意味を壊さない)。
- アプリへ渡さない: 上のキーは WM が消費し、窓へ Key を積まない。GRPH 単独や f･4 単独は今までどおり窓へ。

### 1-2. マウスキー (カナ = マウスモード)

- **カナの状態がオンの間だけ**、テンキーをポインタの操作に使う。オフならテンキーは数字 (今までどおり)。
- テンキー: 8 / 2 / 4 / 6 で上下左右、7 / 9 / 1 / 3 で斜め。押し続けると加速 (最初 1 ドット → 16 tick 後から 4 ドット → 32 tick 後から 8 ドット、定数 1 か所)。5 で左クリック (押下と解放)。0 で左ボタンを押したまま (ドラッグ開始)、「.」で離す。「+」で右クリック。「-」でダブルクリック (案)。
- 実装は **gshell の中だけ** (KAPI・カーネルは変えない): キーで作った dx/dy とボタンを `capture_mouse` の入力に足し込み、既存の `wm_button_down/up` / `forward_pointer` に流す。本物のマウス (NP21/W のシームレスモードを含む) の絶対座標と重なるときは、**最後に動いた方が勝つ** (本物が動いたら、その値から続ける)。
- 表示: マウスモード中はタスクバーに小さな印 (例: `[M]`) を出す。
- CUI (テキストモード) では何もしない。

### 1-3. カナの状態の取り方 (§3 の実機確認の結果で決める)

- 方式 A (今のドライバのまま): 修飾ビット KANA (make で反転) をそのまま使う。
- 方式 B (機械式ロックの場合): カナの make でオン、break でオフ。`drivers/kbd.c:299` を直す (CAPS も同じ扱いにそろえるかを判断)。
- どちらになってもよいように、gshell は **修飾ビット KANA だけを見る** (ドライバ側で正しい状態を作る)。

## 2. レビューに見てほしいこと

1. キーの割り当てが既存のアプリ (edit_gui、filer、ゲーム) のキーとぶつからないか。特に GRPH+TAB、SHIFT+f･10、テンキー (カナ中)。
2. 取る順番 (FEP より前) で FEP の入力を壊さないか (FEP 中の GRPH / テンキー)。
3. マウスキーの足し込みが X4 の制約と矛盾しないか、本物のマウスとの競合の規則。
4. 窓の切り替えで最小化した窓・モーダル・スタートメニューの扱い。
5. v1 に入れるものと後回しでよいもの (タスクバーのフォーカス、ダブルクリック、Alt+Tab の一覧)。

## 3. 実機で確かめること (次の実機の回)

1. シリアルで `kbdstat` → 本体のカナを 1 回押す → `kbdstat` → もう 1 回押す → `kbdstat`。`code` と `now`、押したときに make だけか make+break か。**カナを押したまま (ロック) の間に break が来るか**。
2. 結果で方式 A / B を決める。
