# V86 Mode — Phase 1 & 2 (進行中) 報告レポート

## 概要

OS32のV86モード実装において、Phase 1 (V86メモリ空間とCOM実行) を完了し、Phase 2 (FreeDOSブート) の機能実装に移行した。本ドキュメントではここまでの実装内容と遭遇した重要なバグ、およびその解決策を記録する。

---

## Phase 1 完了: V86メモリ空間と基本BIOSエミュレーション

### 実装内容

1. **ページング (`v86_mem.c`)**: 
   - 0x00000 - 0x100000 (1MB) を全て V86用のページ (PTE_USER, PTE_RW) としてマッピングする仕組みを構築。
   - BDA (BIOS Data Area) と IVT (Interrupt Vector Table) の初期化を実装。
   - IVT には全256ベクタにダミーIRET (0xCF) のハンドラを配置。
2. **BIOSエミュレーション (`v86_bios.c`)**:
   - `INT 18h`: PC-98 テキストBIOS。AH=0Ah(モード設定), AH=16h(VRAMクリア), AH=13h(カーソル設定)を実装。
   - `INT 29h`: DOS 1文字高速出力。
3. **テスト検証 (`HELLO.COM` & `HELLO_BIOS.COM`)**:
   - TVRAMへの直接書き込みによる表示と、BIOS(INT 18h / 29h)を通じた文字表示テストがともにパス。

---

## Phase 2 進行状況: PIC仮想化とカレンダBIOS

Phase 2 では FreeDOS の KERNEL.SYS をブートするためのハードウェア仮想化を進めている。

### 実装内容

1. **カレンダBIOS (`INT 1Ch`)**:
   - `AH=00h` を実装し、OS32ネイティブの `rtc_read()` を呼び出して BCD (Binary Coded Decimal) 形式の 6バイトデータに変換し、V86側に返す処理を追加。
2. **PIC仮想化 (`v86_pic.c`)**:
   - V86モードから実ハードウェアのPICを直接操作させないため、マスタ (00h/02h) とスレーブ (08h/0Ah) の IN/OUT をトラップ。
   - IMR (Interrupt Mask Register) および EOI (End of Interrupt) 等をカーネル内で仮想レジスタとして管理するロジックを実装。
3. **リブート検知 (OUT 0xF0)**:
   - DOS アプリケーションの終了 (`INT 20h` 等) やキーボードリセット時の `OUT 0xF0, 0x00` を検知し、OS32のシェルに安全に復帰 (V86モード終了) する仕組みを実装。

---

## 発生した致命的バグと教訓 (Phase 1/2)

### 1. V86 #GP ハンドラ内でのスタックオーバーフロー
- **症状**: `HELLO_BIOS.COM` 実行中、`INT 18h` などのエミュレーション中にトリプルフォルト (`cr2=0008fffc` — カーネルスタック底付近への不正アクセス) が発生。
- **原因**: 
  - V86 用のカーネルスタックが `4096` バイトと小さすぎた。
  - V86からの #GP や IN/OUT トラップを処理している最中に、タイマ割り込み (IRQ0, 100Hz) がネストして発生し、スタックを食いつぶしていた。
- **解決策**:
  - `v86_kstack` のサイズを `16384` (16KB) に拡張。

### 2. V86 モード中のハードウェア割り込み発生時の DS/ES 未復元
- **症状**: 割り込みを許可 (`STI`) して実行していると、ランダムにトリプルフォルトが発生。
- **原因**: 
  - CPU は V86 モード (Ring 3) から カーネルモード (Ring 0) への割り込み発生時、**DS / ES / FS / GS セグメントレジスタを `0` にクリア** する仕様がある (Intel SDM 準拠)。
  - `isr_stub.asm` において、`v86_gp` パスではこれを考慮して `DS=0x10`, `ES=0x10` に設定していたが、**タイマ (IRQ0) やキーボード (IRQ1) などの純粋なハードウェア割り込み (IRQスタブ) では復元を忘れていた**。
  - その結果、V86モード中にタイマ割り込みが発生すると、DS=0 の状態で C言語のハンドラ (`timer_handler`) が呼び出され、グローバル変数 (`tick_count` など) にアクセスした瞬間に #GP が発生してトリプルフォルトに陥っていた。
- **解決策**:
  - 全ての IRQスタブ (`irq_stub_0`, `1`, `4`, `11`, `13`) の先頭 (PUSHAD 直後) に、`DS` と `ES` を保存し、`0x10` (カーネルデータセグメント) に設定するコードを追加し、IRET 前に復元するように修正。

```nasm
;; 例: irq_stub_0
        push    ds
        push    es
        pushad
        
        ;; ★ V86モードからの割り込み時、CPUがDS/ESを0にクリアするため復元
        mov     ax, 0x10
        mov     ds, ax
        mov     es, ax
        
        ;; Cハンドラを呼び出し
        call    timer_handler
        
        ;; ... EOI送出等 ...
        
        popad
        pop     es
        pop     ds
        iretd
```

> [!CAUTION]
> x86 の V86モードにおいて、「割り込み・例外発生時に CPU がデータセグメントを 0 にクリアする」という仕様は忘れがちであり、全ハンドラでのケアが必須である。
